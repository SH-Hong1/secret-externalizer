# 추천 이름의 환경, 이전 판정의 이름, Ant 비밀번호의 분류

- 날짜: 2026-11-23
- 상태: 확정

## 배경

판정 화면이 추천하는 이름은 `분류.대상.항목`이었다(`db.main.password`). 써 보니 두 가지가 어색했다.

- `application-prod.yml`과 `application-dev.yml`의 비밀번호가 `db.main.password`, `db.main2.password`로 추천되어 이름만 보고는 어느 환경의 값인지 알 수 없었다. 이름은 OpenBao의 저장 경로가 되므로 값이 다르면 이름도 달라야 하는데, 다른 점이 숫자뿐이었다.
- Ant `build.xml`의 `<scp password="…">`와 `deploy.password` 속성이 `db.….password`로 추천되었다. 규칙 `ant-task-password`와 `ant-property-password`가 `build.xml`의 모든 비밀번호를 `storage-credential`로 분류했고, 이름의 첫 마디는 분류에서 오기 때문이다. 또 `<scp file="…" … password="…">` 줄에서는 줄의 첫 `=` 앞에 있는 `file`이 대상이 되었다.

- 같은 값을 다른 곳에서 판정한 적이 있으면 판정 화면은 그 판정과 이름을 그대로 제안했다. 저장 경로는 프로젝트마다 따로인데(`projects/<ID>/ext.<이름>`) 이름은 프로젝트를 넘어 따라왔고, 다른 프로젝트에서 다른 파일을 보고 붙인 이름이 지금 묶음의 환경이나 분류와 맞지 않아도 그대로 제안되었다. 같은 예제를 두 번째 프로젝트로 등록하면 모든 추천이 첫 프로젝트의 이름이었다.

## 결정

1. 묶음의 모든 파일이 같은 환경을 가리키면 이름은 `분류.환경.대상.항목`이다(`db.prod.main.password`, shell에서는 `EXT_DB_PROD_MAIN_PASSWORD`). 환경이 없으면 지금처럼 `분류.대상.항목`이다.
2. 환경은 파일 경로에서 읽는다. 확장자를 뺀 파일 이름의 마지막 단어부터 보고, 없으면 가까운 폴더부터 본다. 단어는 글자와 숫자가 이어진 것이고 대소문자를 가리지 않는다. 대문자 경계에서는 나누지 않는다(`LocalCache.java`는 환경이 없다).

   | 이름에 쓰는 환경 | 경로의 단어 |
   |---|---|
   | `prod` | `prod`, `production`, `prd`, `real`, `live` |
   | `stg` | `stg`, `stage`, `staging` |
   | `uat` | `uat` |
   | `qa` | `qa` |
   | `test` | `test`, `tst` |
   | `dev` | `dev`, `develop`, `development` |
   | `local` | `local` |

3. 묶음의 파일 가운데 환경이 없는 것이 있거나 두 파일의 환경이 다르면 환경을 넣지 않는다. 같은 값을 여러 환경이 함께 쓰는 묶음이기 때문이다.
4. 파일에서 환경을 얻지 못했고 키의 첫 단어가 환경이면(`prod.order.password=`) 그것을 환경으로 쓰고, 그 다음 단어가 대상이다. 키의 첫 단어가 파일의 환경과 같으면 한 번만 쓴다. 다르면 파일의 환경을 쓰고 키의 단어는 대상으로 남는다.
5. 대상을 정하는 키는, 줄에 `name="…"` 속성이 없으면 찾은 값 바로 앞에 적힌 키다(위치의 시작 열로 찾는다). 값 바로 앞에 키가 없으면 지금처럼 줄의 첫 `=`나 `:` 앞의 것이다.
6. Ant 규칙을 넷으로 나눈다.
   - `ant-remote-task-password`(`ssh-credential`): `<scp>`, `<sshexec>`, `<sshsession>`, `<ftp>`, `<telnet>`, `<rexec>`의 `password`, `passwd`, `passphrase`.
   - `ant-task-password`(`storage-credential`): 그 밖의 작업의 `password`, `passwd`, `storepass`, `keypass`.
   - `ant-remote-property-password`(`ssh-credential`): 이름에 `ssh`, `scp`, `ftp`, `deploy`, `remote`가 든 비밀번호 속성.
   - `ant-property-password`(`storage-credential`): 그 밖의 비밀번호 속성.
7. 이전 판정에서는 판정과 보류 사유만 이어받는다. 외부화를 제안할 때의 이름은 언제나 지금 묶음에서 위 규칙으로 만든다. 화면의 "같은 값을 다른 곳에서 …(으)로 판정했습니다" 안내는 그대로다.

## 이유

- 환경을 분류 뒤에 둔 것은 환경이 없는 이름과 첫 마디가 같게 하기 위해서다. 이미 판정한 이름(`db.main.password`)과 나란히 놓여도 분류로 묶인다.
- 환경을 파일 경로에서 읽는 것은 레거시 프로젝트가 환경을 파일로 나누기 때문이다(`application-prod.yml`, `conf/dev/jdbc.properties`). 주변 줄에는 환경이 없는 경우가 많다.
- 대문자 경계에서 나누지 않는 것은 Java 클래스 이름(`LocalDateUtil`, `TestHelper`)이 환경으로 읽히지 않게 하기 위해서다. 그 대신 `applicationProd.properties`는 환경을 얻지 못한다.
- 이름은 추천일 뿐이고 사람이 고칠 수 있다. 그래서 틀리면 사람이 고치는 값이 드러나는 쪽(환경을 넣는 쪽)을 골랐다.
- `deploy.password`는 무엇의 비밀번호인지 이름만으로 확정할 수 없다. Ant에서 `deploy`는 대개 다른 서버로 보내는 일이므로 `ssh-credential`로 본다. 틀린 분류는 화면과 리포트의 분류 건수에만 영향을 주고, 판정과 적용은 분류와 상관없이 같다.
- 이미 저장된 항목의 분류는 다음 스캔이 새 규칙으로 다시 정한다. 이미 판정한 이름은 바뀌지 않는다.
- 이전 판정의 이름을 이어받지 않는 것은 이름이 가리키는 것이 값이 아니라 자리이기 때문이다. 같은 값이라도 어느 환경의 어느 저장소에 쓰이는지는 지금 묶음의 파일과 분류가 말한다. 저장 경로가 프로젝트마다 따로라서 프로젝트 사이에 이름이 같아도 값이 한 곳에 모이지 않는다.

## 검토한 다른 방법

- 환경을 맨 앞에 두기(`prod.db.main.password`): 저장소에서 환경별로 모으기 쉽지만, 환경이 없는 이름과 첫 마디의 뜻이 달라진다.
- 환경이 다른 파일에 같은 값이 있을 때 첫 파일의 환경 쓰기: 다른 환경도 같은 이름을 쓰게 되어 이름이 사실과 다르다.
- 분류는 그대로 두고 이름의 첫 마디만 줄의 내용으로 바꾸기: 화면과 리포트, 대시보드의 분류 건수는 여전히 SSH 비밀번호를 DB로 센다.
- 찾은 값과 가장 가까운 키 고르기: 같은 줄의 앞쪽 값이 가려지면서 길이가 달라지면 열이 어긋나 옆 키를 고를 수 있다. 정확히 값 바로 앞일 때만 쓰고 아니면 이전 방법으로 돌아간다.
- 이전 판정의 이름을 같은 프로젝트 안에서만 이어받기: 한 프로젝트 안에서 지문이 같은 항목은 한 묶음이므로, 이어받을 일은 사람이 묶음을 나눈 때뿐이다. 그때는 다른 대상이라서 나눈 것이므로 같은 이름이 맞지 않다.
