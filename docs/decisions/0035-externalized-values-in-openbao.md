# OpenBao의 외부화 값

- 날짜: 2026-11-20
- 상태: 확정

## 배경

적용은 판정이 `externalize`인 묶음의 값을 소스에서 빼내 OpenBao에 저장하고, 소스의 그 자리를 placeholder로 바꾼다. 추적되지 않는 파일(키 파일, 무시된 설정 파일)에서 뺀 값은 OpenBao의 저장본이 유일한 사본이 될 수 있다. 그래서 저장 경로, 저장하는 자료, 이미 값이 있을 때의 동작, worker의 권한, 한 번에 보낼 수 있는 크기를 정해야 한다. 계획 5 문서의 검토 항목 9, 10, 11, 27이 정한 안을 따르고, 구현하면서 확인한 사실과 정한 한도를 적는다.

## 결정

1. **저장 경로는 `secret/data/projects/<프로젝트 ID>/ext.<이름>`이다**(검토 항목 9). `bao.StorePath`가 만든다. 마지막 마디는 파일 종류와 상관없이 설정 표기 하나라서, 한 묶음이 `.yml`과 `.sh`에 걸쳐 있어도 값은 한 곳에 있다. 키는 `^ext\.[a-z][a-z0-9]*(\.[a-z][a-z0-9]*){1,4}$`에 맞고 104바이트 이하여야 하며, 아니면 OpenBao를 부르지 않고 오류다. 프로젝트 ID는 양수여야 한다. 그래서 키가 경로 마디를 더하거나 다른 프로젝트, `pending/` 경로를 가리킬 수 없다. 이 검사는 패키지 변수의 정규식이 아니라 함수로 한다.
2. **저장하는 자료는 `value`(base64), `encoding`(`base64`), `format`(`text` 또는 `file`), `fingerprint`, `kind` 다섯 필드다**(검토 항목 10). 텍스트 값은 스캔이 지문을 만든 것과 같은 UTF-8 바이트(EUC-KR 파일의 값도 UTF-8로 바꾼 것)이고, 키 파일은 디스크의 바이트 그대로다. 언제나 base64라서 NUL이 든 바이너리도 같은 길로 간다.
3. **저장되는 값은 소스에 적힌 글자 그대로다.** XML의 `&amp;`, properties와 Java의 `\` 이스케이프, YAML의 따옴표 안 이스케이프를 풀지 않는다. 풀어 쓴 값이 필요한 쪽은 파일 종류를 보고 풀어야 한다. `docs/next-steps.md`에 남은 일로 적었다.
4. **쓰기는 언제나 check-and-set이다**(검토 항목 11). `PutStored`는 `options.cas`를 보낸다. KV v2는 경로가 그 버전이 아닐 때 400으로 답하지만, 다른 거절(데이터 없음, `cas_required`, 저장소의 크기 거절 등)도 400이다. 그래서 400을 받으면 경로를 다시 읽고, 지금 버전이 `cas`와 다를 때만 `ErrVersionConflict`를 돌려준다. 버전이 `cas` 그대로면 정해진 글의 일반 오류다(다시 써도 성공하지 않는다). **충돌은 결코 "저장되었다"는 뜻이 아니다.** 충돌을 받은 쪽은 경로를 다시 읽어 저장된 바이트의 HMAC을 비교하고, 필요하면 읽은 버전으로 다시 쓰되 다시 쓰는 횟수에 한도를 둔다. 403은 다시 로그인한 뒤에도 거절되면 `ErrForbidden`이다. `ReadStored`는 값, 버전, `File`(`format`이 `file`)을 돌려주고, 한 번도 쓰지 않은 경로는 `ErrNotStored`, 마지막 버전이 soft-delete되었거나 destroy된 경로는 `Deleted: true`와 그 버전을 돌려준다. `encoding`이 `base64`가 아니거나 `format`이 `text`, `file`이 아닌 기록(그 경로에 다른 무엇이 쓴 기록)은 정해진 글의 오류다. 이미 값이 있을 때 비교, 같으면 쓰지 않기, 다르면 새 버전 쓰기, 쓴 뒤 다시 읽어 확인하기는 적용 실행기(Task 10)가 이 두 함수로 한다. 비교는 저장된 바이트의 HMAC을 다시 계산해 하고, 저장된 `fingerprint` 필드는 쓰지 않는다.
5. **`PutStored`는 고객정보 종류(`finding.Kind.CustomerData`)와 `finding`이 모르는 종류를 OpenBao를 부르지 않고 거부한다.** "고객정보의 값은 `projects/`에 쓰지 않는다"를 적용 실행기의 계획과 따로 한 번 더 지킨다.
6. **KV v2 마운트 `secret`은 경로마다 100개 버전을 남긴다.** 기본값은 10개라서 11번째 쓰기가 첫 버전을 지운다. 그 첫 버전이 값의 유일한 사본일 수 있으므로 `config.hcl`의 self-init이 마운트 직후 `secret/config`에 `max_versions = 100`을 쓴다(`kv-max-versions` 요청). worker는 버전을 지울 수 없으므로, 한 경로에 100번 넘게 다른 값을 쓰지 않는 한 이전 값이 남는다. 테스트는 같은 설정을 테스트 서버에 쓰고, `TestKVConfigMatchesConfig`가 `config.hcl`의 요청을 확인한다.
7. **worker 정책은 `secret/data/projects/*`에 `create`, `update`, `read`만 가진다**(검토 항목 27). 지우기(`delete`), `secret/metadata/projects/*`, `secret/destroy/projects/*`는 없다. 그래서 worker는 이전 버전을 지울 수 없다. web 정책은 그대로(`read`)다. 테스트의 `workerPolicy`, `webPolicy` 상수가 `config.hcl`의 정책과 같은 글인지 `TestPolicyMatchesConfig`가 확인하므로, 통합 테스트가 확인하는 권한이 실제 서버의 권한이다.
8. **지문 요청은 값 500개 또는 값의 바이트 합 8MiB(`maxBatchBytes`)에서 나눈다.** 8MiB보다 큰 값 하나는 혼자 한 요청이다.
9. **값 하나의 최대 크기 `apply.DefaultMaxStoredBytes`는 16MiB(16,777,216바이트)로 둔다.** 이보다 큰 값은 저장하지 않고 `too-large`로 건너뛴다. 16MiB 값의 base64는 약 21.4MiB라 지문 요청 하나와 쓰기 요청 하나가 모두 OpenBao의 요청 한도 32MiB 안에 여유 있게 든다. 실제 서비스(pebbledb)는 항목 크기에 따로 한도가 없고 요청 크기 한도만 있음을 확인했다(아래).
10. **보내는 base64 문자열과 클라이언트 라이브러리의 버퍼는 0으로 지울 수 없다.** Go 문자열과 공식 클라이언트가 만드는 요청 본문, 응답을 읽은 버퍼는 이 패키지가 손댈 수 없다. `PutPending`과 같은 한계이고, 값은 worker 프로세스의 메모리에만 있다.

## 확인한 사실

2026-11-20에 `openbao-test`(OpenBao 2.7.2, `-dev` 메모리 서버)에서 확인했다.

- `options.cas` 0은 경로가 비어 있을 때만 성공하고, 버전이 있으면 400(`check-and-set parameter did not match the current version`)이다. N은 지금 버전이 N일 때만 성공하고, 다르면 같은 400이다.
- 쓰기 응답의 버전은 `data.version`, 읽기 응답의 버전은 `data.metadata.version`이다.
- 한 번도 쓰지 않은 경로의 읽기는 본문 `{"errors":[]}`의 404다. 공식 Go 클라이언트는 이것을 `nil, nil`로 돌려준다.
- 마지막 버전을 soft-delete하면 읽기는 404지만 본문에 `data: null`과 `metadata.version`(N), `deletion_time`이 온다. destroy하면 `deletion_time`은 비고 `destroyed: true`다. 공식 클라이언트의 `Read`는 이 본문을 돌려준다. 그 경로에 `cas 0`은 400, `cas N`은 성공해 버전 N+1이 된다.
- 경로 마디에 `.`을 쓸 수 있다(`ext.db.main.password`).
- KV v2 마운트의 `max_versions`는 기본 0이고, 이는 경로마다 10개 버전을 남긴다는 뜻이다. 12번 쓰면 버전 3~12만 남고 `oldest_version`이 3이 된다. 새로 만든 KV v2 마운트에 바로 `config`로 `max_versions = 100`을 쓰면 204이고, 그 뒤 11번 써도 버전 1이 읽힌다.
- check-and-set이 아닌 400도 있다. 버전이 맞는 `cas`로 `data` 없이 쓰면 400(`no data provided`), `data`가 객체가 아니면 400이다. `PutStored`는 언제나 `data`를 보내므로 이 400을 통합 테스트에서 일으킬 수는 없었고, 가짜 서버 테스트(`TestPutStored_Refused`)가 다룬다.
- 요청 본문 한도는 리스너 기본값 32MiB(33,554,432바이트)다. 본문 32,156,356바이트(값 23MiB)는 성공하고, 33,554,456바이트(값 24MiB)는 413이다. `config.hcl`의 리스너도 `max_request_size`를 정하지 않으므로 같은 기본값이다.
- 20MiB 값 하나의 HMAC 요청(본문 약 26.7MiB)은 성공한다. 빈 입력도 HMAC을 돌려준다.
- worker 역할(바뀐 정책)은 `projects/` 경로를 쓰고 읽을 수 있고, 지우기, 메타데이터 읽기와 지우기, destroy는 403이다. web 역할의 쓰기는 403이다. 테스트 서버에 같은 정책과 AppRole을 만들어 통합 테스트로 확인했다.

## 이유

- 경로를 숫자 ID로 만들면 프로젝트 이름(한글, 공백, `/`)이 경로에 들어가지 않는다. 임시 경로(`pending/<프로젝트 ID>/…`)와 같은 방식이다.
- 텍스트 값을 풀어 저장하면 파일 종류마다 풀기 규칙이 필요하고, 풀기가 틀리면 저장본과 소스의 값이 달라져 지문으로 확인할 수 없다. 글자 그대로 저장하면 저장된 바이트의 HMAC이 스캔의 지문과 같아야 한다는 한 가지 확인으로 충분하다.
- check-and-set이 없으면 두 실행이 겹치거나 사람이 그 사이에 값을 바꿨을 때 나중 쓰기가 앞의 값을 말없이 덮는다. 충돌을 오류로 받으면 실행기는 다시 읽고 확인할 수 있다.
- worker는 소스에서 그 값을 이미 읽으므로 `read`를 더해도 worker가 볼 수 있는 값은 늘지 않는다. 지우기와 메타데이터 권한이 없으면 worker가 잘못 동작해도 이전 버전은 남는다(100개 한도 안에서).
- 400을 모두 충돌로 보면, 다시 써도 성공할 수 없는 거절을 받은 실행기가 "다시 읽고 다시 쓴다"를 되풀이하거나 실패 사유를 잘못 적는다. 다시 읽어 버전을 보면 두 경우를 가를 수 있고, worker는 `read` 권한이 있다.
- 지문 요청의 한도: 요청 본문은 값의 약 4/3(base64)에 항목마다 몇십 바이트가 붙는다. 8MiB 묶음은 본문 약 11MiB로 32MiB 한도의 3분의 1이다. 스캔이 읽는 파일은 20MiB 이하(`scan.DefaultMaxFileBytes`)이고 그런 값 하나는 혼자 보내도 본문 약 26.7MiB라 한도 안이다. 묶음을 더 크게 해도 요청 수가 크게 줄지 않고, 서버와 worker가 한 번에 들고 있는 메모리만 커진다.
- 저장 크기의 한도: 처음에는 pebbledb에도 raft처럼 항목 한도(1MiB)가 있다고 보고 512KiB로 두었다. 실제 서비스에서 잰 결과(아래) 항목 한도는 없고 요청 본문의 한도 32MiB만 있었으므로, base64가 그 안에 여유 있게 드는 16MiB로 올렸다. 스캔이 읽는 파일은 20MiB 이하라 그보다 큰 키 파일은 어차피 항목이 되지 않고, 16MiB와 20MiB 사이의 키 파일은 `too-large`로 소스에 남는다.

## 실제 서비스에서 확인한 것

2026-11-20에 compose의 실제 `openbao` 서비스(OpenBao 2.7.2, pebbledb, colima)에서 worker AppRole로 확인했다.

- 고친 `config.hcl`로 빈 볼륨에서 self-init이 끝났다.
- 한 경로에 11번 쓴 뒤에도 버전 1을 읽을 수 있었다(`max_versions = 100`이 적용되었다).
- worker 역할로 `secret/data/projects/*`의 삭제, destroy, `secret/metadata/projects/*` 읽기, `secret/config` 읽기는 모두 403이었다.
- base64로 0.5, 0.7, 1, 2, 4, 16, 24, 30MiB인 값을 저장할 수 있었고, 16MiB 값은 읽어 보니 바이트가 같았다. 40MiB는 413이었다. 그래서 항목 크기의 한도(약 1MiB)는 없고, 한도는 요청 크기 32MiB다.

## 검토한 다른 방법

- 경로에 이미 다른 값이 있으면 거부하고 이름을 바꾸게 한다. 더 보수적이지만, 이름을 다시 쓰게 되는 경우(묶음이 지워진 뒤)가 드물고 이전 버전이 남으므로 택하지 않았다.
- 프로젝트에 경로용 키 열을 더한다. 등록 화면과 마이그레이션이 늘고, 사람이 읽기 좋다는 것 말고는 얻는 것이 없다.
- 값을 풀어(이스케이프를 해석해) 저장한다. 위의 이유로 택하지 않았다.
- 지문 요청을 건수로만 나눈다. 큰 키 파일 여러 개가 한 요청에 모이면 32MiB를 넘어 413이 되고, 그 실패가 스캔 전체를 실패시킨다.
