# 계획 5를 구현하면서 대신 정한 것

- 날짜: 2026-11-20
- 상태: 확정

## 배경

계획 5(`docs/superpowers/plans/2026-11-20-05-apply.md`)는 계획 4와 같은 방식으로, 하위 에이전트가 Task를 하나씩 구현하고 다른 에이전트가 검토하면서 진행했다. 사용자는 2026-11-20에 "확인받지 말고 권고안대로 정하고 문서로 남기라"고 했다. 그래서 계획 문서의 "검토 때 정해 주실 것" 32개도 사용자 검토 없이 권고안으로 확정했고, 구현하는 동안 계획이 답하지 않거나 계획의 가정이 틀린 것은 멈추지 않고 정했다. 이 문서는 그렇게 정한 것을 한곳에 모은다. 주제별 결정 기록(0032~0040)에 이미 적은 것은 그 번호를 붙였다. 틀렸다면 각 항목의 "틀렸을 때" 만큼만 고치면 된다.

## 결정

### 진행 방식

| 정한 것 | 이유 | 틀렸을 때 |
|---|---|---|
| 계획 문서의 "검토 때 정해 주실 것" 32개를 모두 권고안으로 확정했다 | 사용자의 지시. 사용자 검토 대신 별도의 검토 에이전트가 계획을 읽고 고쳤다 | 사용자가 계획과 결정 기록을 읽은 뒤 해당 항목을 다시 한다 |
| PR을 둘로 나눴다. PR 1(#11)은 화면 없는 적용 엔진, PR 2는 확인 재스캔과 화면이다. PR 1만으로는 적용을 시작할 방법이 없다 | 검토할 양을 나누고, 엔진을 화면보다 먼저 검토받으려고 | 없음 |
| 마이그레이션 `0007`을 병합 전에 두 번 고쳤다(`prev_after_hash` 열, `holds-customer-data` 사유) | 병합되지 않은 브랜치의 파일이었고 테스트 스키마에서만 실행되었다. "병합된 마이그레이션은 고치지 않는다"는 규칙은 병합부터 적용된다. 지금은 고정이다 | 없음 |
| 실제 확인(Task 15)을 위해 로컬 볼륨을 `down -v`로 지우고 새로 띄웠다 | 이 환경은 적용을 한 적이 없었고 예제의 가짜 값만 있었다 | 없음 |

### 값을 잃지 않기 위한 규칙

| 정한 것 | 이유 | 틀렸을 때 |
|---|---|---|
| 하드 링크가 둘 이상인 파일은 바꾸지 않고 사유를 붙여 건너뛴다(0037) | 이름 바꾸기로 덮어쓰면 다른 링크에 값이 남는데 성공으로 보고된다 | 그런 파일은 사람이 손으로 처리한다 |
| 키 파일을 지우기 직전에 다시 읽어, 저장한 내용과 해시가 같을 때만 지운다(0032) | 파일 삭제는 되돌릴 수 없는 유일한 변경이다. 크기와 수정 시각만으로는 부족하다 | 지우는 파일마다 읽기 한 번 |
| KV v2 마운트는 경로마다 버전을 100개 남긴다(0035) | 기본값 10이면 열한 번째 쓰기가, 추적되지 않는 파일에서 빼낸 값의 유일한 사본을 밀어낼 수 있다 | 경로당 저장 공간이 늘 뿐이다 |
| 값 하나의 한도를 512KiB 추정에서 16MiB로 올렸다(0035) | 재 보니 요청 한도가 32MiB였고 base64로 30MiB까지 저장되었다. 더 큰 값은 거부되고 소스에 그대로 남는다 | 거부일 뿐 값은 사라지지 않는다 |
| 저장된 기록의 인코딩이 `base64`가 아니면 읽기를 거부하고, 고객정보 종류는 `projects/` 아래에 쓰기를 거부한다(0035) | "고객정보는 어디에도 복사하지 않는다"의 두 번째 방어선 | 없음 |
| 파일 기록에 `prev_after_hash`를 두어, 이미 바꾼 파일을 다시 쓰다 멈추면 기록을 "바꿈" 상태로 되돌린다(0038) | 기록을 지우면 다음 점검이 그 파일을 "커밋되지 않은 변경"으로 본다 | 열 하나 |
| `EndFile`은 해시와 임시 파일 이름이 맞을 때만 기록을 닫는다(0038) | 임대를 잃은 worker가 다른 worker의 기록을 닫지 못하게 | 서명 하나 |
| manifest는 파일을 바꾼 뒤에 다시 읽어 합친다(0032) | manifest 자신이 적용 대상일 수 있다 | 읽기 한 번 |

### 무엇을 적용하는가

| 정한 것 | 이유 | 틀렸을 때 |
|---|---|---|
| 비밀 값의 범위가 고객정보 항목의 범위와 바이트를 공유하면 그 자리는 `holds-customer-data`로 건너뛴다(0039) | 값을 저장하면 고객정보가 OpenBao에 복사된다. 사용자가 고객정보 항목을 오탐으로 판정하면 풀린다 | 잘못 걸린 고객정보 규칙이 외부화를 막는다. 오탐 판정으로 푼다 |
| 아무것도 적용하지 못했고 모든 저장이 실패한 실행은 "성공, 적용 0"이 아니라 실패로 닫는다(0032) | 성공으로 보이면 오해한다. 일부만 성공한 실행은 성공이고 건수로 보인다 | 상태 하나 |
| 적용된 외부화 묶음에서 항목을 옮길 수 있는 경우를 좁혔다. 마지막 스캔이 그 항목을 여전히 찾았고, 묶음의 마지막 항목이 아니고, 그 항목에 적용했거나 쓰던 기록이 없을 때만 옮긴다(0036) | 처음에는 모두 금지했는데, 적용 뒤에 같은 값이 새 자리에 나타나면 그 항목을 처리할 방법이 없었다 | 옮긴 항목은 다음 적용에서 자기 이름을 받는다 |
| 점검한 스캔보다 새 스캔이 어떤 상태로든 있으면 적용 확인을 거부한다(0036) | worker가 어차피 거부하는데 그때의 사유는 알아보기 어렵다 | 점검을 한 번 더 요청한다 |
| 점검 요청은 화면이 버튼을 내놓지 않는 조건(스캔이나 적용이 진행 중, 새 스캔이 있음, 적용할 것이 없음)이면 서버도 409로 거부한다 | 직접 보낸 요청이 준비된 점검을 무효로 만들었다 | 없음 |
| "복구 불가" 동의는 점검이 그런 파일을 보여 준 경우에만 받아들인다 | 보여 주지 않은 것에 대한 동의가 감사 로그에 "동의함"으로 남았다 | 없음 |

### 스캔과 확인

| 정한 것 | 이유 | 틀렸을 때 |
|---|---|---|
| 스캔은 값 전체가 `${...}` 하나인 결과와, 구성 요소가 모두 placeholder인 접속 URL을 항목으로 만들지 않는다(0026) | 실제 확인에서 적용 뒤의 확인 스캔이 도구가 써넣은 placeholder 15개를 새 미판정 항목으로 보고했다. 그것을 외부화하면 placeholder 글자가 비밀 값으로 저장된다 | 글자 그대로 `${...}` 모양인 실제 비밀 값은 보고되지 않는다 |
| "다시 발견" 건수는 그 스캔이 요청되기 전에 적용된 묶음만 센다(0040) | 지난 확인 스캔의 화면이, 그 뒤에 적용한 묶음을 두고 "다시 발견"이라고 했다 | 없음 |
| 실패한 실행도 쓰던 파일이 있으면 확인 스캔을 요청한다(0040) | 파일이 바뀌었을 수 있다. 스캔 한 번이 더 도는 것은 해가 없다 | 스캔 한 번 |
| 결과 화면과 "적용됨" 탭은 기록이 보여 주는 것만 말한다. 쓰다 멈춘 파일은 "바뀌었을 수 있음"으로, 적용 뒤 스캔이 없으면 "확인 전"으로 보인다 | 화면이 사실과 다른 말을 하던 세 곳을 검토에서 찾았다 | 문장 몇 개 |

### 환경

| 정한 것 | 이유 | 틀렸을 때 |
|---|---|---|
| git은 `protocol.allow=never`에 더해 `GIT_NO_LAZY_FETCH=1`, `GIT_ALLOW_PROTOCOL=none`으로 실행한다(0033) | 계획이 가정한 설정만으로는 부분 복제 저장소가 원격에 접속하는 것을 막지 못했다 | 없음 |
| OpenBao self-init에서 KV 마운트를 맨 처음, 버전 수 설정을 맨 끝에 보낸다 | 실제 확인에서 빈 볼륨으로 띄우다 한 번 실패했다. 새 KV v2 마운트는 저장소를 올리는 동안 요청을 거부하고, 요청 하나가 거부되면 초기화가 중단된다. self-init에는 다시 시도하는 방법이 없다. 빈 볼륨에서 일곱 번 다시 띄워 확인했다 | 그래도 겹치면 빈 볼륨에서 기동이 실패하고 로그에 보인다. 잃을 값이 없는 시점이다(`docs/local-run.md`) |
| 예제 작업본은 `core.autocrlf=false`로 커밋한다 | 호스트의 git이 CRLF를 LF로 커밋하면 컨테이너의 git은 그 파일을 "커밋되지 않은 변경"으로 본다 | 문서의 명령 한 줄 |

### 고치지 않고 넘긴 것

`docs/next-steps.md`의 "계획 5에서 남은 일"에 적었다.

## 이유

멈춰서 묻는 것보다 정하고 기록하는 편이 빠르고, 위의 결정은 대부분 고치는 데 드는 일이 작다. 값을 잃을 수 있는 쪽과 거부하는 쪽이 갈릴 때는 언제나 거부하는 쪽을 골랐다. 거부는 사람이 다시 요청하면 되지만 사라진 값은 되찾을 수 없다.

## 검토한 다른 방법

- **항목마다 사용자에게 묻는다**: 사용자가 하지 말라고 했다.
- **주제별 결정 기록에만 적는다**: 무엇이 사용자 대신 정해졌는지 한눈에 볼 수 없다.
