# 화면은 아는 만큼만 말하고, htmx 요청의 실패도 화면에 보인다

- 날짜: 2026-11-24
- 상태: 확정

## 배경

`next-steps.md`에 화면의 작은 불일치 넷이 남아 있었다.

1. 적용 화면은 점검 전에 데이터베이스만 보고 "적용할 판정이 있음: 통과"를 보인다. 남은 외부화 묶음이 worker가 언제나 건너뛰는 것뿐이면 점검 뒤에는 같은 이름의 조건이 실패했다(0049, 0051의 알려진 한계).
2. 원본이 없는 묶음의 상세는 미판정일 때만 "보관된 원본이 없습니다"를 보였다. 오탐, 보류, 외부화, 삭제·마스킹으로 판정한 묶음은 원본 보기도 안내도 없었다.
3. htmx로 보낸 요청이 실패하면 화면에 아무 변화가 없었다. htmx는 4xx, 5xx 응답을 바꿔 넣지 않는다. 세션이 끝난 뒤의 GET은 `/login`으로 가는 303을 htmx가 자기 요청 안에서 따라가다가 Keycloak(다른 출처)에서 막혔다. 목록 줄을 누를 때(`hx-get`)와 원본 보기(`hx-post`)가 모두 그랬다.
4. 판정 화면의 목록 줄이 shell 묶음의 이름을 `ext.…`로 보인다는 항목. 확인해 보니 `entryName`이 이미 `Entry.Shell`을 보고 `EXT_…`로 보이고 `TestTriage_ShellName`이 붙잡고 있었다. 고칠 것이 없어 항목만 닫았다.

## 결정

1. **점검한 뒤의 조건은 이름을 "적용할 수 있는 항목이 있음"으로 한다.** 점검 전의 조건은 "적용할 판정이 있음" 그대로다. 앞의 것은 데이터베이스가 아는 사실(판정이 있다)이고 뒤의 것은 worker가 파일을 읽고 안 사실(바꿀 자리가 있다)이다. 실패했을 때의 문장("적용할 수 있는 항목이 없습니다. … 판정한 항목이 있다면 모두 적용이 건너뛰는 항목입니다.")은 그대로다.
2. **admin이 보는 상세에서, 원본이 없고 적용되지 않은 묶음은 언제나 이유를 보인다.**
   - 오탐: "오탐으로 판정한 값은 원본을 보관하지 않습니다. 판정을 바꾸고 다시 스캔하면 보관됩니다."
   - 그 밖의 판정과 미판정: "보관된 원본이 없습니다. 다시 스캔하면 보관됩니다."
   - 적용된 묶음: 아무것도 보이지 않는다. 상세가 이미 저장 경로를 보인다.
3. **htmx가 오류 상태(4xx, 5xx)의 응답을 `body`에 바꿔 넣게 한다.** `htmx-config`의 `responseHandling`으로 정한다. 서버는 htmx 요청에도 전과 같은 오류 화면을 보내므로 사용자는 일반 요청이 실패했을 때와 같은 화면을 본다.
4. **세션 없이 온 htmx GET에는 303 대신 401과 `HX-Redirect: /login?return_to=…`를 보낸다.** 브라우저가 화면을 떠나 로그인으로 가고, 로그인한 뒤 누르려던 주소로 돌아온다. 세션 없이 온 POST는 전과 같이 401 오류 화면이고, 결정 3 때문에 htmx 요청에서도 "다시 로그인" 링크와 함께 보인다.

## 이유

- 같은 이름의 조건이 통과였다가 실패로 바뀌면 사용자는 그 사이에 무엇이 달라졌는지 찾게 된다. 달라진 것은 없고 아는 것이 늘었을 뿐이므로 이름을 나눈다. 점검 전에 건너뛰는 사유를 알려면 파일을 읽어야 하고, 그것이 점검이 하는 일이다(0049).
- 오탐의 원본을 보관하지 않는 것은 의도한 동작이다(0040, 0054). "다시 스캔하면 보관됩니다"는 오탐에는 틀린 말이라 문장을 따로 둔다. 계획 5의 확인 표 16이 기대한 것도 안내가 보이는 쪽이었다.
- 오탐에서 다른 판정으로 바꾼 묶음은 다음 스캔까지 원본이 없다. 원본 보기 단추가 왜 없는지 알리는 것이 미판정일 때와 똑같이 필요하다.
- htmx는 `HX-Redirect`를 응답 상태보다 먼저 처리하고, `responseHandling`의 `target`과 `swapOverride`로 오류 응답이 들어갈 자리를 따로 정할 수 있다. 스크립트를 더하지 않고 설정과 헤더만으로 된다. CSP(`default-src 'self'`)도 그대로다.
- 오류 화면은 `layout`으로 그린 문서 전체다. `body`에 넣으면 메뉴와 오류 문장이 그대로 보이고 제목도 바뀐다.

## 검토한 다른 방법

- **점검 전의 조건을 "통과"가 아닌 다른 상태로 보인다(예: "점검 필요").** 판정이 하나도 없을 때 이 조건이 점검 단추를 막는 역할은 남아야 하므로 상태가 셋이 되고, 다른 조건과 읽는 법이 달라진다.
- **원본 보기 양식에서 `hx-post`를 뺀다.** 일반 POST는 실패하면 오류 화면이 나온다. 그러나 목록 줄의 `hx-get`에는 같은 문제가 남는다.
- **`htmx:responseError`를 듣는 스크립트를 둔다.** 정적 파일 하나와 브라우저 테스트가 더 필요하다. 설정으로 되는 일이다.
- **원본 보기의 실패를 200과 안내 문장으로 자리에 그린다.** 권한(403)과 CSRF(403) 실패는 handler 앞의 미들웨어에서 나므로 그 길을 따로 만들어야 한다.

## 확인한 것

- 서버 쪽은 테스트로 붙잡았다: `TestApplyPage_NothingToApplyCondition`, `TestTriage_NoOriginalNotice`, `TestRequireLogin_HtmxRequest`, `TestLayout_HtmxShowsErrorResponses`.
- htmx의 동작은 이 저장소의 `htmx.min.js`(2.0.11)와 같은 `htmx-config`, 같은 CSP를 쓰는 임시 서버를 Chromium으로 열어 확인했다: 500을 받은 `hx-get`과 `hx-post`가 오류 화면으로 바뀌고 제목이 바뀌며, 401과 `HX-Redirect`를 받은 `hx-get`은 `/login?return_to=…`로 옮겨 간다.

## 알려진 한계

- 실제 스택(새 web 이미지)에서는 확인하지 않았다. 2GB Docker VM에서 이미지를 다시 빌드하는 비용 때문이다. 다음에 web 이미지를 빌드할 때 판정 화면에서 세션을 지우고 목록 줄을 눌러 로그인으로 가는지 본다.
- `hx-post`가 오류 화면으로 바뀐 뒤에도 주소 표시줄은 판정 화면의 주소다. 새로 고치면 판정 화면으로 돌아간다.
- 점검 전 화면의 "적용할 판정이 있음: 통과"는 그대로다. 점검을 해야 "적용할 수 있는 항목"을 안다.
- htmx를 올릴 때(`next-steps.md`의 4.x 항목) `responseHandling`의 `target`, `swapOverride`와 `HX-Redirect`의 처리 순서를 다시 확인한다.
