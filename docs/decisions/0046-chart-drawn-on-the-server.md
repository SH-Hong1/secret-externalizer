# 대시보드의 추이 차트를 서버가 SVG로 그린다

- 날짜: 2026-11-23
- 상태: 확정

## 배경

대시보드(계획 7)는 스캔별로 분류를 쌓은 "남은 항목 추이" 차트 하나를 그린다. 막대는 30개(`dashboard.MaxPoints`) 이하이고 분류는 다섯 개다. 설계 5절의 [제안]은 "차트용 라이브러리 하나를 정적 파일로 포함"이고, 11절은 선택을 만드는 사람에게 맡긴다. 화면 시안(`docs/design/README.md`)에는 판정의 색만 있고 분류의 색이 없다.

계획 7 Task 4의 첫 단계에서 다음을 확인했다.

- `html/template`은 HTML 안의 인라인 `<svg>`를 보통의 HTML 요소처럼 다룬다. `<rect>`의 숫자 속성은 그대로 나오고, `class` 속성의 값은 속성 문맥으로 이스케이프된다(`x" onload="y`가 `x&#34; onload=&#34;y`가 된다). `<title>`은 RCDATA로 다뤄져 `<script>`가 `&lt;script&gt;`로, `<text>`의 글자도 `&lt;b&gt;`로 나온다. 브라우저는 SVG 안의 `<title>`을 SVG 제목으로 읽고 엔티티를 풀어 보인다.
- 실제 템플릿으로 그린 화면을 `default-src 'self'; base-uri 'none'; frame-ancestors 'none'` 머리말과 함께 Chromium(playwright)에 열었을 때, 조각의 `fill`이 `app.css`의 클래스에서 그려졌고(`rgb(0, 135, 106)`) CSP 위반이 없었다. 막대의 `<title>`은 이스케이프된 프로젝트 이름을 원래 글자로 보였다. 390px 너비에서도 쪽이 가로로 넘치지 않았다. 다만 차트가 viewBox대로 줄면 390px에서 글자가 약 3.6px이 되어, 차트에 최소 너비 780px(`.chart`의 `min-width`)를 두고 그보다 좁으면 `.chart-scroll` 안에서 가로로 스크롤하게 했다. 글자는 13px(viewBox 단위)이라 780px에서 약 10.5px, 1280px(차트 너비 약 1024px)에서 약 13.9px이다. 같은 숫자는 "표로 보기"에서도 읽는다.

## 결정

1. 차트 라이브러리를 넣지 않는다. `internal/web/chart.go`의 `newBarChart`가 viewBox(960×300) 좌표로 막대와 조각, 눈금을 계산하고, `templates/dashboard.html`이 `<rect>`, `<line>`, `<text>`, `<title>`로 그린다. 스크립트를 더하지 않고 CSP를 바꾸지 않는다. 막대마다 안쪽 `<svg>`(x, 폭)를 두어 템플릿이 계산 없이 막대 이름을 가운데(`x="50%"`)에 놓는다.
2. 조각의 자리는 쌓인 합을 반올림해 정하므로 조각 높이의 합이 막대 높이와 같고, 조각이 겹치거나 틈이 생기지 않는다. 세로 눈금의 최댓값은 가장 큰 합 이상의 가장 작은 "1, 2, 5 × 10ⁿ"이고, 눈금은 여섯 개 이하가 되는 가장 작은 "1, 2, 5 × 10ⁿ" 간격이다.
3. 분류의 색 다섯 개를 새로 정해 `docs/design/README.md`의 "분류의 색"에 적고 `app.css`의 토큰(`--color-category-*`)과 `chart-<분류>` 클래스로 준다.

   | 분류 | 색 |
   |---|---|
   | 저장소 접속 정보 | `#00876A` |
   | SSH 접속 정보 | `#D0560F` |
   | 제휴사 세션 정보 | `#3E6ED2` |
   | 기타 비밀 값 | `#B33B86` |
   | 고객정보 | `#7A7A00` |

   dataviz 스킬의 검증 스크립트(`validate_palette.js --mode light --surface #ffffff`)를 `categoryOrder` 순서로 돌려 모든 검사를 통과했다: 명도 범위, 채도 하한, 이웃한 색의 색각 이상 구분(가장 낮은 것 ΔE 10.1, 기준 8), 정상 시각 구분(가장 낮은 것 ΔE 22.3, 기준 15), 흰 면 대비 3:1 이상. 쌓은 막대에서는 이웃한 조각끼리만 맞닿으므로 이웃한 쌍의 검사가 해당한다(모든 쌍 검사는 통과하지 않는다).
4. 색만으로 분류를 구분하지 않는다. 범례에 분류 이름을 적고, 조각 사이에 면 색의 1px 테두리로 틈을 두며, 막대의 `<title>`에 분류마다의 수를 적고, 차트 아래 "표로 보기"에 같은 숫자의 표를 둔다.

## 이유

- 그릴 것이 막대를 쌓은 차트 하나뿐이다. Go가 좌표를 계산하면 숫자와 그림이 같은지를 Go 테스트(`TestNewBarChart_*`, `TestHandleDashboard_OK`의 `<rect>` 수)로 붙잡을 수 있다.
- 스크립트가 없으므로 CSP(`default-src 'self'`)가 그대로이고, 자료를 스크립트에 넘길 길(JSON 주소나 `data-` 속성)이 필요 없다.
- 고정할 버전과 체크섬이 늘지 않는다(`AGENTS.md`: 표준 라이브러리로 할 수 있으면 의존성을 더하지 않는다).
- 색은 판정의 색(외부화 `#1F4FD8`, 삭제·마스킹 `#6B2FB8`, 보류 `#8A4300`)과 값이 다르다. 분류의 색은 차트와 범례에만 쓰고 판정의 색은 표시와 타일에만 쓰므로 둘이 한 자리에 함께 나오지 않는다. 그래도 파랑(제휴사 세션)과 주황(SSH)은 외부화와 보류에 가까운 색상이라, 분류를 언제나 글자와 함께 보인다.

## 검토한 다른 방법

- **Chart.js나 uPlot을 정적 파일로 넣는다.** 확대, 범례로 계열 끄기 같은 상호작용을 얻지만, 자료를 스크립트에 넘길 길과 스크립트 파일 하나가 늘고, 그림이 숫자와 같은지를 테스트할 수 없다. 막대 30개와 분류 다섯 개에는 상호작용이 필요하지 않다.
- **막대 이름의 가운데 좌표를 `chartBar`의 필드로 둔다.** 템플릿은 더 단순해지지만 계획이 정한 타입에 필드가 늘고, 안쪽 `<svg>`로 같은 결과를 얻는다.
- **분류의 색으로 판정의 색을 다시 쓴다.** 차트의 분류와 화면의 판정이 같은 색으로 보여 뜻이 섞인다.
