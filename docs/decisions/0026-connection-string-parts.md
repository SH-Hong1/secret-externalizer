# 접속 정보를 구성 요소로 나눠 저장한다

- 날짜: 2026-11-19
- 상태: 확정

## 배경

계획 4의 판정 화면은 구성 요소(호스트, 포트, 계정, 비밀번호)마다 판정과 자리 표시자 이름을 따로 준다. 지금까지는 JDBC URL 하나가 종류 `url`인 항목 하나로 저장되어, `jdbc:mysql://shop_app:비밀번호@db:3306/shop` 같은 URL에서 비밀번호만 외부로 빼거나 호스트만 환경 변수로 바꿀 수 없었다.

구현 전에 규칙 파일과 실제 실행 파일(betterleaks 1.10.1, opengrep 2.0.0, darwin/arm64)로 확인한 사실:

- `rules/opengrep/shell.yml`은 `user@host`를 값 하나로 보고하지 않는다. 같은 정규식으로 규칙 두 개(`shell-ssh-user`, `shell-ssh-host`)가 계정(`account`)과 호스트(`host`)를 각각 보고한다. `scp app.war deploy@host.invalid:/srv/app`에서도 `deploy`와 `host.invalid`만 보고했다. 따라서 ssh 대상을 나타내는 종류는 없고, 나누는 대상은 종류가 `url`인 결과뿐이다.
- 종류가 `url`인 규칙은 모두 opengrep 규칙(`spring-xml-datasource-url`, `properties-jdbc-url`, `yaml-jdbc-url`)이고, 범위는 `jdbc:`부터 URL 끝까지 전체다. `    url: jdbc:mysql://…/shop` 줄에서 시작은 `j`, 끝은 `shop` 다음이었다.
- betterleaks의 기본 규칙 `generic-credential-uri`는 `계정:비밀번호@` 형태의 URL 안의 비밀번호를 따로 보고하고(`other-secret`, `other`), `generic-password`는 `?password=…` 매개변수의 값을 보고한다. 나눈 비밀번호와 파일, 시작 위치, 값이 같으므로 지문이 같아 한 위치로 합쳐지고, 분류 규칙(0021)에 따라 `storage-credential`의 `password`가 되며 검출은 둘 다 남는다. 실제 스캐너로 확인하는 테스트는 `TestHandle_RealScannersSplitURL`이고, 규칙 예제(`legacy-shop`의 `application-prod.yml` 21번 줄)에도 이 경우를 더했다.

## 결정

- `internal/connstr.Split`이 값을 구성 요소로 나눈다. 아는 형식은 셋이다.
  - `jdbc:oracle:thin:`(또는 `oci:`) 뒤에 선택적인 `계정/비밀번호`, `@`, 그리고 `호스트:포트:SID`, `호스트:포트/서비스`, `//호스트:포트/서비스`. TNS 기술자(`@(DESCRIPTION=…)`)는 계정과 비밀번호만 나누고 호스트는 나누지 않는다.
  - 그 밖의 `jdbc:<하위 프로토콜>://[계정[:비밀번호]@]호스트[:포트][,호스트[:포트]…]`와 뒤의 `?`(구분자 `&`) 또는 `;`(구분자 `;`) 매개변수. `user`, `username`의 값은 계정이고, 이름에 `password`, `pwd`, `secret`, `token`이 든 매개변수(대소문자 무시. `sslpassword`, `trustCertificateKeyStorePassword`, `accessToken`, `keyStoreSecret` 등)의 값은 비밀번호다. 나뉜 URL은 구성 요소만 가리므로, 이런 매개변수를 비밀번호로 나누지 않으면 그 값이 주변 줄에 그대로 보인다. 이름만 보고 정하므로 `passwordCharacterEncoding` 같은 설정 값도 비밀번호 항목이 된다. 인증 영역(`//` 뒤에서 첫 `/`, `?`, `;`, `#`까지) 뒤에 `@`가 있으면 나누지 않고 URL 항목 하나로 남긴다. 사용자 정보의 비밀번호에 인코딩하지 않은 `/`, `?`, `#`가 들어 있어 경계를 알 수 없는 경우이고(`u:12#ab@db`), 매개변수 값에 `@`가 든 URL도 같이 통째로 남는다. SQL Server의 중괄호 값(`password={a;b}`)은 괄호 안을 값으로 본다. 대괄호 IPv6 주소는 괄호를 빼고, SQL Server 인스턴스 이름(`호스트\인스턴스`)은 호스트에 넣지 않는다.
  - `계정@호스트`, `계정@호스트:포트`, `계정@호스트:경로`(ssh, scp 대상). 러너는 지금 이 형식의 값을 넘기지 않지만, 같은 함수가 다루도록 둔다.
- `${`로 시작하는 구성 요소는 결과에서 뺀다. 모든 구성 요소가 자리 표시자이거나 형식을 모르면(`jdbc:h2:mem:test`) `nil`을 돌려주고, 호스트나 포트가 형식에 맞지 않거나 UTF-8이 아닌 값도 `nil`이다.
- 러너는 값의 자리를 정한 뒤(`locate`), 지문을 만들기 전에 종류가 `url`이고 파일 전체 결과가 아닌 결과를 나눈다. 나뉘면 원래 결과를 구성 요소마다 하나씩의 결과로 바꾼다. 도구, 규칙, 분류는 원래 결과의 것이고, 종류와 범위만 구성 요소의 것이다. 나뉘지 않으면 그대로 둔다.
- 나뉜 URL은 URL 항목을 남기지 않는다.
- DB 이름, 경로, 그 밖의 매개변수(`useSSL=false` 등)는 구성 요소가 아니다. 항목이 되지 않고 주변 줄에서도 가리지 않는다. 주변 줄은 `url: jdbc:mysql://****:****@****:****/shop`처럼 보인다.
- 종류 `port`를 더한다. 마이그레이션 `0004_port_kind.sql`이 `finding.kind`의 CHECK 제약을 `port`를 더한 것으로 바꾼다. 미리보기는 다른 비밀 값 종류와 같아서, 8글자보다 짧은 포트는 `****`다.

## 이유

- 통째 항목을 남기지 않는 이유: 같은 값이 URL 항목과 구성 요소 항목에 함께 들어 있으면 판정이 두 곳에서 갈릴 수 있다. 비밀번호는 외부로 빼기로 했는데 URL 항목은 "그대로 둠"이 되면 적용 단계에서 같은 줄을 서로 다르게 고치게 된다. 또 URL 항목의 원본이 OpenBao에 보관되면, 구성 요소를 판정한 뒤에도 비밀번호가 든 URL 원본이 따로 남는다.
- DB 이름을 빼는 이유: DB 이름과 경로는 접속에 쓰이지만 그것만으로 접근 권한을 주지 않는 설정 값이다. 비밀 값으로 다루면 판정할 항목이 늘고, 주변 줄에서 가리면 어느 DB를 가리키는 설정인지 화면에서 알 수 없게 된다.
- 지문을 만들기 전에 나누는 이유: 지문과 원본 보관, 합치기(파일, 시작 위치, 지문)가 모두 구성 요소 값을 기준으로 이루어져야 betterleaks가 따로 보고한 비밀번호와 한 위치로 합쳐진다.
- 짧은 값의 가리기: 4바이트보다 짧은 구성 요소(포트 `22`, 계정 `sa`)도 그 파일의 주변 줄에서는 자기 자리에서 가린다(그 파일에 자리를 정한 모든 값의 범위를 가리는 규칙, 0021). 다만 다른 자리에 나오는 같은 값은 0021의 규칙대로 가리지 않는다. 전에는 URL 전체가 4바이트 이상이라 다른 파일에서 같은 URL이 나오면 통째로 가려졌지만, 이제는 4바이트 이상인 구성 요소만 가려진다. 규칙이 보고하지 않은 자리에 같은 URL이 있으면 짧은 포트나 계정은 보일 수 있다.

## 검토한 다른 방법

- URL 항목을 남기고 구성 요소 항목을 더하기: 위의 판정 충돌과 원본 중복 때문에 택하지 않았다.
- 규칙(opengrep 정규식)에서 구성 요소마다 규칙을 따로 쓰기: URL 규칙 세 개(XML, properties, YAML)마다 형식별 규칙을 여러 개 더해야 하고, 같은 형식 해석이 여러 파일에 흩어진다. Go 한 곳에서 나누면 표 형태의 단위 테스트와 퍼징으로 확인할 수 있다.
- `net/url`로 파싱하기: `jdbc:oracle:thin:@호스트:포트:SID`나 SQL Server의 `;` 매개변수는 URL 문법이 아니고, 파싱 결과에서 원문의 바이트 위치를 되찾을 수 없어 쓰지 않았다.
