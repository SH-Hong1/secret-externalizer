# 세션은 해시한 키로 저장하고 토큰을 담지 않는다

- 날짜: 2026-11-18
- 상태: 확정

## 배경

로그인 후 브라우저는 세션 ID만 쿠키로 들고 있고, 서버는 valkey에서 세션을 찾는다. valkey 내용이 새거나 운영자가 덤프를 보더라도 사용 중인 세션을 가로챌 수 없어야 하고, 세션이 영원히 살아 있어서도 안 된다.

## 결정

- valkey 키는 ID 원문이 아니라 SHA-256 값이다: `session:<hex>`, `attempt:<hex>`. ID는 `crypto/rand`의 32바이트를 base64url로 적은 값이다.
- 세션 값에는 `subject`, `name`, `roles`, `expires_at`만 담는다. 액세스 토큰, 리프레시 토큰, ID 토큰은 담지 않는다.
- 수명은 셋이다.
  - 유휴 30분(`IdleTimeout`): 읽을 때마다 남은 수명을 다시 건다.
  - 절대 8시간(`AbsoluteTimeout`): 로그인 시각에서 8시간이 지나면 읽어도 연장되지 않고 `Get`이 지운다. 남은 수명은 `min(유휴, 절대 만료까지 남은 시간)`이다.
  - 로그인 시도 10분(`AttemptTimeout`): 인가 요청에서 콜백까지의 시간이다. 읽으면서 지운다(`GETDEL`)라서 같은 콜백을 두 번 쓸 수 없다.
- 세션 ID 타입은 `fmt`, `slog`, `encoding/json`으로 출력하면 `[redacted]`를 낸다. 다른 값의 공개 필드로 들어 있을 때도 같다.
- valkey는 디스크에 저장하지 않는다(compose의 `--save "" --appendonly no`). valkey를 다시 띄우면 모두 다시 로그인한다.
- web의 valkey 클라이언트는 실패한 읽기를 두 번만 다시 시도하고(100ms, 200ms 뒤), 연결 시도는 2초에서 끊는다. 요청의 context에는 마감 시각이 없어서, 기본 설정이면 valkey-go가 valkey가 돌아올 때까지 읽기를 계속 다시 시도해 화면이 멈춘다. 세션 저장소가 없으면 기다리기보다 503 화면을 바로 보여주는 편이 낫다.
- 이 설계에서 다음 결과를 받아들인다.
  - 역할은 로그인할 때 찍어 둔 값이다. Keycloak에서 역할을 빼거나 사용자를 비활성화해도 그 사용자의 세션이 끝날 때까지(최대 8시간) 권한이 남는다.
  - 키가 세션 ID의 해시라서 사용자 단위로 세션을 찾아 끊을 수 없다. 한 사용자의 세션을 모두 끊으려면 valkey를 비우는 수밖에 없다.
  - 계획 2에서 web은 valkey에 인증하지 않는다(비밀번호도 TLS도 없다). compose 네트워크 안에서만 쓰는 로컬 개발 환경이라서 받아들이며, 공유하는 환경에 올리기 전에 고친다(`docs/next-steps.md`).

## 이유

- 키가 ID의 해시이므로 valkey를 읽을 수 있는 사람도 해시에서 쿠키 값을 만들 수 없다. ID가 256비트 난수라서 salt나 느린 해시가 필요 없다.
- 이 앱은 로그인 후 identity provider를 다시 호출하지 않으므로 토큰을 갖고 있을 이유가 없다. 저장하지 않으면 valkey가 새어도 토큰이 새지 않는다(`AGENTS.md`의 "비밀 값은 세션에 남기지 않는다" 규칙).
- 유휴 시간제한은 방치된 브라우저를, 절대 시간제한은 계속 쓰이는 탈취된 쿠키를 끊는다. 둘 중 하나만으로는 나머지를 막지 못한다.
- 로그인 시도를 한 번만 쓰게 하면 state와 PKCE verifier의 재사용을 막는다.

## 검토한 다른 방법

- 서명된 쿠키(JWT 등)에 세션 내용을 담기: 서버에서 세션을 끊을 수 없다(로그아웃, 권한 회수).
- 키에 ID 원문을 쓰기: 구현은 단순하지만 valkey 내용이 곧 사용 가능한 쿠키 목록이 된다.
- 유휴 시간제한만 두기: 활동이 계속되면 세션이 끝나지 않는다.
