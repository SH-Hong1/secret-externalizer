# 원본 보기는 값이 화면에 나오는 유일한 자리이고, 주변 줄은 저장된 그대로 보인다

- 날짜: 2026-11-20
- 상태: 확정

## 배경

`AGENTS.md`의 Security 절은 비밀 값이 로그, 오류 메시지, 템플릿, 데이터베이스 열, 리포트, manifest, 세션 어디에도 나오지 않는다고 정한다. 화면에는 지문과 `finding.Preview`의 미리보기만 둘 수 있다(`0023`).

그런데 판정하는 사람은 가끔 미리보기(`Sh0p****`)만으로는 값을 알아보지 못한다. 같은 이름의 비밀번호가 운영용인지 개발용인지, 토큰이 아직 쓰이는 것인지는 값을 봐야 알 수 있다. 원본은 스캔이 OpenBao KV v2의 `secret/data/pending/<프로젝트 ID>/<지문>`에 보관해 두었고(`0003`, `0017`), web AppRole의 정책은 처음부터 이 경로의 읽기를 허용했다. 계획 4의 검토 항목 13이 이 열람을 어떻게 허용할지 물었다.

같은 검토의 항목 12는 판정 화면의 주변 줄을 물었다. 스캔은 그 스캔이 어디에서든 찾은 값을 주변 줄에서 가리고, 로그와 샘플 데이터 파일과 고객정보가 나온 파일에는 주변 줄을 만들지 않는다(`0021`, `0024`). 그래도 어떤 규칙도 보고하지 않은 텍스트(규칙이 잡지 못한 형태의 비밀번호, 주석 속 이름이나 연락처)는 소스 파일의 주변 줄에 남을 수 있다. 판정 화면은 이 주변 줄을 `user`에게도 보인다.

## 결정

### 원본 보기 (검토 항목 13)

값이 화면에 나오는 곳을 하나만 둔다. `admin`이 판정 화면에서 비밀 값 묶음의 "원본 보기"를 누른 요청의 응답이다.

- `admin`만 쓸 수 있다. 버튼도 `admin`에게만, 마지막 성공 스캔이 원본을 보관한 구성원이 있는 비밀 값 묶음에만 보인다. 고객정보 묶음, 원본이 없는 묶음, 마지막 스캔에 없는 묶음은 404다.
- `POST /projects/{id}/bundles/{bundle}/original`이다. 상태를 바꾸는 요청(감사 기록)이므로 `POST`이고 교차 출처 보호를 받는다. 값이 주소, 쿼리, 리다이렉트에 들어가지 않는다.
- 감사 기록을 먼저 남기고 그다음 OpenBao에서 읽는다. 기록이 실패하면 읽지 않고 500이다. OpenBao에 원본이 없거나 닿지 않아도 열람 시도는 기록에 남는다. 기록에는 동작(`reveal`), 사용자, 프로젝트, 묶음만 있고 값은 없다.
- 값은 그 요청을 처리하는 handler와 그 응답을 그리는 버퍼에만 있다. 세션, 데이터베이스, 로그, 오류에 남기지 않는다. `bao.Value`는 `fmt`의 모든 형식, `slog`, `encoding/json`에서 `[redacted]`로 나오고, `Reveal`로만 바이트를 꺼낸다. 응답은 `Cache-Control: no-store`다(모든 응답에 붙는다).
- UTF-8이 아니거나 NUL이 든 값은 내용 대신 "텍스트가 아닌 원본입니다. N바이트."만 보인다.
- "닫기"는 같은 상세를 값 없이 다시 여는 링크다.
- htmx 없이 받은 원본 보기 응답을 브라우저에서 새로 고치면(다시 보내기 확인을 거쳐) 같은 요청이 다시 가서 감사 기록이 하나 더 남고 원본을 다시 읽는다. 의도한 동작이다. 값을 다시 읽는 일은 언제나 기록을 거친다.
- OpenBao에 닿지 않으면(연결 실패, 시간 초과) "비밀 저장소에 연결할 수 없습니다.", OpenBao가 답했지만 읽기를 거부했거나 저장된 값을 쓸 수 없으면 "비밀 저장소에서 원본을 읽지 못했습니다."를 보인다. 둘 다 정해진 문구이고 오류 내용은 로그에만 남는다.
- `AGENTS.md` Security 절 첫 항목에 이 예외를 한 문장으로 적는다.

### 주변 줄 (검토 항목 12)

주변 줄은 저장된 그대로 `user`에게도 보인다. 규칙이 잡지 못한 텍스트가 소스 파일의 주변 줄에 남을 수 있다는 위험을 받아들인다. 로그, 샘플 데이터 파일, 고객정보가 나온 파일에는 지금처럼 주변 줄이 없다. `0021`의 "남은 일" 첫 항목은 이것으로 정리한다.

## 이유

- 판정을 맞게 하려면 값을 봐야 할 때가 있다. 그때 OpenBao에 직접 들어가게 하면 누가 언제 무엇을 봤는지가 이 도구의 감사 기록에 남지 않고, 사람마다 OpenBao 권한을 따로 줘야 한다.
- 기록을 먼저 남기면 "기록 없이 값이 나간" 경우가 생기지 않는다. 반대로 기록은 있는데 값을 못 본 경우(OpenBao 장애)는 해가 없다.
- `admin`으로 좁히면 값을 볼 수 있는 사람이 Keycloak의 역할 하나로 정해진다. 판정은 `user`도 하지만 대부분은 미리보기와 주변 줄로 충분하다.
- 바이너리 값(키 저장소 등)은 화면에 그려도 읽을 수 없고, 제어 문자가 화면을 깨뜨릴 수 있다. 크기만으로 "무엇이 보관되어 있다"는 것은 확인된다.
- 주변 줄은 값이 쓰이는 문맥(어느 설정 키인지, 어느 bean의 속성인지)을 보여 줘 판정의 근거가 된다. 주변 줄 없이 탐지된 줄만 두면 대부분의 항목에서 이 근거가 사라진다. 이미 찾은 값은 모두 가리고, 사람의 정보가 몰려 있는 파일(로그, 샘플 데이터, 고객정보가 나온 파일)에는 주변 줄을 만들지 않으므로 남는 위험은 규칙이 놓친 텍스트에 한정된다. 이 도구의 사용자는 원래 그 소스를 다루는 개발자다.

## 검토한 다른 방법

- 원본 보기를 두지 않기: `AGENTS.md`의 문장을 그대로 지킬 수 있지만, 미리보기로 구별되지 않는 값은 판정자가 OpenBao나 원래 소스를 따로 열어야 하고 그 열람은 기록에 남지 않는다.
- `GET`으로 열기: 링크 하나로 열 수 있지만, 감사 기록을 남기는 요청이 `GET`이 되어 미리 가져오기나 브라우저 기록 복원만으로도 기록과 열람이 생긴다.
- 읽은 뒤 기록하기: 기록이 실패하면 값은 이미 나간 뒤다.
- 값을 세션이나 캐시에 잠시 두고 "닫기"까지 유지하기: 값이 요청 밖에 머무는 자리가 하나 더 생긴다.
- 주변 줄 대신 탐지된 줄만 저장하기: 규칙이 놓친 텍스트가 보일 범위는 줄지만, 판정의 근거가 되는 문맥이 사라지고 탐지된 줄에도 규칙이 놓친 텍스트는 남을 수 있다.
