# 계획 4를 구현하면서 대신 정한 것

- 날짜: 2026-11-20
- 상태: 확정

## 배경

계획 4(`docs/superpowers/plans/2026-11-19-04-design-and-triage.md`)는 하위 에이전트가 Task를 하나씩 구현하고 다른 에이전트가 검토하는 방식으로 진행했다. 진행하는 동안 계획과 설계가 답하지 않는 것, 계획의 문장과 확인받은 시안이 다른 것이 나왔고, 그때마다 멈추지 않고 정한 뒤 계속했다. 사용자는 2026-11-20에 "확인받지 말고 권고안대로 정하고 문서로 남기라"고 했다. 이 문서는 그렇게 정한 것을 한곳에 모은다. 틀렸다면 각 항목의 "틀렸을 때" 만큼만 고치면 된다.

계획 문서의 "검토 때 정해 주실 것" 17개는 사용자가 직접 확정한 것이라 여기에 넣지 않았다.

## 결정

### 진행 방식

| 정한 것 | 이유 | 틀렸을 때 |
|---|---|---|
| Task 1(시안)은 사용자의 확인을 기다리고, 그동안 화면이 없는 Task 3~5를 먼저 구현했다 | 계획의 Task 1이 그렇게 적었다 | 없음 |
| PR 2의 작업은 `feat/verdict-screen` 위에 쌓은 `feat/triage-screen`에서 했다 | PR 1을 Task 5에서 멈춰 두려고 | 브랜치 이름을 바꾼다 |
| Task 10의 화면 확인은 처음에 볼륨을 지우지 않고 했고, 사용자의 지시를 받은 뒤 `down -v`로 빈 볼륨에서 다시 띄워 등록, 스캔, 원본 보기를 확인했다 | 볼륨 삭제는 되돌릴 수 없다. 로컬 볼륨에는 예제의 가짜 값만 있었다 | 없음 |

### 화면

| 정한 것 | 이유 | 틀렸을 때 |
|---|---|---|
| 프로젝트 목록에 마지막 스캔, 미판정, 전체 열을 넣었다(`Store.ProjectSummaries`) | 확인받은 시안에 있다 | 조회 하나와 열 세 개를 뺀다 |
| 판정 화면에서 고른 고객정보 줄의 주소는 `sel=c.<판정\|none>.<종류>.<파일>`이다 | "전체" 필터에서는 같은 파일과 종류의 줄이 판정별로 따로 나온다 | handler 하나의 주소 형식을 바꾼다 |
| shell 파일에만 나온 묶음의 이름 입력란은 접두어 `EXT_` 뒤에 저장하는 형태(`ssh.main.password`)를 그대로 보인다 | 시안 `DetailSuggested.dc.html`이 그렇게 그렸다 | 접두어 문자열 하나를 바꾼다 |
| 시각은 D2Coding으로 쓴다 | `docs/design/README.md`와 결정 기록 0029 | CSS 클래스 하나 |
| 감사 로그 표는 5열이고 대상은 "내용" 열에 넣었다 | 계획의 문장(별도의 "대상" 열)보다 확인받은 시안 `Audit.dc.html`을 따랐다 | 열 하나를 더한다 |
| 분류 이름은 모든 화면에서 긴 이름("저장소 접속 정보" 등)을 쓴다 | 화면마다 이름이 달랐다. 시안의 짧은 이름("스토리지")은 쓰지 않는다 | 표 하나를 바꾼다 |
| 스캔 화면의 파일 수는 "찾은 파일 N개"로 쓰고 건너뛴 파일도 센다고 알린다 | 저장된 수가 건너뛴 파일을 포함하고, 실제로 읽은 수는 스키마를 바꾸지 않고는 계산할 수 없다 | 읽은 파일 수를 따로 저장한다 |
| 감사 로그의 판정 줄에 종류를, 고객정보는 파일도 보인다. 기록 당시가 아니라 지금 그 묶음에 든 항목 기준이다 | 시안에 있고, 조회 한 번으로 된다. 종류와 경로는 값이 아니다 | 기록할 때 함께 저장한다 |

### 판정의 규칙

| 정한 것 | 이유 | 틀렸을 때 |
|---|---|---|
| 판정과 옮기기가 허용되는지는 마지막으로 성공한 스캔에 나온 구성원만 보고 정한다 | 화면이 그 구성원만 보여 준다. 지난 스캔에만 있던 JSP 항목이 외부화를 영영 막는 일이 생겼다 | 지난 스캔의 JSP 항목이 다시 나타나면 외부화 묶음에 외부화할 수 없는 구성원이 생긴다. 적용(계획 5)이 다시 확인해야 한다(`docs/next-steps.md`, 결정 기록 0027) |
| 이름 제안에서 종류가 "기타"면 항목 낱말은 `value`, 키 종류면 `key`다. `value`는 대상 낱말로 쓰지 않는다 | 계획의 테스트 표가 그 값이다 | 제안이 달라질 뿐이고 사용자가 고칠 수 있다 |
| 이름을 읽을 설정 키에 가린 값(`*`)이 섞여 있으면 대상을 `main`으로 한다 | 가린 값의 앞 4자가 이름에 들어가 소스와 manifest로 나갈 수 있었다 | 없음 |
| 판정 양식은 판정 버튼을 눌러야만 저장한다. 입력란에서 Enter를 눌러도 저장되지 않고, 판정 값 없는 요청은 400이다. 판정 취소는 `verdict=none`이다 | 브라우저가 Enter를 양식의 첫 버튼으로 처리해, 고르지 않은 판정(외부화, 오탐, 삭제·마스킹)이 저장되었다 | 없음 |
| 고객정보 항목은 묶음을 옮길 수 없다 | 확정 5번("고객정보는 항목마다 묶음 하나"). 화면에는 없지만 직접 만든 요청으로 합칠 수 있었다 | 없음 |
| 고객정보 묶음은 묶음 주소로 판정할 수 없다(404). 파일과 종류 단위의 주소만 쓴다 | 한 줄로 모아 보이는 무리가 갈라진다 | 없음 |

### 원본 보기와 설정

| 정한 것 | 이유 | 틀렸을 때 |
|---|---|---|
| 원본을 읽지 못했을 때의 안내를 둘로 나눴다. 답이 없으면 "비밀 저장소에 연결할 수 없습니다", 답은 왔지만 거부되었거나 값이 깨졌으면 "비밀 저장소에서 원본을 읽지 못했습니다" | 권한 오류를 연결 문제로 읽게 된다 | 문장 하나 |
| 스크립트 없이 원본 보기를 한 응답을 새로 고치면 한 번 더 읽고 감사 기록도 한 줄 더 남는다 | 값을 어디에도 두지 않으려면 다시 읽을 수밖에 없다(결정 기록 0028) | 없음 |
| web이 기동할 때 설정을 가린 채로 한 줄 로그에 남긴다 | worker와 같게 | 줄 하나를 뺀다 |
| compose의 web은 openbao가 시작되기만 기다린다(`service_started`) | web은 OpenBao 없이도 기동해야 한다 | 조건 하나 |
| 스캔 기록에 요청한 사람의 이름을 저장한다(`requester_name`) | 화면에 식별자(UUID)가 보였다(결정 기록 0030) | 열 하나 |
| 로그인 흐름이 아닌 400 화면은 "요청을 처리할 수 없습니다"를 보인다 | "다시 로그인해 주세요"가 필터 값이 틀린 요청에도 나왔다 | 문장 하나 |

### 고치지 않고 넘긴 것

`docs/next-steps.md`의 "계획 4에서 남은 일"에 적었다. htmx를 2.0.11에 고정한 것, 판정 탭의 건수가 묶음 수인 것, 호스트·포트·계정을 자동으로 묶지 않는 것, htmx로 보낸 원본 보기가 실패하면 화면이 그대로인 것 등이다.

## 이유

멈춰서 묻는 것보다 정하고 기록하는 편이 빠르고, 위의 결정은 모두 고치는 데 드는 일이 작다. 되돌릴 수 없는 일(볼륨 삭제, push, PR)은 사용자의 지시를 받은 뒤에 했다.

## 검토한 다른 방법

- **항목마다 사용자에게 묻는다**: 하루가 걸리고, 대부분은 시안이나 확정 내용에서 답이 나온다.
- **기록하지 않고 진행한다**: 사용자가 무엇이 대신 정해졌는지 알 수 없다.
