# 프로젝트 폴더의 파일 바꾸기

- 날짜: 2026-11-20
- 상태: 확정

## 배경

적용은 소스 파일의 값을 자리표시자로 바꾸거나 키 파일을 지우고, 프로젝트 폴더에 manifest를 새로 만든다. 이 일은 `internal/rewrite`의 `Dir`이 `os.Root`로 연 프로젝트 폴더 안에서 한다. 저장소는 신뢰할 수 없으므로 심볼릭 링크를 따라가거나 폴더 밖으로 나가면 안 되고, 파일을 읽은 뒤 바뀌었으면 쓰지 않아야 하며, 중간에 죽어도 파일이 반쯤 쓰인 채로 남으면 안 된다.

Go 1.27.4에서 확인한 사실:

- `os.Root.OpenFile`은 `O_NOFOLLOW`를 주어도 루트 안을 가리키는 마지막 심볼릭 링크를 따라간다(`root_unix.go`의 `checkSymlink`). 루트 밖을 가리키는 링크는 거부한다.
- `os.Root.Lstat`은 마지막 마디를 따라가지 않지만, 중간 마디가 루트 안을 가리키는 링크면 따라간다.
- `Root.Link`는 대상 이름이 있으면 `EEXIST`로 실패한다.

## 결정

1. 읽기는 `Lstat`으로 일반 파일인지 본 뒤 `O_NOFOLLOW|O_NONBLOCK`으로 열고, 연 파일의 `Fstat`이 `Lstat`과 같은 파일(`os.SameFile`)인지 확인한다. 경로의 중간 폴더는 모두 `Lstat`으로 링크가 아닌 폴더인지 확인한다. 루트 안을 가리키는 링크도 거부한다.
2. 바꿔 쓰기는 같은 폴더의 임시 파일(`<이름>.se-apply-<16자리>.tmp`, `O_EXCL`)에 쓰고 `Sync`한 뒤, `rename` 직전에 대상을 다시 확인하고 `rename`, 부모 폴더 `Sync` 순서로 한다. 대상이 읽을 때와 같은 파일, 크기, 수정 시각이 아니면 `ErrChanged`다.
3. 링크가 둘 이상인 파일(하드 링크)은 바꾸지도 지우지도 않는다(`ErrHardLinked`). 쓰기 전과 `rename` 직전에 모두 확인한다.
4. 새 파일 만들기(`Create`)는 임시 파일을 대상 이름으로 하드 링크한 뒤 임시 파일을 지운다. 대상이 그 사이에 생겼으면 링크가 실패하므로 남의 파일을 덮어쓰지 않는다.
5. 변경이 디스크에 반영된 뒤의 단계(부모 폴더 `Sync`, `Create`의 임시 파일 지우기)가 실패하면 `ErrAfterCommit`을 감싼 오류를 돌려준다. 그 밖의 오류는 대상이 그대로라는 뜻이다. 실행기는 `ErrAfterCommit`이면 먼저 적은 기록을 열어 두고 다음 맞추기(R1)가 디스크의 해시로 정하게 한다.
6. 바꾼 파일은 원래 파일의 권한 비트만 이어받는다. setuid, setgid, sticky 비트와 소유자는 이어받지 않는다(worker에는 `CAP_CHOWN`이 없다).

## 이유

- `O_NOFOLLOW`만으로는 루트 안의 링크를 막지 못하므로 열린 파일이 확인한 파일인지 따로 맞춰 봐야 한다.
- 하드 링크된 파일을 `rename`으로 바꾸면 다른 이름에는 원래 바이트(비밀 값 포함)가 그대로 남는데 적용은 성공으로 보고된다. 지우기도 같다.
- `rename`은 대상이 있으면 덮어쓰므로, 존재 확인과 `rename` 사이에 생긴 파일을 지울 수 있다. 하드 링크는 그 경우 실패한다.
- 변경 뒤의 실패를 변경 전의 실패와 구별하지 못하면 실행기가 "바꾸지 않았다"고 기록할 수 있다. 실제 디스크 상태는 맞추기가 해시로 정한다.
- setuid 같은 특수 비트를 worker가 새 파일에 다시 거는 일은 필요 없고, 소스 트리의 실행 파일에 특수 비트를 남길 이유도 없다.

## 검토한 다른 방법

- 마지막 마디를 직접 `openat(O_NOFOLLOW)`로 열기: `os.Root`가 그 fd를 내주지 않아 `syscall`로 폴더를 다시 따라가야 하고, `os.Root`가 보장하는 루트 밖 차단을 다시 구현해야 한다.
- `Create`에 `Lstat` 확인 뒤 `rename`: 하드 링크를 지원하지 않는 파일 시스템에서도 동작하지만, 확인과 `rename` 사이에 생긴 파일을 덮어쓴다. compose의 마운트(Linux bind mount, Docker Desktop virtiofs)가 하드 링크를 지원하는지는 계획 5 Task 15에서 확인한다.
- Linux `renameat2(RENAME_NOREPLACE)`, macOS `renamex_np(RENAME_EXCL)`: 운영체제마다 다르고 `os.Root`에 없다.
- 하드 링크된 파일을 복사해 바꾸기(같은 inode에 덮어쓰기): 원자적이지 않아 중간에 죽으면 반쯤 쓰인 파일이 남는다.
