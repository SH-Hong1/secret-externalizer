# 파일 인코딩을 순서대로 판별하고 EUC-KR 변환에 x/text를 쓴다

- 날짜: 2026-11-19
- 상태: 확정

## 배경

스캔 대상인 오래된 Java/Spring 소스에는 EUC-KR(CP949) 파일이 많고 줄 끝이 CRLF인 경우도 흔하다. 외부 스캐너에는 UTF-8 사본을 넘겨야 하고, 스캐너가 알려 주는 위치는 다시 원본 기준의 줄과 열로 바꿔야 한다. 표준 라이브러리에는 EUC-KR 변환이 없으므로 의존성 추가의 이유도 함께 기록한다.

## 결정

`internal/textfile`의 `Read`는 다음 순서로 판별한다.

1. UTF-8 BOM으로 시작하면 BOM을 뗀 나머지를 UTF-8로 본다. 나머지의 처음 8,000바이트에 NUL이 있으면 `ErrBinary`이고, 나머지가 `utf8.Valid`가 아니면 `ErrUnknownEncoding`이다. BOM이 있는 파일은 EUC-KR로 바꿔 보지 않는다.
2. UTF-16 BOM(`FF FE`, `FE FF`)으로 시작하면 `ErrUnknownEncoding`이다.
3. 처음 8,000바이트에 NUL이 있으면 `ErrBinary`다.
4. 전체가 `utf8.Valid`이면 UTF-8이다.
5. 아니면 `golang.org/x/text/encoding/korean`의 `korean.EUCKR`로 UTF-8로 바꾼다. 결과에 `U+FFFD`가 있으면 `ErrUnknownEncoding`이다.

`korean.EUCKR`은 이름과 달리 CP949(통합 완성형, UHC)를 구현한다. 문서에도 "EUC-KR, also known as Code Page 949"라고 적혀 있고, 완성형 2,350자 밖의 한글(예: `똠`)도 변환한다. 테스트 `TestRead_CP949ExtendedHangul`이 `똠방각하`로 이를 확인한다.

의존성은 `golang.org/x/text`(v0.44.0, 확인 시점의 최신 안정 버전)를 쓴다. 이미 간접 의존성으로 `go.mod`에 있었고 직접 의존성이 되었다.

`File.Hash`는 BOM과 줄 끝을 포함한 디스크의 원래 바이트의 SHA-256이다. 변환 결과가 아니라 원본을 기준으로 해야 같은 파일을 다시 스캔했을 때 변경 여부를 판단할 수 있다.

## 이유

- UTF-8은 EUC-KR 바이트열이 우연히 UTF-8로 유효할 확률이 매우 낮은 규칙적인 구조다. 먼저 `utf8.Valid`를 보면 UTF-8 파일을 잘못 변환할 일이 사실상 없다.
- EUC-KR 변환기는 잘못된 바이트를 오류 대신 `U+FFFD`로 바꾸므로, `U+FFFD`를 거부해야 깨진 파일을 조용히 통과시키지 않는다. 정상 EUC-KR 텍스트는 `U+FFFD`로 변환되지 않는다.
- BOM이 있는 파일도 다른 파일과 같이 NUL과 UTF-8 유효성을 확인한다. 확인하지 않으면 깨진 바이트가 주변 줄로 postgres에 들어가려다 거부되어 그 프로젝트의 스캔이 매번 실패한다.
- NUL 검사를 처음 8,000바이트로 제한하면 큰 파일 전체를 훑지 않고도 바이너리를 걸러 낸다. 검사 구간은 문자 경계와 상관없이 바이트 단위이고 NUL은 UTF-8의 다른 문자 안에 나타나지 않으므로 다중 바이트 문자가 경계에 걸려도 문제가 없다. 8,000바이트 뒤에 NUL이 있는 파일(제자리에서 잘린 로그 등)은 텍스트로 남으므로, 주변 줄은 `finding.Context`가 NUL과 다른 제어 문자, 깨진 UTF-8을 `U+FFFD`로 바꿔 저장한다.
- UTF-16은 지원하지 않고 명확한 오류로 알린다. 대상이 되는 소스에는 거의 없고, 조용히 바이너리로 처리하는 것보다 사유가 분명하다.
- 표준 라이브러리만으로 EUC-KR 표(약 2만 개 항목)를 직접 만드는 것은 현실적이지 않다. `x/text`는 Go 팀이 유지하고 이미 이 프로젝트의 의존성 그래프에 있었다.

## 검토한 다른 방법

- 통계적 문자셋 감지기(`chardet` 계열): 짧은 설정 파일에서는 확신도가 낮고 결과가 입력에 따라 달라져 재현하기 어렵다. 이 프로젝트가 만나는 인코딩은 UTF-8과 EUC-KR 둘뿐이라 고정된 순서가 더 단순하고 예측 가능하다.
- 파일 확장자나 프로젝트 설정으로 인코딩을 지정: 사용자가 프로젝트마다 입력해야 하고, 한 프로젝트에 두 인코딩이 섞인 경우를 다루지 못한다.
- 모든 비 UTF-8 파일을 EUC-KR로 간주하고 `U+FFFD`를 허용: 깨진 파일의 위치와 값이 어긋난 채 스캔 결과가 나온다.
