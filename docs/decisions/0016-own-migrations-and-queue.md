# 마이그레이션과 작업 큐를 직접 만든다

- 날짜: 2026-11-19
- 상태: 확정

## 배경

스키마를 버전별로 적용하는 마이그레이션 도구와, web이 올린 스캔 작업을 worker가 가져가는 작업 큐가 필요하다. web과 worker는 같은 postgres 계정 `se_app`을 쓰고, 둘 다 기동할 때 `Migrate`를 부른다.

## 결정

- 마이그레이션은 `internal/db`에 직접 만든다. `NNNN_이름.sql` 파일을 `go:embed`로 바이너리에 넣고, 번호순으로 실행하며, 실행한 번호를 `schema_migration`에 남긴다. 전체를 `pg_advisory_lock`으로 감싸 web과 worker가 동시에 기동해도 차례로 실행되게 하고, 파일 하나가 트랜잭션 하나다.
- 작업 큐는 postgres 표 하나와 `FOR UPDATE SKIP LOCKED`, 임대(lease) 만료 시각으로 만든다.
- 작업은 최대 세 번까지 내준다. 세 번째 임대까지 끝나면 작업과 스캔을 `failed`로 닫는다.
- 임대 시각은 worker의 시계가 아니라 데이터베이스의 `now()`로 정하고 비교한다.
- 결과를 쓰는 문장은 `locked_by`가 자기 worker ID일 때만 반영한다. worker ID는 호스트 이름에 프로세스마다 다른 난수를 붙여 만든다.

## 이유

- 쓰는 기능이 작다. 앞으로만 가는 SQL 파일 실행, 적용 기록, 동시 기동 직렬화가 전부이고 코드가 작아 한 파일에서 읽을 수 있다.
- `tern`은 `sprig`와 `cobra`를 끌어온다. 쓰지 않는 기능 때문에 의존성이 늘고, 그 의존성이 보안 검토 대상이 된다.
- `River`는 모듈이 8개 늘고 자체 스키마를 가지며 1.0 이전이라 인터페이스가 바뀔 수 있다. 작업 종류가 스캔 하나뿐인 지금은 큐의 기능을 대부분 쓰지 않는다.
- 스캔 중에 worker를 죽이는 입력(메모리 부족 등)이 있어도 같은 작업이 끝없이 되살아나면 안 된다. 횟수 제한이 없으면 그 스캔이 worker를 계속 죽인다. 세 번은 일시적인 장애(재시작, 배포)를 견디면서 계속되는 문제는 드러내는 값이다.
- 여러 worker의 시계는 서로 다르므로, 임대 만료를 각자의 시계로 판단하면 아직 일하는 worker의 작업을 다른 worker가 가져갈 수 있다. 한 곳(데이터베이스)의 시계로 정하면 비교가 일관된다.
- 임대가 끝나 다른 worker가 작업을 가져간 뒤에도 느린 worker가 결과를 쓸 수 있다. `locked_by`로 걸러 오래된 worker의 저장을 막는다. 같은 호스트에서 재시작한 worker가 이전 프로세스와 같은 ID를 가지면 이 검사가 무력해지므로 ID는 프로세스마다 달라야 한다.
- 큐를 같은 postgres에 두면 작업 등록과 프로젝트 변경을 한 트랜잭션으로 묶을 수 있고, 별도 브로커를 운영하지 않는다.

## 검토한 다른 방법

- `golang-migrate`, `goose`: 쓰는 기능에 비해 드라이버와 부가 기능이 많다. 위 이유로 직접 만드는 쪽이 더 작다.
- `tern`: 위에서 설명한 의존성 때문에 고르지 않았다.
- `River`: 위에서 설명한 모듈 수, 별도 스키마, 1.0 이전 상태 때문에 고르지 않았다.
- valkey를 큐로 쓰기: valkey는 디스크에 남기지 않으므로 재시작하면 작업이 사라진다.

작업 종류가 늘어 재시도, 예약, 우선순위가 필요해지면 `River`를 새 결정으로 다시 검토한다.
