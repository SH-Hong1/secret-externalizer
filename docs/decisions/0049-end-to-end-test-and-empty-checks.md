# 스캔부터 확인 스캔까지 도는 통합 테스트와, 바꿀 것이 없는 점검

- 날짜: 2026-11-23
- 상태: 확정

## 배경

스캔, 판정, 적용, 확인 스캔은 각자의 테스트가 있었지만 서로 이어서 도는 자동 테스트는 없었다. `internal/apply`의 통합 테스트는 실제 데이터베이스와 OpenBao를 쓰되 스캔 결과는 테스트가 손으로 만든 것을 넣었고, 실제 스캐너를 쓰는 테스트는 스캔에서 멈췄다. 계획 5의 손 확인에서 나온 결함 둘(placeholder를 다시 찾는 것, OpenBao 초기화 순서)은 이 틈에 있었다. 대시보드도 쿼리와 화면을 따로 붙잡을 뿐 스캔에서 이어지는 테스트가 없었다.

이 테스트를 처음 돌렸을 때 결함이 하나 더 나왔다. 모든 것을 적용하고 커밋한 뒤 다시 점검하면, 남은 판정이 worker가 언제나 건너뛰는 것(다른 저장소 안의 파일, 소스 파일 안의 키 파일 경로)뿐인데도 점검이 `ready`였다. `nothing-to-apply`는 저장된 자료만으로 세운 계획(`NewPlan`)에 대상이 없을 때만 붙었고, 파일을 읽은 뒤에 건너뛰기로 바뀐 대상은 세지 않았다.

## 결정

1. **통합 테스트 `TestIntegration_ScanApplyRescan`을 `internal/apply`에 둔다.** 예제 프로젝트(`newShop`)를 실제 betterleaks, opengrep, 키 파일 스캐너, postgres, OpenBao(`openbao-test`), git으로 돌린다. 스캔 러너와 적용 러너를 직접 만들고 작업은 테스트가 하나씩 집어 넘긴다.
2. **판정은 도구의 추천을 그대로 받는 사용자처럼 내린다.** 고객정보는 삭제·마스킹, 프론트엔드 파일의 묶음은 추천대로 보류, 나머지는 추천 이름(`triage.Default`)으로 외부화한다.
3. **예제의 발견 목록을 고정하지 않고, 규칙이 무엇을 찾든 지켜져야 하는 것을 확인한다.**
   - 스캔과 점검은 프로젝트의 파일을 바꾸지 않는다.
   - 실패한 항목이 없고, 건너뛴 사유는 예제가 일부러 만든 둘(`nested-repository`, `key-in-source-file`)뿐이다.
   - OpenBao에 저장된 값의 지문이 그 묶음의 지문과 같다.
   - 외부화한 비밀번호, 토큰, 키, 기타 비밀 값은 적용이 건너뛴 자리가 없는 파일 어디에도 남지 않고, 모든 테이블, worker 로그, manifest에도 없다.
   - 확인 스캔은 적용이 바꾼 자리를 다시 찾지 않고, 첫 스캔에 없던 것을 찾지 않으며(placeholder, 마스크, manifest의 줄이 항목이 되지 않는다), 적용이 건드리지 않은 파일의 항목을 잃지 않는다.
   - `Reappeared`는 확인 스캔이 찾은 항목 가운데 적용이 저장한 묶음에 든 것의 수와 같다.
   - 대시보드의 프로젝트 요약은 확인 스캔의 리포트 요약과 같고, 추이의 점은 둘이다.
   - 바뀐 것을 커밋한 뒤의 두 번째 점검은 `nothing-to-apply` 하나로 막힌다.
4. **점검은 파일을 읽은 뒤에도 바꿀 위치가 하나도 없고 manifest를 기다리는 적용된 값도 없으면 `nothing-to-apply`로 막는다.** 추적되지 않는 파일의 고객정보는 점검에서 건너뛰기로 표시하지 않으므로(사용자가 동의하면 적용된다) 바꿀 위치로 센다. 막는 문장은 "적용할 수 있는 항목이 없습니다."다.
5. **적용 단계에는 이 조건을 더하지 않는다.** 점검과 적용 사이에 파일이 바뀌어 모든 위치가 건너뛰어지면, 적용은 지금처럼 건너뛴 항목과 사유를 적고 끝난다.

## 이유

- 러너를 직접 만드는 쪽은 `internal/apply`에 이미 있는 준비 코드(테스트마다의 스키마, `openbao-test`에 worker 정책 만들기, 예제 프로젝트)를 그대로 쓴다. `cmd/worker`의 `runWith`로 돌리면 큐의 폴링과 설정 읽기까지 지나지만, 그 연결은 `cmd/worker`의 테스트가 가짜 스캐너로 이미 붙잡고 있고 OpenBao 준비 코드를 세 번째로 베껴야 한다.
- 예제의 발견 목록은 `internal/ruleset`의 `expected.json`이 붙잡는다. 여기서 또 고정하면 규칙을 고칠 때마다 두 곳을 고쳐야 하고, 이 테스트가 보려는 것(단계 사이의 약속)이 목록 차이에 묻힌다.
- 호스트, 포트, 계정, URL은 규칙이 보고하지 않은 자리와 다른 항목의 주변 줄에 남을 수 있다는 것이 알려진 한계라서(`docs/next-steps.md`), "어디에도 남지 않는다"는 비밀번호, 토큰, 키, 기타 비밀 값에만 건다.
- 바꿀 것이 없는데 `ready`이면 사용자는 "적용"을 누르고 아무 일도 일어나지 않은 실행을 본다. 점검이 이미 모든 위치의 건너뛰는 사유를 알고 있으므로 그때 막는 것이 맞다.
- 적용 단계에서 막으면 실행이 `failed`가 되는데, 실패한 실행의 결과 화면은 막은 조건을 보이지 않는다. 건너뛴 항목과 사유를 보이는 지금의 끝이 더 많이 알려 준다.

## 검토한 다른 방법

- **compose 스택 전체를 띄워 web 화면부터 누르는 테스트.** Keycloak 로그인과 브라우저가 필요하고 2GB Docker VM에서 느리다. 화면은 `internal/web`의 테스트가 붙잡는다.
- **적용된 항목의 목록을 정확히 고정한다.** 위의 이유로 하지 않았다.
- **`NewPlan`이 건너뛰는 사유를 모두 미리 안다.** 다른 저장소 안의 파일인지, 파일이 바뀌었는지는 디스크와 git을 읽어야 알 수 있고, 계획은 저장된 자료만으로 세워 확인의 digest가 되어야 한다.

## 알려진 한계

- 기간 필터와 화면은 이 테스트가 지나지 않는다. 대시보드는 저장소 메서드까지만 본다.
- 적용 화면이 점검 전에 데이터베이스만 보고 보이는 "적용할 판정이 있음: 통과"는 그대로다. 건너뛰는 사유는 파일을 읽어야 알 수 있다.
