# 스캔 리포트가 보이는 것

- 날짜: 2026-11-20
- 상태: 확정

## 배경

설계 8절은 리포트에 "탐지, 외부화, 삭제, 오탐, 보류"의 건수와 종류별 파일, 남은 미판정 항목, 판정 이력이 들어가고 값은 들어가지 않는다고 했다. 어떤 시점의 무엇을 어떤 단위로 보일지, 얼마나 길게 보일지는 정하지 않았다. 사용자가 2026-11-20에 확인 없이 권고안으로 정하라고 해서, 계획 6(`docs/superpowers/plans/2026-11-20-06-report-and-pdf.md`)의 "검토 때 정해 주실 것" 2~9번을 이 문서에 모은다. 틀렸다면 해당 항목만 고치면 된다.

## 결정

1. 리포트는 저장하지 않고 열 때마다 만든다. 시점을 고정한 사본은 PDF다. 머리와 PDF에 만든 시각(`GeneratedAt`)을 적는다.
2. 스캔 N의 리포트는 세 가지를 보인다.
   - 찾은 것: 스캔 N이 찾은 묶음. 판정은 리포트를 만든 시각의 것이다.
   - 적용한 것: 그 프로젝트의 적용 실행 가운데 스캔 N이 요청되기 전에 시작된 실행(`coalesce(started_at, finished_at) < scan.requested_at`)이 `applied`로 남긴 항목 전부(누적). 스캔 N이 그 실행의 확인 스캔이면(`scan.apply_id`) 시각과 관계없이 앞선 실행으로 본다. 시작 시각도 끝난 시각도 없는 실행(작업을 돌려받아 다시 대기 중인 실행)의 항목은 어느 스캔의 앞에도 뒤에도 두지 않는다.
   - 판정 이력: 그 프로젝트의 판정, 묶음 옮기기, 적용 확인 기록. 원본 보기 기록은 싣지 않는다.
3. 리포트와 PDF에는 미리보기, 지문, 주변 줄을 싣지 않는다. `report` 패키지의 타입에는 그런 필드가 없고 `TestTypes_HoldNoValueField`가 붙잡는다. 사용자가 쓴 사유(note)는 싣는다. `AGENTS.md`의 Security 절에 한 줄을 더했다.
4. 건수의 단위는 묶음이고 위치 수를 함께 보인다(`Count`). 고객정보는 값마다 묶음 하나이므로 묶음 수가 곧 찾은 값의 수다.
5. 요약의 숫자는 일곱 개다. 찾은 항목, 외부화 완료, 삭제·마스킹 완료, 오탐, 보류, 미판정, 적용 대기. 찾은 항목은 오탐, 보류, 미판정, 적용 대기의 합이다. 증감(`Delta`)은 바로 앞의 성공한 스캔과의 차이이고, 그런 스캔이 없으면 영이다.
6. 찾은 묶음은 세 절 가운데 정확히 한 곳에 실린다. 오탐은 오탐 절, 오탐이 아니고 프론트엔드 구성원이 있거나 보류 사유가 "구조 변경 필요"이면 구조 변경 절, 나머지는 "남은 항목" 절이다. 고객정보는 프론트엔드 파일에 있어도 삭제·마스킹할 수 있으므로 파일 종류로는 구조 변경 절에 가지 않는다.
7. 고객정보는 파일, 종류, 판정, 보류 사유, 사유 글이 같은 것끼리 한 줄로 묶는다. 비밀 값은 묶음마다 한 줄이다. 외부화한 항목은 소스에 쓰인 이름마다 한 줄이고 바뀐 자리를 모두 적는다. 한 묶음이 `.yml`과 `.sh`에 걸치면 이름이 둘이라 항목도 둘이다. 삭제·마스킹은 종류(`phone`, `rrn`, `email`, `card`, `address` 순)와 파일로 보인다.
8. 절마다 1,000줄(`MaxRows`)까지만 싣고 "외 N줄"을 적는다. 외부화한 항목 하나의 자리는 50곳(`MaxPlaces`)까지다. 건수는 언제나 전체를 센다.

## 확인한 사실

2026-11-20에 테스트 데이터베이스에서 확인했다.

- 한 트랜잭션의 `now()`는 트랜잭션을 시작한 시각이다. `Decide` 한 번으로 묶음 세 개를 판정하면 `audit_event` 세 줄의 `at`이 같고, `(at, actor_subject, actor_name, action, detail)`로 `GROUP BY`하면 한 줄이 된다. `jsonb` 열로 묶을 수 있다. 그래서 판정 이력은 이 다섯 열로 묶는다.
- 정상으로 끝난 실행은 `started_at`이 확인 스캔의 `requested_at`보다 앞서고, `finished_at`은 확인 스캔의 `requested_at`과 같다(같은 트랜잭션).
- `ReleaseJob`으로 `started_at`이 비워진 실행을 다시 시작하지 않은 채 `FailApply`로 닫으면 `started_at`은 NULL이고 `finished_at`이 확인 스캔의 `requested_at`과 같다. `coalesce(started_at, finished_at) < requested_at`만으로는 이 실행이 자기 확인 스캔의 앞에 들지 않아, 방금 바꾼 항목이 확인 스캔의 리포트에서 빠지고 "이후 적용됨"으로 보인다. 그래서 2번의 "적용한 것"에 `scan.apply_id`로 가리킨 실행을 더했다. 다른 실행의 시작 시각이 스캔 요청 시각과 같아지는 일은 스캔과 적용이 겹치지 않으므로(결정 기록 0036) 생기지 않는다.
- `http.ServeMux`는 `GET /scans/{id}`, `GET /scans/{id}/report`, `GET /scans/{id}/report.pdf`를 함께 등록해도 충돌하지 않고, 세 주소를 각각의 패턴으로 보내며 `{id}`를 같은 값으로 읽는다(2026-11-21에 go1.27.4의 `net/http`로 확인).

## 이유

- 판정은 스캔이 끝난 뒤에 하므로 스캔 종료 시점의 스냅숏에는 판정도 적용도 없다. 언제 확정하는지 정할 사건이 없고 테이블만 는다.
- 마지막 성공한 스캔의 리포트가 프로젝트의 지금 상태를 말하는 문서가 되려면, 적용 뒤의 확인 스캔 리포트에 방금 외부화한 항목이 실려야 한다.
- PDF는 도구 밖으로 나가는 문서이고 화면 리포트는 PDF와 같은 내용이어야 하므로, `AGENTS.md`가 데이터베이스와 화면에만 허용하는 미리보기와 지문을 둘 다에서 뺀다.
- 로그 파일이 수천 개인 프로젝트에서도 화면이 5초 안에 그려지고 PDF가 제한 시간 안에 만들어지게 한다.

## 검토한 다른 방법

- 스캔이 끝날 때 리포트를 스냅숏으로 저장한다. 위의 이유로 버렸다.
- 스캔 N을 근거로 한 실행(`apply_run.scan_id = N`)만 싣는다. 확인 스캔의 리포트에 외부화한 항목이 하나도 없고, 공유할 문서가 사라졌는지 확인한 결과가 없는 "적용 전 스캔의 리포트"가 된다.
- 지난 스캔의 리포트는 판정도 그때의 것으로 되돌려 보인다. `audit_event`를 되감아야 하고 묶음 옮기기 때문에 정확히 되돌릴 수 없다.
- 미리보기를 PDF에만 뺀다. 화면과 PDF가 다른 내용이 된다.

## 알려진 한계

한 자리를 적용하고, 사람이 되돌리고, 다시 적용하면 `applied` 항목이 둘이라 그 자리가 외부화한 항목의 자리에 두 번 실리고 두 번 센다. 판정 화면의 "적용됨" 탭과 같은 셈이다.
