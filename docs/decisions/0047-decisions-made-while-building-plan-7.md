# 계획 7을 구현하면서 대신 정한 것

- 날짜: 2026-11-23
- 상태: 확정

## 배경

계획 7(`docs/superpowers/plans/2026-11-23-07-dashboard.md`)은 계획 4, 5, 6과 같은 방식으로 진행했다. 하위 에이전트가 Task를 하나씩 구현하고 다른 에이전트가 검토했다. 사용자는 2026-11-20에 "확인받지 말고 권고안대로 정하고 문서로 남기라"고 했다. 그래서 계획 문서의 "검토 때 정해 주실 것" 13개를 사용자 검토 없이 권고안으로 확정했다. 구현하고 확인하는 동안 계획이 답하지 않은 것도 멈추지 않고 정했다. 이 문서는 그렇게 정한 것을 한곳에 모은다. 주제별 결정 기록(0045 대시보드가 세는 것, 0046 서버가 그리는 차트)에 이미 적은 것은 번호를 붙였다. 틀렸다면 각 항목의 "틀렸을 때" 만큼만 고치면 된다.

## 결정

### 진행 방식

| 정한 것 | 이유 | 틀렸을 때 |
|---|---|---|
| 계획 문서의 "검토 때 정해 주실 것" 13개를 모두 권고안으로 확정했다. 구현하면서 바꾼 항목은 없다 | 사용자의 지시. 사용자 검토 대신 별도의 검토 에이전트가 계획을 읽었고, 그 검토가 찾은 다섯 가지(끝난 시각이 없거나 같은 스캔의 순서, 소수 눈금, 비율의 내림, 양식의 빈 값, 묶음의 분류를 정하는 구성원)를 구현 전에 계획에 넣었다 | 사용자가 계획과 결정 기록을 읽은 뒤 해당 항목을 다시 한다 |
| 계획도 PR도 하나다(검토 항목 1) | Task 다섯 개이고 화면 하나다. 마이그레이션과 컨테이너 구성의 변경이 없다 | 없음 |
| 실제 확인(Task 5)에서 web 이미지만 다시 빌드했다. worker는 그대로다 | 마이그레이션이 없다. Docker VM이 2GB다 | worker의 코드는 이 계획에서 바뀌지 않았다 |
| 두 번째 프로젝트는 예제 `internal/ruleset/testdata/legacy-shop`을 작업 공간에 `legacy-shop-2`로 한 번 더 복사해 등록했다 | 전체 보기의 합을 보려면 프로젝트가 둘이어야 한다. 예제의 값은 모두 가짜다 | 없음. 확인이 끝난 뒤에도 개발 환경에 남아 있다 |
| 기간 필터는 `legacy-shop` 스캔의 `finished_at`을 잠시 30일 앞으로 옮겨 확인하고, 저장해 둔 원래 값으로 되돌린 뒤 같은지 대조했다 | 예제의 스캔이 모두 최근 7일 안에 끝나 있어 어느 기간을 골라도 같은 막대가 나왔다. 기다리거나 시계를 바꿀 수 없다 | 되돌린 값이 다르면 추이의 순서가 달라진다. 대조에서 같았다. 개발 환경의 데이터베이스에만 한 일이다 |

### 대시보드가 세는 것(0045)

| 정한 것 | 이유 | 틀렸을 때 |
|---|---|---|
| 건수는 묶음 수이고, 프로젝트의 마지막 성공한 스캔의 리포트 요약과 같은 함수(`readTotals`)로 센다. 남은 항목 = 미판정 + 보류 + 적용 대기(검토 항목 3) | 리포트와 대시보드의 숫자가 다르면 어느 쪽도 믿을 수 없다 | 리포트의 셈을 바꾸면 대시보드도 함께 바뀐다 |
| 증감은 지난 성공한 스캔과의 차이이고, 앞 스캔이 있는 프로젝트의 차이만 더한다(검토 항목 4) | 기간과 섞이지 않는 기준 하나를 두려고 | 기간 시작 대비 증감이 필요하면 따로 만든다 |
| 스냅숏 테이블을 만들지 않는다. 추이의 한 점은 그 스캔이 찾은 묶음 가운데 지금 오탐이 아닌 것의 수다(검토 항목 5) | 판정은 스캔이 끝난 뒤에 하므로 스캔 종료 시점의 수는 전부 미판정이다. 판정 이력은 묶음 옮기기 때문에 정확히 되감을 수 없다(0042) | 오탐으로 판정하면 지난 점도 바뀐다. 그때의 판정으로 본 추이가 필요하면 스캔별 건수를 저장한다 |
| 여러 프로젝트를 볼 때 막대는 그 스캔이 끝난 때의 "프로젝트마다 마지막 성공한 스캔의 수의 합"이다. 기간 전에 끝난 스캔은 막대가 되지 않지만 합에는 든다(검토 항목 6, 7) | 프로젝트마다의 수를 그냥 늘어놓으면 높이가 프로젝트 크기에 따라 오르내려 추이로 읽을 수 없다 | 새 프로젝트를 처음 스캔하면 합이 오른다. 화면이 그 스캔의 프로젝트 이름을 막대의 `<title>`과 표에 보인다 |
| 스캔의 순서는 (끝난 시각, 없으면 요청한 시각, 그다음 ID)다. "가장 새 점"과 앞 스캔은 ID로 고른다 | 성공한 스캔은 언제나 끝난 시각이 있고, 프로젝트 하나에 스캔이 한 번에 하나만 돈다. 두 규칙이 갈리지 않는다 | worker를 늘려 한 프로젝트의 스캔이 겹치면 갈릴 수 있다. 하나로 맞춘다(남은 일) |
| "오탐이 많은 규칙"은 마지막 성공한 스캔의 묶음을 규칙마다 세고, 한 묶음을 두 규칙이 찾았으면 둘 다에 센다. 비율은 내림한다(검토 항목 9) | 어느 규칙이 오탐을 냈는지는 묶음에 적혀 있지 않다. 찾은 규칙 모두가 후보다 | 규칙 하나의 오탐 수가 실제보다 많게 보일 수 있다 |
| 완료율 = 완료 ÷ (완료 + 남은 항목), 내림한 백분율, 분모가 0이면 "—"(검토 항목 10) | 100%는 남은 항목이 0일 때만 보여야 한다 | 식만 바꾼다 |
| 마이그레이션을 더하지 않았다 | 스캔 30개, 위치 36만 줄에서 분류별 수를 세는 쿼리가 150ms였다 | 느려지면 인덱스를 더한다 |

### 화면과 차트(0046)

| 정한 것 | 이유 | 틀렸을 때 |
|---|---|---|
| 차트 라이브러리를 넣지 않고 서버가 인라인 SVG로 그린다. 색은 `app.css`의 클래스로 준다(검토 항목 2) | 스크립트가 없어 CSP가 그대로이고, 숫자와 그림이 같은지를 Go 테스트로 붙잡으며, 고정할 버전이 늘지 않는다 | 확대나 범례 끄기가 필요해지면 라이브러리를 정적 파일로 넣는다. 자료를 만드는 `dashboard.Build`는 그대로 쓴다 |
| 눈금은 정수이고 1, 2, 5의 배수로 올린다. 막대의 이름은 스캔 번호(`#N`)다 | 묶음 수에는 소수가 없다. 시각은 막대 30개의 이름으로 쓰기에 길다 | 모양만 바뀐다 |
| 분류의 색 다섯 개를 새로 정해 `docs/design/README.md`에 적었다. 조각 사이의 1px 틈, 범례의 글자, `<title>`, 표를 함께 둔다(검토 항목 12) | 시안에는 판정의 색만 있다. 색만으로 구분하지 않게 하려고 | 색을 바꾼다. 클래스 다섯 개만 고치면 된다 |
| 차트는 너비 780px 아래로 줄지 않고, 그보다 좁은 화면에서는 `chart-scroll` 안에서 가로로 스크롤한다. 글자는 viewBox의 13단위다 | 실제 확인에서 390px 화면의 차트가 292px로 줄어 글자가 약 3.6px였다. 고친 뒤 390px과 800px에서 10.6px, 1280px에서 13.8px이다 | 좁은 화면에서는 처음에 가장 오래된 막대가 보인다. 가장 새 막대부터 보이게 하려면 스크립트나 다른 배치가 필요하다(남은 일) |
| 줄바꿈 금지(`table-nowrap`)는 대시보드의 표 셋에만 준다. 다른 표의 `.table th`는 그대로다 | 390px에서 규칙 표의 머리글이 글자마다 줄바꿈되었다. 모든 표에 주면 A4 폭에 맞춘 리포트 PDF의 모양이 바뀔 수 있고 그것을 이 계획에서 확인할 수 없다 | 다른 표에도 필요하면 그 표에 클래스를 준다 |
| 기간은 추이에만 적용하고 화면에 그렇게 적는다. 프로젝트 표는 언제나 모든 프로젝트를 보인다(검토 항목 7, 8) | 한 화면에 "지금"과 "그 기간"의 숫자가 섞이지 않게 | 기간 안의 증감과 규칙 통계가 필요하면 절을 더한다 |
| `project`와 `period`의 빈 값은 주지 않은 것으로 본다. 양의 정수가 아닌 `project`와 모르는 `period`는 400, 없는 프로젝트는 404다(검토 항목 11) | 양식의 "전체"가 빈 값을 보낸다 | 없음 |
| 프로젝트 표의 "마지막 스캔" 시각은 요청한 시각이다 | 이 칸은 성공하지 않은 스캔도 보이는데, 실패했거나 대기 중인 스캔에는 끝난 시각이 없다 | 추이의 끝난 시각과 다르게 보인다(예제의 #8은 18분). 표에 끝난 시각을 따로 보인다(남은 일) |

### 고치지 않고 넘긴 것

`docs/next-steps.md`의 "계획 7에서 남은 일"에 적었다.

## 이유

멈춰서 묻는 것보다 정하고 기록하는 편이 빠르고, 위의 결정은 대부분 고치는 데 드는 일이 작다. 대시보드는 새 자료를 만들지 않고 이미 있는 스캔과 판정을 세기만 한다. 그래서 숫자의 뜻을 리포트와 같게 두는 쪽을 골랐고, 그 값을 따로 저장하지 않았다. 저장하지 않은 것은 나중에 더할 수 있지만, 뜻이 다른 숫자 두 벌은 되돌리기 어렵다.

## 검토한 다른 방법

- **항목마다 사용자에게 묻는다**: 사용자가 하지 말라고 했다.
- **스캔이 끝날 때 건수를 저장한다**: 판정이 스캔 뒤에 오므로 저장한 수는 전부 미판정이고, 이미 있는 스캔은 같은 계산으로 채워야 한다(0045).
- **Chart.js나 uPlot을 정적 파일로 넣는다**: 상호작용을 얻지만 스크립트와 자료를 넘길 길이 늘고 그림을 테스트할 수 없다(0046).
- **좁은 화면에서 차트를 감추고 표만 보인다**: 차트가 있는 화면과 없는 화면의 내용이 달라진다. 스크롤은 같은 그림을 보인다.
- **주제별 결정 기록에만 적는다**: 무엇이 사용자 대신 정해졌는지 한눈에 볼 수 없다.
