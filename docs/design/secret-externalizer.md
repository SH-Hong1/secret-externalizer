# secret-externalizer 설계 문서

이 문서는 지금의 시스템을 설명한다. 결정의 경위와 이유는 `docs/adr/`의 결정 기록(ADR)에 있고, 문장 끝의 "(ADR NNNN)"이 그 기록을 가리킨다. 두 문서가 어긋나면 번호가 큰 ADR이 맞다. 띄우는 방법은 `docs/local-run.md`, 코드 규칙은 `AGENTS.md`, 달라진 내용은 `CHANGELOG.md`에 있다.

## 1. 배경과 범위

레거시 소스에 박혀 있는 민감 정보를 소스 밖으로 빼내는 프로젝트가 진행 중이다. secret-externalizer는 그 일을 하는 개발자의 작업 도구다. 개발자는 로컬에 있는 소스를 스캔하고, 찾은 값을 사람이 판정하고, 판정한 값을 placeholder로 바꾸고, 무엇을 어디서 뺐는지 기록으로 남긴다. 진행 상황은 리포트와 대시보드로 본다.

도구가 맡는 범위는 "찾고, 사람이 판정하게 하고, 소스에서 빼내고, 기록하는 것"까지다. 빼낸 값을 운영 비밀 저장소(AWS 등)에 넣는 일, 앱이 다시 기동되게 하는 일, 키를 폐기하고 다시 발급하는 일, 커밋하는 일은 개발자와 운영 담당자의 몫이다.

대상 소스는 다음과 같다.

- Java, Spring Framework 구버전(3 계열). 빌드는 Maven과 Ant, 배포는 ssh로 접속해 실행하던 셸 스크립트, 버전 관리는 git이다.
- EUC-KR(CP949)과 UTF-8, CRLF와 LF가 섞여 있다. 도구는 파일마다 인코딩을 판별해 탐지하고, 바꿀 때 원래 바이트의 인코딩과 줄바꿈을 그대로 둔다(ADR 0019).
- 민감 정보의 분류는 다섯이다: 제휴사 세션(`partner-session`), 저장소 접속 정보(`storage-credential`), SSH 접속 정보(`ssh-credential`), 기타 비밀 값(`other-secret`), 고객정보(`customer-data`).

| 파일 | 내용 | 처리 |
|---|---|---|
| `.java` | 문자열 리터럴 | 탐지, 치환(코드 수정 필요로 표시) |
| Spring XML, `.properties`, `application*.yml` | dataSource 등 설정 값 | 탐지, 치환 |
| `pom.xml`, `settings.xml`, `build.xml` | 저장소 계정, 배포 설정 | 탐지, 치환 |
| `.sh` | `ssh`, `scp`, `sshpass` 인자, `SSHPASS=` | 탐지, 치환(`EXT_` 표기) |
| 개인키, 인증서, 키 저장소 | 파일 전체 | 탐지, 파일 제거 |
| JSP, JSPF, JS, HTML, HTM | 하드코딩된 토큰 | 탐지만(외부화할 수 없다) |
| 로그, 샘플 데이터 | 고객정보 | 탐지, 마스킹 |

### 사용자

- 사용자는 외부화 프로젝트를 수행하는 개발자다. 주로 개발자 PC에서 docker compose로 띄워 쓴다. 마스킹되어 있어도 민감 정보를 다루므로 로그인을 요구한다.
- 프로젝트 하나는 한 사람이 맡는다. 여러 사람이 같은 프로젝트를 각자의 인스턴스로 나눠 작업하는 경우는 다루지 않는다.
- 로그인은 Keycloak OIDC이고 역할은 둘이다(ADR 0005).

| 역할 | 할 수 있는 일 |
|---|---|
| `user` | 프로젝트 등록, 스캔, 판정, 점검과 적용, 리포트와 PDF, 대시보드. 값은 가린 미리보기와 가린 주변 줄로만 본다 |
| `admin` | `user`의 모든 일, 원본 보기, 감사 로그(`/audit`) |

역할이 없는 계정은 로그인한 뒤 403을 본다.

## 2. 목표와 하지 않는 것

### 목표

1. 로컬 작업 공간의 소스에서 민감 정보를 탐지한다.
2. 찾은 값을 사람이 묶음 단위로 판정한다. 판정되지 않은 값은 소스에 반영되지 않는다(ADR 0004, 0027).
3. 판정한 비밀 값을 소스에서 빼고 `${ext.<이름>}`(셸은 `${EXT_<이름>}`) placeholder로 바꾼다. 고객정보는 `[REDACTED:<종류>]`로 가린다(ADR 0039).
4. 뺀 값은 OpenBao KV v2에 보관하고, 프로젝트 루트의 `secrets-manifest.yml`에 이름, 저장 경로, 위치를 기록한다(ADR 0034, 0035).
5. 스캔마다 리포트를 화면으로 보이고 PDF로 내보낸다(ADR 0042).
6. 대시보드에서 남은 항목, 완료율, 추이를 보인다(ADR 0045).
7. 판정, 옮기기, 적용 확인, 원본 보기를 감사 기록으로 남긴다.
8. 코드와 구조가 Go 모범사례의 본보기가 될 수준이다(`AGENTS.md`).

### 성공 기준

- 예제 프로젝트를 스캔하고 추천대로 판정해 적용한 뒤, 확인 스캔이 적용한 자리를 다시 찾지 않고 placeholder, 마스크, manifest의 줄을 새 항목으로 보고하지 않는다(ADR 0049).
- 외부화한 비밀번호, 토큰, 키, 기타 비밀 값이 적용이 건너뛴 자리가 없는 파일, 모든 테이블, worker 로그, manifest 어디에도 남지 않는다(ADR 0049).
- OpenBao에 저장된 값의 지문이 그 묶음의 지문과 같다(ADR 0032, 0070).
- 대시보드의 프로젝트 요약이 그 프로젝트의 마지막 성공한 스캔의 리포트 요약과 같다(ADR 0045).
- 위 네 가지를 통합 테스트 `TestIntegration_ScanApplyRescan`이 실제 스캐너, postgres, OpenBao, git으로 확인한다(5.2).

### 하지 않는 것

- 원격 저장소(GitHub 등)를 대상으로 한 스캔과 그 인증 토큰의 관리
- git 히스토리에 남은 값의 탐지와 제거
- AWS KMS, Secrets Manager 연동
- 치환 뒤 앱이 기동되는지 보장하는 일, 키 폐기와 재발급
- AI를 이용한 전수 검사와 판정 보조. 판정 단계는 "제안자"를 끼울 수 있게 두었다(ADR 0004)
- trivy 연동(ADR 0002)
- 프론트엔드 파일(JSP, JS, HTML)의 토큰 자동 치환. 탐지와 리포트만 한다
- 도구가 대신 커밋하는 일, 저장소를 바꾸는 git 명령의 실행
- 서로 다른 파일의 같은 값을 자동으로 나누거나, 키만 다른 같은 비밀을 자동으로 합치는 일(ADR 0053, 0063)

### 실패로 보는 것

동작하더라도 다음 중 하나가 생기면 실패다.

- 비밀 값의 원본이 postgres, valkey, 로그, 오류, 리포트, PDF, manifest, 세션 어디에든 평문으로 남는다.
- 사람의 판정과 적용 확인 없이 소스가 바뀐다.
- 소스에서 값이 지워졌는데 OpenBao에는 저장되지 않아 값이 사라진다.
- 고객정보의 사본이 도구 안에 새로 생긴다.
- 커밋되지 않은 변경이 있는 추적 파일을 도구가 덮어쓴다.
- 스캐너가 소스를 바꾸거나 외부화한 값을 읽을 수 있다(ADR 0068, 0069).

## 3. 설계

### 3.1 개요

하나의 Go 모듈에서 바이너리 둘(`cmd/web`, `cmd/worker`)을 만든다. web과 worker는 postgres의 작업 큐로만 연결된다(ADR 0001, 0016). worker 이미지는 두 서비스로 뜬다. `worker`는 스캔만, `applier`는 적용의 점검과 적용만 한다(ADR 0068).

```
브라우저 ── web ──┬─ postgres  (프로젝트, 스캔, 항목, 묶음, 적용 기록, 작업 큐, 감사 기록)
                  ├─ valkey    (세션, 로그인 시도)            TLS, ACL 사용자 se-web
                  ├─ keycloak  (OIDC 로그인, 역할)
                  ├─ openbao   (admin의 원본 보기, 읽기만)     TLS, AppRole se-web
                  └─ pdf       (리포트 HTML → PDF)

worker  (WORKER_JOBS=scan)  ─┬─ postgres (작업 수신, 결과 저장)
                             ├─ openbao  (지문, 원본 보관과 정리)   AppRole se-worker
                             ├─ /workspace (읽기 전용)
                             └─ betterleaks, opengrep, 키 파일 탐지기, git(읽기)

applier (WORKER_JOBS=apply) ─┬─ postgres (점검, 적용 기록)
                             ├─ openbao  (외부화 값 쓰기와 읽기)    AppRole se-applier
                             ├─ /workspace-rw (읽기-쓰기)
                             └─ git(읽기)
```

| 구성 요소 | 하는 일 |
|---|---|
| web | HTTP 서버와 화면, 로그인, 판정과 옮기기 기록, 스캔·점검·적용 요청, 리포트와 PDF 요청, 대시보드, admin의 원본 보기. 소스 마운트와 스캐너가 없다 |
| worker | `scan` 작업을 실행한다. 작업 공간을 읽기 전용으로만 받고, 스캐너를 실행하고, 지문을 계산하고, 원본을 OpenBao `pending/`에 보관하고 결과를 저장한다. 적용 뒤의 확인 스캔도 스캔이므로 worker가 한다 |
| applier | `apply-check`와 `apply` 작업을 실행한다. 작업 공간을 읽기-쓰기로 받는 유일한 서비스이고, 스캐너를 실행하지 않는다 |
| pdf | Gotenberg(Chromium). web이 보낸 완성된 리포트 HTML을 PDF로 바꾼다. 바깥과 다른 서비스에 닿지 못한다(ADR 0006, 0043) |
| OpenBao | 지문용 HMAC(transit 키 `fingerprint`), 판정 전 원본(`secret/data/pending/<프로젝트>/<지문>`), 외부화한 값(`secret/data/projects/<프로젝트>/ext.<이름>`)을 둔다(ADR 0003, 0035) |
| postgres | 업무 데이터, 작업 큐, 마이그레이션 기록. Keycloak의 데이터베이스와 테스트용 데이터베이스를 같은 인스턴스에 따로 둔다 |
| valkey | 서버 쪽 세션과 로그인 시도. 디스크에 저장하지 않는다(ADR 0013, 0066) |
| Keycloak | OIDC 로그인과 역할. realm, client, 개발용 계정을 기동할 때 import 파일에서 읽는다(ADR 0005) |
| openbao-secrets, valkey-secrets, openbao-roles | 한 번 실행되고 끝나는 준비 서비스. secret-id, TLS 인증서, ACL 파일을 만들고, 역할과 정책을 파일대로 맞춘다(ADR 0066, 0067, 0069) |

스택은 Go(`net/http`의 `ServeMux`, `log/slog`), `html/template`, htmx 2.0.11, tailwindcss 4 standalone CLI(ADR 0025), pgx(ADR 0015), valkey-go(ADR 0011), go-oidc와 oauth2(ADR 0010), OpenBao 공식 Go 클라이언트(ADR 0018), errgroup(ADR 0008)이다. 차트 라이브러리는 쓰지 않는다(ADR 0046).

### 3.2 사용 흐름

```
프로젝트 등록 → 스캔 → 판정 → 점검 → 적용 → 확인 스캔 → 리포트/PDF → 대시보드
```

1. **프로젝트 등록.** 이름(1~100자, 제어 문자와 깨진 UTF-8은 거부), 작업 공간 루트 기준 상대 경로, 제외 경로를 받는다. 경로와 제외 경로는 NUL을 포함한 제어 문자를 거부한다. worker와 applier는 쓸 때마다 경로를 심볼릭 링크까지 풀어 작업 공간 루트 안인지 확인한다(`project.Resolve`).
2. **스캔.** 프로젝트 화면에서 사람이 요청한다(`POST /projects/{id}/scans`). web은 `scan`과 `job`을 한 트랜잭션에 넣고, worker가 가져가 실행한다. 한 프로젝트에서 스캔과 적용은 겹치지 않는다(ADR 0036). 스캔 화면은 상태, 찾은 파일 수, 건너뛴 파일과 스캐너 오류 수("검사하지 못한 것"), 버린 건수를 보인다(ADR 0030).
3. **판정.** 판정 화면(`/projects/{id}/triage`)은 마지막으로 성공한 스캔이 찾은 묶음을 목록과 상세로 보인다. 사람이 묶음마다 판정과 이름을 정하고, 항목을 다른 묶음으로 옮기거나 묶음 전체를 합친다(3.5).
4. **점검.** 적용 화면에서 점검을 요청하면 applier가 소스를 바꾸지 않고 조건과 계획을 확인해 실행을 `ready`나 `blocked`로 닫는다. 화면은 바꿀 자리, 건너뛸 자리와 사유, "복구 불가" 파일을 보인다(ADR 0036).
5. **적용.** 사람이 점검 결과를 확인하면 applier가 처음부터 다시 확인하고 OpenBao 저장, 소스 치환, manifest 기록 순으로 실행한다(3.6).
6. **확인 스캔.** 적용한 자리가 하나라도 있으면 실행을 닫는 트랜잭션이 스캔을 하나 넣는다. worker가 실행하고, 적용 결과 화면과 스캔 화면은 외부화한 묶음의 값이 다시 발견되었는지 보인다(ADR 0040).
7. **리포트와 PDF.** 성공한 스캔마다 리포트(`/scans/{id}/report`)를 열 때마다 만들고, PDF(`/scans/{id}/report.pdf`)로 내보낸다(ADR 0042).
8. **대시보드.** `/dashboard`가 모든 프로젝트의 지금 상태와 스캔별 추이를 보인다(ADR 0045).

개발자는 적용 뒤 `git diff`로 바뀐 것을 확인하고 직접 커밋한다. 되돌릴 때도 git을 쓴다.

### 3.3 스캔

#### 대상 파일

- 현재 작업본의 파일을 대상으로 한다. git이 추적하지 않는 파일과 `.gitignore` 대상도 포함한다. 로그, 샘플 데이터, 개인키가 주로 거기 있기 때문이다.
- `.git/`, `target/`, `build/`, `node_modules/`는 언제나 제외하고, 프로젝트의 제외 경로를 더한다. 제외 경로는 스캐너에 넘기지 않고, 실행기가 만든 파일 목록에 없는 파일의 결과를 버리는 것으로 지킨다(ADR 0020, 0021).
- 프로젝트 폴더 맨 위에 `.gitleaksignore`나 `.betterleaksignore`가 있으면 스캐너를 실행하지 않고 정해진 사유로 실패한다. betterleaks가 그 파일에 적힌 결과를 숨기기 때문이다(ADR 0021).
- 파일은 `textfile`의 여는 코드 하나로 읽는다. 폴더를 `os.Root`로 열고, `Lstat`으로 일반 파일인지 본 뒤 `O_NOFOLLOW|O_NONBLOCK`으로 열어 같은 파일인지 다시 확인한다. 걷기와 읽기 사이에 링크나 FIFO로 바뀐 파일은 건너뛴다(ADR 0058).
- 20MiB를 넘는 파일, 바이너리, UTF-8도 EUC-KR도 아닌 파일, 읽을 수 없는 파일, 경로가 UTF-8이 아니거나 제어 문자가 든 파일은 텍스트로 스캔하지 않고 건너뛴 수에 센다. 건너뛴 경로는 처음 200개만 저장한다(ADR 0021, 0030). 키 저장소(`.jks`, `.p12` 등)는 바이너리라도 키 파일 항목이 된다.

#### 인코딩

인코딩은 UTF-8 BOM, UTF-16 BOM(거부), 앞 8,000바이트의 NUL(바이너리), 전체 UTF-8 검사, `x/text`의 `korean.EUCKR`(CP949) 변환 순으로 판별한다(ADR 0019). EUC-KR 파일은 UTF-8 사본을 worker의 임시 폴더(`<임시 폴더>/<스캔 ID>/`, tmpfs)에 같은 상대 경로로 두고 스캐너가 사본 폴더도 스캔한다. 이 사본은 도구가 스캔 대상의 내용을 복사하는 유일한 경우이고 스캔이 끝나면 지운다(ADR 0021, 0023). 파일의 해시는 BOM과 줄 끝을 포함한 디스크 바이트의 SHA-256이다.

#### 스캐너

스캐너는 버전과 체크섬을 `deploy/worker/scanners.lock`에 고정해 worker 이미지에 넣고, `internal/scanexec`가 `exec.CommandContext`와 인자 슬라이스로 실행한다. 환경 변수는 `PATH`, `HOME`, `TMPDIR`만 넘기고, 표준 출력은 메모리로만 받으며(256MiB 한도), 표준 오류는 버린다. 스캐너는 자기 프로세스 그룹에서 돌고 끝나면 그룹을 정리한다. 오류에는 도구 이름과 종료 코드, 정해진 사유만 담는다(ADR 0002, 0020).

| 탐지기 | 찾는 것 |
|---|---|
| betterleaks | 기본 규칙(키, 토큰, 비밀번호 등 알려진 형식), 제휴사 세션(쿠키, Bearer 토큰), 고객정보(전화번호, 주민·외국인등록번호, 이메일, 카드번호, 주소). 고객정보 규칙은 고객정보 경로에만 적용한다 |
| opengrep | 문맥으로 찾는 것. Spring XML의 dataSource, `.properties`와 `application*.yml`의 접속 정보, Java 문자열 리터럴 대입, 셸의 ssh 인자, Maven과 Ant의 비밀번호 |
| 키 파일 탐지기(`internal/keyfile`) | 이름(`id_rsa` 등), 확장자(`jks`, `p12`, `pfx`, `keystore`, `ppk`), 앞 4KiB의 PEM 머리 줄로 찾은 파일 전체 |

- 규칙은 `rules/`(`betterleaks.toml`, `opengrep/*.yml`)에 있고, 규칙마다 분류와 종류를 적는다. 규칙은 값만 잡고 따옴표, 키 이름, 태그는 범위에 넣지 않는다. 규칙 버전은 `rules/` 아래 파일의 이름과 내용으로 계산한다.
- 고객정보 경로는 확장자가 `log`, `out`, `csv`, `tsv`, `txt`, `sql`, `dat`, `json`인 파일, 회전된 로그(`app.log.1`, `catalina.out.2` 등), 어느 깊이든 `log`, `logs`, `sample`, `samples`, `data`, `dump` 폴더 아래의 파일이다. Go의 `finding.CustomerDataPath`와 규칙의 `path`가 같은지 규칙 테스트가 확인한다(ADR 0021, 0024).
- 알려진 누락과 오탐 가운데 고친 것과 남은 것은 ADR 0052에 있다.

#### 자리 정하기

- betterleaks 결과는 `Match` 안에서 `Secret`이 처음 나오는 곳으로 줄과 열을 옮기고, 그 자리의 바이트가 값과 같아야 한다. opengrep 결과는 범위가 텍스트 안이고 글자 경계여야 한다. 아니면 버리고 `Dropped`에 센다(ADR 0020, 0021).
- 결과가 있는 파일은 다시 읽어 목록을 만들 때의 해시와 다르면 그 파일의 결과를 모두 버린다.
- 디코딩해서 찾은 결과(base64, hex, 퍼센트)는 파일에 적힌 인코딩된 글자를 항목의 값으로 한다. 스캔이 그 구간을 직접 풀어 `Secret`이 나올 때만 자리로 삼고, 확인 과정에서 만드는 글은 결과 하나에 16MiB까지다. 확인하지 못한 결과와 고객정보 규칙의 디코딩 결과는 버린다. 탐지 기록에 인코딩을 남기고 판정 화면은 "(base64 디코딩)"처럼 보인다(ADR 0071).
- 종류가 `url`인 결과는 `internal/connstr.Split`이 구성 요소(호스트, 포트, 계정, 비밀번호)로 나눈다. 나뉜 URL은 URL 항목을 남기지 않는다. DB 이름, 경로, 그 밖의 매개변수는 구성 요소가 아니다(ADR 0026).
- 값 전체가 `${…}`나 `#{…}` 자리 표시자 하나인 결과, 구성 요소가 모두 자리 표시자인 URL은 항목으로 만들지 않는다. 적용이 써넣은 placeholder를 다음 스캔이 새 비밀로 보고하지 않게 하려는 것이다(ADR 0026, 0052).

#### 지문과 원본

- 지문은 OpenBao transit 키 `fingerprint`로 계산한 HMAC이다. 짧은 비밀번호도 역산할 수 없다. 키는 모든 프로젝트가 함께 쓰고 회전하지 않는다(ADR 0003, 0017). 요청은 값 500개 또는 바이트 합 8MiB에서 나눈다(ADR 0035).
- 지문을 만드는 값은 UTF-8 텍스트의 그 범위이고, 키 파일은 디스크의 원래 바이트 전체다.
- 고객정보가 아닌 항목의 원본은 지문마다 한 번 `pending/`에 보관한다. admin의 원본 보기에 쓰고, 적용의 근거로는 쓰지 않는다(ADR 0028, 0032).
- 모든 묶음이 오탐인 지문(`SettledFingerprints`)의 원본은 보관하지 않는다. 이 목록은 마지막 성공한 스캔이 구성원을 찾은 묶음만 센다. 목록을 읽지 못하면 모든 원본을 보관하고 스캔은 계속한다(ADR 0040, 0054).
- 결과를 저장한 뒤에만 이번 결과에 없는 지문의 원본을 지운다. 값 하나를 지우기 직전마다 같은 프로젝트에 더 새 스캔이 있는지 확인하고, 있거나 확인하지 못하면 멈춘다(ADR 0021, 0060).
- 원래 값은 스캔 동안 worker 메모리에만 있고, 키 파일의 바이트는 보관한 뒤 0으로 지운다.

#### 주변 줄과 미리보기

- 주변 줄은 비밀 값 항목의 자리 앞뒤 몇 줄이다. 그 파일에서 자리를 정한 모든 값, 자리를 정하지 못한 결과의 값, 그 스캔이 어느 파일에서든 찾은 4바이트 이상의 값이 이 파일에 나오는 모든 자리를 `****`로 가린 뒤 저장한다. 그 뒤 제어 문자와 깨진 UTF-8을 `U+FFFD`로 바꾸고 줄을 200글자로 자른다(ADR 0021).
- 다음 파일에는 어느 항목에도 주변 줄을 만들지 않는다: 자리를 정하지 못한 결과가 있는 파일, 스캐너가 스스로 결과를 버린 파일, 키 파일 탐지기가 파일 전체로 보고한 텍스트 파일, 고객정보 경로의 파일, 고객정보 규칙의 결과가 나온 파일(ADR 0021).
- 미리보기는 `finding.Preview`가 만든다. 8글자 이상인 비밀 값은 앞 4글자와 `****`, 짧은 값과 개인키, 키 파일은 `****`만이다. 고객정보는 고정된 형식 문자열이고 전화번호만 맨 앞 숫자 묶음을 남긴다(ADR 0023).
- 주변 줄은 저장된 그대로 `user`에게도 보인다. 규칙이 잡지 못한 텍스트가 소스 파일의 주변 줄에 남을 수 있다는 위험을 받아들인다(ADR 0028).

#### 저장

- 한 스캔의 결과는 `SaveResult`가 작업을 닫는 트랜잭션 안에서 저장한다. 임대를 확인하고, 프로젝트 행을 `FOR NO KEY UPDATE`로 잠가 판정·옮기기와 서로 기다리게 한다(ADR 0021, 0056).
- 저장은 읽기, 계획, 쓰기의 세 단계다. 프로젝트의 항목과 `shared`·`frontend` 묶음을 한 번 읽고, 메모리에서 항목마다 이어 쓸 줄과 들어갈 묶음을 정한 뒤, 1000줄씩 한 문장으로 쓰고 위치는 `COPY`로 넣는다(ADR 0057).
- 다시 찾은 항목은 ID와 첫 스캔을 유지하고 마지막 스캔, 분류, 종류, 미리보기, `has_original`을 이번 스캔의 것으로 바꾼다. 위치는 스캔마다 새로 넣는다.
- 스캔 하나의 제한 시간은 30분이다. 커밋 해시는 `worktree.CommitHash`로 읽고, 실패하면 비운다(ADR 0021, 0033).
- 실패 사유는 정해진 문구뿐이다(예: `the secret store could not be reached; see the worker log`). 원인 오류는 worker 로그에 한 번 남는다.

### 3.4 항목, 묶음, 설정 키

#### 항목

항목(`finding`)은 한 프로젝트에서 "지문, 파일 경로, 설정 키"가 같은 값이다. 한 항목은 위치(`location`)를 여럿 가질 수 있다. 같은 파일 안에서 같은 값이 키가 같거나 키를 읽지 못한 자리에 여러 번 나오면 위치가 여럿인 항목 하나다(ADR 0053). 항목의 분류는 검출 가운데 `storage-credential`, `ssh-credential`, `partner-session`, `customer-data`, `other-secret` 순으로 앞의 것이고, 검출(도구, 규칙, 인코딩)은 모두 남긴다(ADR 0021, 0071).

#### 설정 키

키는 값이 대입된 설정의 이름이고, 스캔이 파일 원문에서 읽는다(`internal/scan`의 `configKey`, ADR 0053).

| 파일 | 키 | 예 |
|---|---|---|
| YAML | 들여쓰기가 더 얕은 위쪽 키를 `.`으로 이은 경로. 목록 항목에서 끊는다 | `spring.datasource.live.password` |
| XML | 요소의 `name="…"`, 없으면 속성 이름이나 요소 이름. 값의 자리에서 열려 있는 가장 가까운 `<bean id="…">`의 `id`를 앞에 붙인다 | `liveDataSource.password` |
| 그 밖 | 같은 줄에서 값 바로 앞의 대입(`=`, `:`)의 이름, 없고 호출의 인자이면 `(` 앞의 이름 | `live.db.password`, `setPassword` |

- 키는 ASCII 글자, 숫자, `.`, `_`, `-`만 쓰고 200바이트까지다.
- 값이 두 줄 이상이거나 파일 전체 결과, 고객정보, 주변 줄을 저장하지 않는 파일, 키를 읽은 범위가 가리는 범위와 겹치는 경우, 이름을 찾지 못한 경우에는 키가 비어 있다. 비밀 값이나 그 일부가 키로 DB에 들어가지 않게 하려는 것이다.
- 나눈 URL의 구성 요소는 모두 그 URL이 대입된 키를 받는다.

#### 묶음

판정, 보류 사유, 메모, placeholder 이름은 묶음(`bundle`)에 붙는다. 묶음은 한 프로젝트 안에서 지문이 같은 항목의 모음이다(ADR 0027). 새 항목이 들어갈 묶음은 다음 규칙으로 정하고, 이미 저장된 항목의 묶음은 다시 스캔해도 바뀌지 않는다.

| 항목 | 묶음 |
|---|---|
| 값이 고유한 종류(비밀번호, 토큰, URL, 개인키, 키 파일, 기타) | 지문의 `shared` 묶음. 단, 그 묶음에 같은 파일의 키가 다른 항목이 이미 있으면 자기만의 `own` 묶음 |
| 프론트엔드 파일(JSP, JSPF, JS, HTML, HTM)의 항목 | 프론트엔드 파일끼리 지문마다 `frontend` 묶음(위와 같은 키 규칙) |
| 호스트, 포트, 계정 | 항목마다 `own` 묶음 |
| 고객정보 | 항목마다 묶음 하나. 목록에서는 같은 파일, 종류, 판정의 묶음을 한 줄로 모아 한 번에 판정한다 |

- 그래서 한 파일의 `local.db.password`, `dev.db.password`, `live.db.password`에 같은 값이 있으면 묶음 셋으로 시작하고 추천 이름도 따로 나온다. 다른 파일의 같은 값은 `shared` 묶음으로 모인다(ADR 0053).
- 지문, 파일이 같고 저장된 항목이 키 없는 것 하나뿐이며 이번 스캔이 그 항목을 아직 찾지 않았으면, 키 있는 새 자리가 그 항목(과 묶음, 판정, 이름, 적용 기록)을 이어 쓴다(ADR 0053, 0057).
- **옮기기.** 항목은 지문이 같은 다른 묶음이나 새 묶음으로 옮길 수 있다. 고객정보와 비밀 값 사이, 지문이 다른 묶음 사이로는 옮길 수 없고, 고객정보 항목은 옮길 수 없다. 옮긴 뒤의 묶음이 지금 판정을 허용하지 않으면 옮기지 않는다. 비어 버린 묶음은 지우고 그 이름은 풀린다(ADR 0027).
- **합치기.** 같은 값의 다른 묶음이 있으면 상세에 "이 묶음 전체 합치기"가 보인다. 묶음에 저장된 모든 항목을 한 트랜잭션에서 옮기고, 하나라도 거부되면 아무것도 옮기지 않는다. 같은 비밀인지는 사람이 정한다(ADR 0063).
- 판정과 옮기기의 허용 규칙은 마지막 성공한 스캔이 찾은 구성원만으로 확인한다. 판정 화면이 보이는 구성원과 같다. 마지막 스캔이 구성원을 하나도 찾지 못한 묶음은 판정할 수 없다(ADR 0027).

#### 이름

이름은 접두어 없이 소문자로 시작하는 마디 2~5개를 `.`으로 이은 100바이트 이하의 문자열로 저장하고(`db.main.password`), 첫 마디가 `ext`인 이름은 받지 않는다. 프로젝트 안에서 묶음마다 다르다(`UNIQUE (project_id, name)`). 소스에는 파일 종류에 따라 `ext.db.main.password`(설정, XML, Java)나 `EXT_DB_MAIN_PASSWORD`(셸)로 쓴다(ADR 0027).

추천 이름은 `분류.환경.대상.항목`이다. 환경은 묶음의 모든 파일 경로가 같은 환경(`prod`, `stg`, `uat`, `qa`, `test`, `dev`, `local`)을 가리킬 때만 넣고, 대상은 첫 구성원의 저장된 키에서, 키가 없으면 가린 주변 줄에서 읽는다. 가린 글자가 섞인 키에서는 대상을 `main`으로 한다(ADR 0031, 0048, 0053).

### 3.5 판정

| 판정 | 값 | 고를 수 있는 묶음 | 적용 때 |
|---|---|---|---|
| 외부화 | `externalize` | 비밀 값 묶음. 구성원이 프론트엔드 파일에 있으면 안 된다 | OpenBao 저장, placeholder 치환 또는 파일 제거, manifest 기록 |
| 삭제·마스킹 | `redact` | 고객정보 묶음 | `[REDACTED:<종류>]`로 가린다. 저장하지 않는다 |
| 오탐 | `false-positive` | 모두 | 없음. 원본을 보관하지 않게 된다 |
| 보류 | `hold` | 모두 | 없음. 사유는 `structure-change`(구조 변경 필요), `needs-confirmation`, `later` 가운데 하나다 |
| 미판정 | (빈 값) | 모두 | 없음. 판정을 취소하면 이 상태로 돌아간다 |

- 이름은 외부화에만, 보류 사유는 보류에만 있다. 메모는 모든 판정에 남길 수 있다(ADR 0027).
- 규칙 기반 제안을 한다. 같은 지문에 과거 판정이 있으면 그 판정과 보류 사유를 미리 채우고 이름은 지금 묶음에서 새로 만든다. 없으면 비밀 값은 추천 이름, 프론트엔드 묶음은 "보류: 구조 변경 필요"를 채우고 고객정보에는 제안이 없다(ADR 0004, 0048, `triage.Default`, `triage.Adapt`).
- 판정은 판정 버튼을 눌러야만 저장된다. 판정 값이 없는 요청은 400이다(ADR 0031).
- 판정과 옮기기는 한 트랜잭션에서 프로젝트 행을 `FOR SHARE`로, 그다음 묶음을 잠그고, 허용 규칙을 확인하고, 바꾸고, `audit_event`에 기록한다. 기록의 `detail`에는 판정, 보류 사유, 이름, 메모, 옮겨 간 묶음 ID만 들어간다(ADR 0027, 0036).
- 점검이나 적용이 걸려 있으면(`checking`, `queued`, `running`) 저장소가 판정과 옮기기를 거부하고(409), 판정 화면은 상세를 잠근다(ADR 0036, 0051).
- 적용한 외부화 묶음의 판정과 이름은 고정된다. 메모만 바꿀 수 있다. 그 묶음에서 옮길 수 있는 항목은 마지막 스캔이 여전히 찾았고, 묶음의 마지막 항목이 아니며, 적용했거나 쓰던 기록이 없는 것뿐이다(ADR 0036).

#### 판정 화면

- 목록과 상세 두 칸이다. 목록에서 묶음을 누르면 htmx가 상세를 바꿔 끼운다. 모든 링크와 양식은 htmx 없이도 쪽 전체 요청으로 동작한다. 목록은 한 쪽에 50줄이고 분류와 상태로 거른다(ADR 0025).
- 상세는 분류, 종류, 검출(도구, 규칙, 인코딩), 구성원마다 파일, 설정 키, 줄, 가린 주변 줄, 추천 이름과 이전 판정 안내를 보인다. 고객정보는 종류, 파일, 줄 번호, 같은 파일 안의 건수만 보인다.
- htmx 요청이 4xx, 5xx로 실패하면 오류 화면을 바꿔 넣는다. 세션 없이 온 htmx GET은 401과 `HX-Redirect`로 로그인에 보낸 뒤 누르려던 주소로 돌아온다(ADR 0055).

#### 원본 보기

값이 화면에 나오는 곳은 하나다. `admin`이 비밀 값 묶음의 "원본 보기"를 누른 요청의 응답이다(ADR 0028).

- `POST /projects/{id}/bundles/{bundle}/original`이다. 교차 출처 보호를 받고, 값은 주소, 쿼리, 리다이렉트에 들어가지 않는다.
- 감사 기록(`reveal`, 사용자, 프로젝트, 묶음)을 먼저 남기고 그다음 OpenBao `pending/`에서 읽는다. 기록이 실패하면 읽지 않는다. 읽지 못해도 시도는 기록에 남는다.
- 값은 그 handler와 응답을 그리는 버퍼에만 있다. `bao.Value`는 모든 출력 형식에서 `[redacted]`이고 `Reveal`로만 바이트를 꺼낸다. 모든 응답은 `Cache-Control: no-store`다. 텍스트가 아닌 값은 "텍스트가 아닌 원본입니다. N바이트."만 보인다.
- 버튼은 마지막 성공 스캔이 원본을 보관한 구성원이 있는 비밀 값 묶음에만 보인다. 원본이 없고 적용되지 않은 묶음은 그 이유를 보인다(ADR 0055).
- 외부화한 값은 화면에서 다시 볼 수 없다. 화면은 저장 경로만 보인다.

### 3.6 적용

#### 점검과 확인

- 점검 요청(`POST /projects/{id}/apply/check`)은 `apply_run`을 `checking`으로 넣고 `apply-check` 작업을 만든다. 그 프로젝트의 앞선 `ready`, `blocked` 실행은 `superseded`가 된다. 화면이 버튼을 내놓지 않는 조건(스캔이나 적용이 진행 중, 새 스캔이 있음, 적용할 판정이 없음)이면 서버도 409로 거부한다(ADR 0036, 0041).
- applier는 소스를 바꾸지 않고 조건과 계획을 확인해 실행을 `ready`나 `blocked`로 닫고, 바꿀 자리와 건너뛸 자리, "복구 불가" 파일 목록을 실행에 남긴다.
- 계획 지문(`plan_digest`)은 스캔 ID, 대상 묶음(ID, 판정, 이름, 구성원, 위치, 파일 해시), 고객정보 위치로 만든 SHA-256이다. 값은 들어가지 않는다(ADR 0036, 0039).
- 적용 확인(`POST /projects/{id}/apply`)은 보낸 지문이 실행의 지문과 지금 계획의 지문 모두와 같을 때만 실행을 `queued`로 바꾸고 `apply` 작업과 감사 기록(`apply`)을 한 트랜잭션에 넣는다. 판정이 바뀌었으면 `ErrPlanChanged`, 점검한 뒤 새 스캔이 있으면 `ErrScanFollowed`이고 화면은 둘을 다른 문장으로 알린다(ADR 0036, 0051).
- "복구 불가" 동의는 점검이 그런 파일을 보여 준 실행에서만 센다(ADR 0051).

#### 막는 조건

applier는 점검 결과를 믿지 않고 실행할 때 처음부터 다시 본다. 다음 가운데 하나라도 있으면 OpenBao와 대상 파일을 건드리지 않고 정해진 사유로 실패한다(ADR 0032, 0033, 0039, 0049).

- 프로젝트 폴더가 git 작업본이 아니거나 커밋이 없다. git이 없다.
- 추적되는 파일에 커밋되지 않은 변경이 있다(assume-unchanged, skip-worktree, 병합 중 포함).
- 위험한 git 설정(`filter.*.clean`, `filter.*.process`, `hook.*`, `core.worktree`)이 있다. git이 보고한 경로가 폴더 밖이나 `.git`을 가리킨다.
- manifest를 읽을 수 없다.
- 점검한 스캔이 그 프로젝트의 가장 새 스캔이 아니다(`scan-not-latest`).
- 파일을 읽은 뒤에도 바꿀 자리와 manifest를 기다리는 적용 항목이 없다(`nothing-to-apply`).

git은 `internal/worktree`가 읽기만 하는 명령으로 부른다. 시스템·전역 설정, pager, hook, fsmonitor, 원격 전송, 지연 가져오기를 모두 끄고, 작업 공간 위의 저장소를 찾지 않으며, 호출마다 60초 제한을 건다(ADR 0033).

#### 계획

- 판정이 `externalize`, `redact`이고 마지막 성공한 스캔이 구성원을 찾은 묶음만 대상이다. 묶음마다 허용 규칙을 다시 확인해 지금 허용되지 않으면 `not-allowed`로 건너뛴다(ADR 0039).
- 비밀 값은 `${ext.<이름>}`(`.sh`는 `${EXT_<이름>}`)로 바꾸고 `secret/data/projects/<프로젝트 ID>/ext.<이름>`에 저장한다. 한 묶음이 `.yml`과 `.sh`에 걸쳐도 저장 경로는 하나다(ADR 0035).
- Java 문자열 리터럴 안의 값은 리터럴 안에서 `${ext.…}`로 바뀐다. 이 상태로는 동작하지 않으므로 리포트에 코드 변경이 필요하다고 표시한다.
- 키 파일 전체 대상: 고객정보가 있을 수 있는 파일은 `key-holds-customer-data`, 소스·설정 파일 확장자는 `key-in-source-file`로 건너뛴다. 키 저장소·인증서 확장자와 `id_*` 이름은 대상이고, 그 밖은 내용이 PEM 블록뿐일 때만 지운다(ADR 0039).
- 같은 파일에서 범위가 겹치는 두 위치는 `overlap`, 고객정보 위치와 겹치는 비밀 값은 `holds-customer-data`로 건너뛴다. 고객정보 항목을 오탐으로 판정하면 풀린다(ADR 0039).
- 하위 폴더의 다른 저장소(`nested-repository`), 16MiB를 넘는 값(`too-large`), 스캔 뒤에 바뀐 파일(`file-changed`), 다시 읽은 값의 지문이 다른 자리(`value-mismatch`)도 건너뛴다(ADR 0032, 0035).
- 추적되지 않는 파일의 비밀 값은 그대로 적용한다. 원본이 OpenBao에 남기 때문이다. 추적되지 않는 파일의 고객정보 마스킹은 되돌릴 수 없으므로 점검 화면에 "복구 불가"로 따로 보이고 동의를 받은 실행에서만 가린다(`untracked-irreversible`, ADR 0032, 0036).

#### 저장할 값

적용은 소스의 글자가 아니라 그 글자가 뜻하는 값을 저장한다(ADR 0070).

- `internal/literal`이 확장자로 문법을 고르고, 줄 처음부터 자리 앞까지를 읽어 따옴표 상태를 정한 뒤 푼다. `.properties`, `.xml`, `.yml`·`.yaml`, `.java`, `.sh`, `.json`의 이스케이프를 다룬다. 그 밖의 파일과 키 파일은 글자 그대로다.
- 글자만으로 값을 정할 수 없으면(셸의 `$` 확장, 파일 밖 XML 엔티티, 정의되지 않은 이스케이프, 줄바꿈이 든 값 등) `value-unclear`, 한 저장 키의 자리들이 서로 다른 값으로 풀리면 그 키의 모든 자리를 `values-differ`로 건너뛴다. 비교는 `subtle.ConstantTimeCompare`다.
- 디코딩해서 찾은 항목의 값은 인코딩된 글자이고, 애플리케이션이 지금처럼 스스로 푼다(ADR 0071).

#### 실행 순서

조건 점검 → 저장 단계(저장 키마다 한 번) → 치환 단계(파일마다 한 번) → manifest → 실행 닫기 → 오탐 원본 정리 순이다(ADR 0032).

1. **맞추기.** 시작할 때 열린 파일 기록을 읽어 디스크의 해시와 맞추고 기록된 임시 파일을 지운다. 이미 바꾼 파일은 적용된 것으로 센다.
2. **다시 확인.** 대상 파일마다 지금 해시가 스캔 때 해시인지 보고, 저장된 위치에서 값을 다시 읽어 지문을 다시 계산한다. `pending/`의 원본은 근거로 쓰지 않는다.
3. **저장.** 저장 키마다 경로를 읽어 같은 값이면 쓰지 않고, 없거나 다르면 check-and-set(`cas`)으로 쓴다. 쓴 뒤 다시 읽어 버전과 지문이 맞을 때만 그 키의 위치가 치환 목록에 든다. 쓰기는 많아야 두 번이다. 저장하지 못한 위치는 `store-failed`, `write-failed`이고 소스는 그대로다(ADR 0032, 0035).
4. **치환.** 파일마다 `BeginFile` 기록 → 같은 폴더의 임시 파일(`<이름>.se-apply-<16자리>.tmp`)에 쓰고 `Sync` → `rename` 직전에 대상을 다시 확인하고 `rename` → 부모 폴더 `Sync` → `EndFile` 기록 순이다. 하드 링크가 둘 이상인 파일은 바꾸지 않는다. 바꾼 파일은 원래 권한 비트만 이어받는다. 임시 파일은 원래 파일보다 많은 것을 담지 않는다(ADR 0037, 0038).
5. **파일 제거.** 파일 전체 값이 이번 시도에서 저장되고 확인된 파일만, 제거 직전에 다시 읽어 저장한 바이트와 해시가 같을 때만 지운다. 제거는 되돌릴 수 없는 유일한 변경이다(ADR 0032).
6. **manifest.** 치환 뒤 manifest를 다시 읽어 이번에 적용한 비밀 값 위치와 합치고, 내용이 달라졌을 때만 같은 두 기록을 거쳐 쓴다(ADR 0032).
7. **닫기.** 일부라도 적용했으면 `succeeded`와 건수다. 저장하지 못한 키가 있고 바꾼 파일도 앞 시도의 적용도 없으면 실패다. 적용했거나 쓰던 항목이 있으면 실행을 닫는 트랜잭션에서 확인 스캔을 넣는다(ADR 0032, 0040).
8. **오탐 원본 정리.** 닫은 뒤 `SettledFingerprints`의 원본을 지운다. 실패는 로그 한 줄이고 결과를 바꾸지 않는다(ADR 0032, 0054).

- 작업의 context는 파일 사이와 manifest 앞에서만 본다. worker가 멈추면 작업과 실행을 `queued`로 돌려 다음 시도가 이어 간다. 제한 시간은 30분이다(ADR 0022, 0032).
- 값은 가린 타입(`apply.value`)으로만 들고 있고, 저장 단계가 끝나면 0으로 지운다. 로그와 오류에는 저장 키, 파일 경로, 정해진 문구만 쓴다.
- 적용 화면과 결과 화면은 기록이 아는 것만 말한다. 쓰다 멈춘 파일은 "바뀌었을 수 있음", 확인 스캔 전이면 "확인 전"이다(ADR 0041, 0055).

#### manifest

프로젝트 루트의 `secrets-manifest.yml`이다. 사람이 읽고 다음 작업(운영 비밀 저장소 이전 등)에 참고한다. 값, 미리보기, 지문은 담지 않는다(ADR 0034).

```yaml
version: 1
entries:
  - name: ext.db.prod.main.password
    category: storage-credential
    action: externalized
    store: openbao:secret/data/projects/1/ext.db.prod.main.password
    locations:
      - file: src/main/resources/application-prod.yml
        line: 14
```

- `internal/manifest`가 YAML 라이브러리 없이 한 가지 모양만 쓰고 읽는다. 다른 모양(주석, 앵커, 블록 스칼라, 모르는 키 등)은 `ErrUnsupported`이고 오류 글에는 줄 번호와 정해진 사유만 담는다.
- 항목은 placeholder 표기마다 하나이고 이름으로 식별한다. 한 묶음이 `.yml`과 `.sh`에 걸치면 `ext.…`와 `EXT_…` 두 항목이 같은 `store`를 가리킨다. 고객정보는 넣지 않는다.
- 이미 있는 manifest는 덮어쓰지 않고 합친다. 같은 항목을 여러 번 합쳐도 결과가 같다. 줄바꿈이 CRLF면 CRLF로 쓴다.

### 3.7 리포트와 대시보드

#### 리포트

- 성공한 스캔 하나의 리포트를 열 때마다 만든다. 판정은 리포트를 만든 시각의 것이다. 시점을 고정한 사본은 PDF이고, 머리와 PDF에 만든 시각을 적는다(ADR 0042).
- 요약은 찾은 항목, 외부화 완료, 삭제·마스킹 완료, 오탐, 보류, 미판정, 적용 대기의 일곱 숫자와 바로 앞 성공한 스캔 대비 증감이다. 단위는 묶음이고 위치 수를 함께 보인다.
- 절은 외부화한 항목(이름, 분류, 종류, 파일과 줄, 저장 위치, 코드 변경 필요 여부), 삭제·마스킹한 고객정보(종류와 파일), 구조 변경이 필요한 항목, 남은 항목, 오탐과 사유, 판정 이력(판정, 옮기기, 적용 확인)이다. 원본 보기 기록은 싣지 않는다.
- "적용한 것"은 그 스캔이 요청되기 전에 시작된 적용 실행이 `applied`로 남긴 항목 전부(누적)이고, 그 스캔이 확인하는 실행도 앞선 것으로 본다(ADR 0042, 0044).
- 절마다 100줄(`report.MaxRows`), 외부화 항목 하나의 자리 50곳(`MaxPlaces`)까지 싣고 건수는 전체를 센다. 줄은 DB가 절로 나누고 바이트 순서로 자른다(ADR 0042, 0059).
- 리포트와 PDF에는 미리보기, 지문, 주변 줄을 싣지 않는다. `report` 패키지의 타입에 그런 필드가 없고 `TestTypes_HoldNoValueField`가 붙잡는다. 사용자가 쓴 메모는 싣는다(ADR 0042).
- `db.Store.Report`는 한 스냅숏(repeatable read)에서 읽는다.

#### PDF

- web이 화면과 같은 템플릿에 인쇄용 스타일을 더해 글꼴(woff2), 스타일시트를 포함한 HTML을 완성하고, pdf 서비스로 보내 PDF를 돌려받는다. 변환기는 web에 접속하지 않고 외부 자원을 받지 않는다(ADR 0006, 0043).
- 변환기는 JavaScript를 끄고, 요청 폴더 바로 아래의 `file://`만 열며, 모든 사설·공인 IP를 거부하고, 메모리 1GB, 요청 15초, 본문 32MB로 제한한다(ADR 0043).
- web은 변환을 한 번에 하나만 보낸다. 자리가 없으면 변환 제한 20초 안에서 기다리고, 끝내 자리가 나지 않으면 503 "다른 PDF를 만드는 중입니다"를 보인다. 시간 순서는 Gotenberg 15초 < 변환 20초 < 클라이언트 25초 < web `WriteTimeout` 30초다(ADR 0043, 0050).
- 인쇄용 문서에는 다른 화면으로 가는 링크를 넣지 않는다. 실제 변환기가 만든 PDF에 링크 주석이 없는지 테스트가 본다(ADR 0050).

#### 대시보드

- 건수의 단위는 묶음이고, 프로젝트마다 마지막 성공한 스캔의 리포트 요약과 같은 함수로 센다. 남은 항목은 미판정 + 보류 + 적용 대기다(ADR 0045).
- 타일은 남은 항목(지난 스캔 대비 증감), 외부화 완료, 삭제·마스킹 완료, 오탐, 보류다. 그 밖에 스캔별·분류별로 쌓은 남은 항목 추이, 분류별 남은 항목, 오탐이 많은 규칙 10개, 프로젝트 표(마지막 스캔, 남은 항목, 완료율, 보류)를 보인다.
- 추이의 막대 하나는 성공한 스캔 하나이고, 그 스캔이 찾은 묶음 가운데 지금 오탐이 아닌 것의 수다. 스냅숏 테이블은 없다. 여러 프로젝트는 스캔이 끝난 시각 순으로 늘어놓고 프로젝트마다 마지막 수의 합을 그린다. 막대는 새것부터 30개까지다(ADR 0045).
- 스캔의 순서는 언제나 (끝난 시각, ID)다(ADR 0047, 0060). 프로젝트 표의 마지막 스캔 시각은 끝난 스캔이면 끝난 시각이다(ADR 0061).
- 필터는 프로젝트와 기간(전체, 최근 7·30·90일)이다. 기간은 추이에만 걸리고, 프로젝트 표는 언제나 모든 프로젝트를 보인다(ADR 0045).
- 완료율은 완료 ÷ (완료 + 남은 항목)의 내림 백분율이고 분모가 0이면 "—"다.
- 차트는 라이브러리와 스크립트 없이 서버가 인라인 SVG로 그린다. 분류마다 정한 색 다섯 개에 범례, 조각 사이 틈, `<title>`, 같은 숫자의 표를 함께 두어 색만으로 구분하지 않는다(ADR 0046).
- 프로젝트 상태는 프로젝트 수와 상관없이 쿼리 셋으로 읽는다(ADR 0059).

### 3.8 데이터 모델

스키마는 `internal/db/migrations/NNNN_*.sql`이다. 마이그레이션은 직접 만든 실행기가 번호순으로, 파일 하나를 트랜잭션 하나로, `pg_advisory_lock` 안에서 실행하고 `schema_migration`에 남긴다. 바이너리가 모르는 버전이 적용되어 있거나 번호가 어긋나면 아무것도 적용하지 않고 멈춘다. 병합된 마이그레이션은 고치지 않는다(ADR 0016).

| 표 | 내용 |
|---|---|
| `project` | 이름, 작업 공간 기준 상대 경로, 제외 경로, 만든 사람 |
| `scan` | 상태(`queued`, `running`, `succeeded`, `failed`), 요청자와 이름, 시각, 커밋 해시, 도구와 규칙 버전, 파일·건너뛴·버린 수, 건너뛴 경로 200개, 스캐너 오류 수, 확인하는 적용 실행(`apply_id`) |
| `job` | 작업 큐. 종류(`scan`, `apply-check`, `apply`), 상태, 시도 수, 임대(`locked_by`, `locked_until`) |
| `finding` | 항목. 프로젝트, 지문, 파일, 키(유일), 분류, 종류, 미리보기, `has_original`, 첫·마지막 스캔, 묶음 |
| `location` | 스캔마다 항목의 위치. 시작·끝 줄과 열, 파일 해시, 가린 주변 줄, 검출(도구, 규칙, 인코딩) |
| `bundle` | 묶음. 지문, `origin`(`shared`, `frontend`, `own`), 판정, 보류 사유, 이름(프로젝트 안에서 유일), 메모, `applied_at`, `store_path` |
| `apply_run` | 점검과 적용 실행. 상태(`checking`, `ready`, `blocked`, `queued`, `running`, `succeeded`, `failed`, `superseded`), 계획 지문, 점검한 스캔, 막는 조건, 복구 불가 파일과 동의, 확인 스캔 |
| `apply_item` | 실행의 위치마다 동작(`replace`, `redact`, `remove-file`), 상태(`planned`, `writing`, `applied`, `skipped`, `failed`), 사유 |
| `apply_file` | 바꾸는 파일의 기록. 바꾸기 전·후 해시, 임시 파일 이름, `prev_after_hash` |
| `audit_event` | 감사 기록. 동작(`verdict`, `move`, `reveal`, `apply`), 사용자, 프로젝트, `detail` |
| `worker_beat` | worker ID, 받는 작업 종류, 마지막으로 작업을 가져가려 한 시각 |

- 작업 큐는 `FOR UPDATE SKIP LOCKED`와 임대 만료 시각으로 만든다. 임대 시각은 데이터베이스의 `now()`로 정하고 비교한다. 작업은 세 번까지 내주고, 결과를 쓰는 문장은 `locked_by`가 자기일 때만 반영한다. worker는 자기 종류의 작업만 가져간다(ADR 0016, 0068).
- 정상 종료하는 worker는 잡고 있던 작업을 `queued`로 돌려주고, 임대 연장이 실패한 채 임대 시간이 지나면 스스로 handler를 멈춘다(ADR 0022).
- 한 프로젝트의 스캔과 적용은 `project` 행의 잠금과 `apply_run`의 부분 유일 인덱스로 겹치지 않는다. 잠그는 순서는 언제나 작업, `project`, 그다음 묶음·항목·실행이다(ADR 0036, 0040, 0056).
- web은 `worker_beat`로 최근 30초 안에 그 종류의 작업을 가져가려 한 worker가 없으면 대기 중인 스캔·적용 화면에 "worker가 응답하지 않습니다"를 보인다(ADR 0062, 0068).
- 데이터베이스의 어느 열에도 비밀 값과 고객정보 원본이 없다. 지문과 `finding.Preview`의 미리보기, 가린 주변 줄만 있다.

### 3.9 실행 환경과 네트워크

#### compose 서비스

`compose.yaml`이 로컬 개발 스택 전체를 띄운다. 파일과 `deploy/` 아래의 비밀번호는 모두 `dev-only-…` 형태의 가짜 값이고, 공유하거나 배포하는 환경에 그대로 쓰지 않는다. 호스트 포트는 `127.0.0.1`에만 연다.

| 서비스 | 호스트 포트 | 비고 |
|---|---|---|
| web | 8080 | `ReadHeaderTimeout` 5초, `ReadTimeout` 15초, `WriteTimeout` 30초, `IdleTimeout` 120초 |
| keycloak | 8081 | 브라우저와 토큰의 발급자는 `localhost:8081`, web은 `keycloak:8080`에서 discovery를 읽는다 |
| postgres | 15432 | 통합 테스트용 |
| worker | 없음 | `WORKER_JOBS=scan`, `/workspace` 읽기 전용, tmpfs `/tmp` |
| applier | 없음 | `WORKER_JOBS=apply`, `/workspace-rw` 읽기-쓰기, 스캐너 없음 |
| openbao, valkey, pdf | 없음 | 내부 네트워크에서만 닿는다 |
| openbao-test, valkey-test, pdf-test | 18200, 16379, 13000 | `test` 프로필. 통합 테스트용 |

- 작업 공간은 `SE_WORKSPACE`로 준다. worker와 applier는 `SE_UID`, `SE_GID`(기본 65532, root 거부)로 실행되고 `restart: unless-stopped`다.
- `WORKER_JOBS`는 `all`(기본), `scan`, `apply`다. `scan`은 `APPLY_WORKSPACE_ROOT`를 받으면 기동하지 않고, `apply`는 그것이 필수이며 스캐너 설정을 읽지 않는다. `all`은 compose 밖의 개발과 테스트를 위해 남긴다(ADR 0068).
- 설정은 `run`이 인자와 환경 변수에서 한 번 읽고, 기동할 때 가린 채로 로그 한 줄에 남긴다.
- 컨테이너는 가능한 곳마다 읽기 전용 루트, `cap_drop: ALL`, `no-new-privileges`로 돈다.

#### 네트워크

| 네트워크 | 종류 | 붙는 서비스 |
|---|---|---|
| `edge` | bridge, NAT 끔 | web, keycloak, postgres |
| `db` | internal | postgres, worker, applier |
| `valkey` | internal | valkey, web |
| `bao` | internal | openbao, web, worker, applier, openbao-roles |
| `pdf` | internal | pdf, web |
| `test` | bridge, NAT 끔 | valkey-test, openbao-test, pdf-test |

어느 서비스도 호스트의 컨테이너 네트워크 밖으로 연결을 열지 못한다. worker와 스캐너, applier는 postgres와 OpenBao에만 닿는다. `openbao-secrets`와 `valkey-secrets`는 네트워크 없이 뜬다(ADR 0065, 0066).

#### TLS와 봉인

- **OpenBao.** 저장소는 pebbledb(`openbao-data` 볼륨)이고, 리스너는 TLS 1.2 이상만 받는다. `openbao-secrets`가 사설 CA와 서버 인증서를 만들고, web, worker, applier는 `BAO_CA_FILE`의 CA만 믿는다(ADR 0017, 0067).
- 로컬의 봉인은 static이고, 봉인 해제 키는 Docker 볼륨 밖의 호스트 파일(`~/.config/secret-externalizer/openbao-unseal.key`, `OPENBAO_UNSEAL_KEY_FILE`)이다. `make openbao-host-files`가 처음 띄우기 전에 만든다. 봉인 블록은 `deploy/openbao/seal-static.hcl`로 나뉘어 있어, 공유하거나 배포하는 환경은 이 파일만 키 관리 서비스에 기댄 자동 봉인 해제로 바꾼다(ADR 0067).
- 첫 기동 때 self-init이 transit 키, KV v2 마운트 `secret`(경로마다 버전 100개), AppRole 인증, 관리 역할 `admin`, audit device(표준 출력)를 만들고 루트 토큰을 폐기한다(ADR 0017, 0035, 0069).
- **valkey.** TLS 포트 6379만 열고 `users.acl`의 사용자만 받는다. web은 ACL 사용자 `se-web`과 비밀번호 파일로 붙고, 이 사용자는 `session:*`, `attempt:*` 키와 web이 쓰는 명령에만 닿는다. 메모리는 64MB이고 `noeviction`이라 다 차면 새 로그인만 503을 본다(ADR 0066).
- CA 파일 읽기와 "그 CA만 믿는 TLS 설정"은 `internal/cafile` 하나에 있다.

### 3.10 권한과 감사

#### 로그인과 세션

- Authorization Code + PKCE로 로그인한다. ID 토큰의 서명, 발급자, 대상, 만료는 go-oidc가, nonce는 앱이 확인한다(ADR 0010).
- 로그인 시도마다 쿠키(`se_login_<state 해시>`, `Path=/auth/callback`)를 따로 두어 동시에 시작한 두 로그인이 서로 깨지지 않는다(ADR 0064).
- 세션 ID는 `crypto/rand`의 32바이트이고, valkey 키는 그 SHA-256이다. 세션에는 subject, 이름, 역할, 만료만 담고 토큰은 담지 않는다. 유휴 30분, 절대 8시간이다. 역할은 로그인할 때의 값이라 Keycloak에서 역할을 빼도 세션이 끝날 때까지 남는다(ADR 0013).
- 세션 쿠키는 `HttpOnly`, `Secure`, `SameSite=Lax`이고 세션 ID만 담는다.
- 상태를 바꾸는 요청은 `POST`이고 `http.CrossOriginProtection`을 받는다(ADR 0012). 응답에는 CSP(`default-src 'self'`)와 보안 헤더가 붙고, 템플릿에 인라인 스크립트와 스타일이 없다(ADR 0025).
- 라우트는 `internal/web/routes.go` 한 곳에 있다. `/audit`과 원본 보기는 `admin`만, 나머지 업무 화면은 `user`와 `admin`이 쓴다.

#### 감사 기록

- `audit_event`는 판정(`verdict`), 옮기기(`move`, 합치기는 옮긴 항목마다 하나), 원본 보기(`reveal`), 적용 확인(`apply`, 복구 불가 동의 여부)을 남긴다. 값은 넣지 않는다. 감사 기록은 프로젝트만 참조하므로 묶음이나 항목이 지워져도 남는다(ADR 0027, 0028, 0036, 0063).
- `admin`은 `/audit`에서 감사 로그를 본다.
- OpenBao 자체의 audit device가 모든 요청을 HMAC으로 가려 표준 출력에 남긴다(ADR 0017).

#### OpenBao 역할

| 역할 | role-id | 허용 |
|---|---|---|
| `worker`(스캔) | `se-worker` | 지문 계산, `pending/` 쓰기, 목록, 삭제. `projects/`에 닿지 못한다 |
| `applier`(적용) | `se-applier` | 지문 계산, `projects/` 쓰기와 읽기, `pending/` 메타데이터 삭제. 원본을 보관하거나 읽지 못한다 |
| `web` | `se-web` | `pending/`과 `projects/` 읽기 |
| `admin`(관리) | `se-admin` | 자기 자신을 뺀 모든 정책과 AppRole을 쓰고 지운다. 토큰 5분 |

- 어느 역할도 외부화 값의 버전을 지우거나 destroy할 수 없다. 그래서 같은 경로에 100번 넘게 다른 값을 쓰지 않는 한 이전 값이 남는다(ADR 0035).
- 정책은 `deploy/openbao/policies/<역할>.hcl` 파일이고 통합 테스트도 같은 파일을 읽는다. `openbao-roles`가 `docker compose up` 때마다 관리 역할로 로그인해 역할, 정책, secret-id를 파일대로 맞추고 선언하지 않은 것을 지운 뒤 토큰을 폐기한다. 정책을 바꿔도 볼륨을 지우지 않는다(ADR 0069).
- 서비스마다 `openbao-secrets` 볼륨의 자기 폴더(secret-id와 CA)만 마운트한다. 관리 역할의 secret-id는 호스트 파일이고 openbao와 `openbao-roles`에만 넘긴다. 스캐너가 worker의 secret-id를 읽어도 외부화한 값을 읽거나 바꾸지 못한다(ADR 0069).
- 클라이언트는 처음 쓸 때 로그인하고 403을 받으면 한 번 다시 로그인한다. 토큰을 갱신하는 goroutine은 없다(ADR 0018).

## 4. 검토한 다른 방법

| 다른 방법 | 고르지 않은 이유 | ADR |
|---|---|---|
| web과 스캔을 한 프로세스에 두기 | 로그인 화면을 받는 프로세스가 소스 쓰기, 스캐너, OpenBao 쓰기 권한을 모두 갖는다 | 0001 |
| docker client로 스캐너 컨테이너를 매번 띄우기 | docker.sock은 socket proxy를 거쳐도 호스트 root 권한과 같다 | 0001, 0002 |
| trufflehog, kingfisher 같은 스캐너 | 찾은 키를 외부 API로 보내 확인하는 동작이 이 도구와 맞지 않는다 | 0002 |
| 원본을 gitignore된 로컬 파일로 내보내거나 보관하지 않기 | 평문 파일이 개발자 PC에 남거나, 원본을 git 히스토리나 백업에서 찾아야 한다. 원본은 OpenBao에만 두고 DB에는 HMAC 지문만 둔다 | 0003 |
| AI(가린 값을 보내는 모델)로 판정을 보조하기 | 범위와 외부 의존이 는다. 사람이 판정하고 규칙 기반 제안만 한다 | 0004 |
| `golang-migrate`, `goose`, `River` 같은 라이브러리, valkey를 큐로 쓰기 | 쓰는 기능에 비해 의존성이 크다. valkey는 디스크에 남기지 않아 재시작하면 작업이 사라진다 | 0016 |
| 서명된 쿠키(JWT)에 세션 내용을 담기 | 서버에서 세션을 끊을 수 없다 | 0013 |

## 5. 공통 관심사

### 5.1 비밀 값과 고객정보

`AGENTS.md`의 Security 절이 기준이고, 이 절은 그것을 옮겨 적는다.

- 비밀 값은 로그 줄, 오류 메시지, 템플릿, 데이터베이스 열, 리포트, manifest, 세션 어디에도 나오지 않는다. 데이터베이스와 화면에 둘 수 있는 것은 파생된 두 형태뿐이다.
  - 지문: OpenBao가 계산한 값의 HMAC.
  - 미리보기: `finding.Preview`가 만든다. 8글자 이상인 비밀은 앞 4글자 뒤에 마스크, 더 짧은 비밀과 개인키, 키 파일은 마스크만이다.
- 값 자체가 쓰이는 곳은 하나다. `admin`이 원본 보기를 요청한 응답이다. 그 요청을 위해 OpenBao에서 읽고, 사본을 남기지 않으며, 읽기 전에 감사 기록을 남긴다.
- 리포트와 그 PDF에는 지문도 미리보기도 없다.
- 비밀 값을 담는 타입은 `LogValue() slog.Value`와 `String() string`을 구현하고 둘 다 가린 형태를 돌려준다(`bao.Value`, `session.Password`, 세션 ID 등).
- 스캔한 파일에서 찾은 고객정보는 어디에도 복사하지 않는다. 종류, 위치, 건수, 지문, `finding.Preview`의 미리보기만 저장한다. 고객정보의 미리보기는 고정된 형식 문자열이고 전화번호만 앞 숫자 묶음의 3자리까지 남긴다. 원본은 OpenBao에 넣지 않고, 고객정보가 든 파일은 주변 줄을 저장하지 않는다.
- 도구가 스캔 대상의 내용을 복사하는 유일한 경우는 EUC-KR 파일의 UTF-8 사본이다. 한 스캔 동안 worker의 임시 폴더에 있고 그 스캔이 끝나면 지운다.
- 적용하는 worker(compose의 applier)는 사용자가 확인한 적용을 실행하는 동안에만, 판정이 `externalize`나 `redact`인 묶음의 자리에서만 프로젝트의 파일을 바꾼다. 값은 OpenBao에서 다시 읽어 지문이 맞은 뒤에만 소스를 떠난다. 파일 전체는 고객정보가 있을 수 없는 경우에만 저장하고 지운다. 바꾼 파일은 같은 폴더의 임시 파일을 거쳐 쓰며, 임시 파일은 원래 파일보다 많은 것을 담지 않는다. 저장소를 바꾸는 git 명령은 실행하지 않는다.
- 실제 비밀을 테스트 예제로 커밋하지 않는다. 예제의 값은 누가 봐도 가짜다.
- 입력에서 온 모든 파일 경로는 심볼릭 링크까지 풀어 작업 공간 루트 안인지 확인한 뒤 쓴다.
- 외부 명령은 `exec.CommandContext`와 인자 슬라이스로 실행하고 셸을 거치지 않는다.
- 예측할 수 없어야 하는 것은 `crypto/rand`, 비밀의 비교는 `subtle.ConstantTimeCompare`를 쓴다.
- 세션 쿠키는 `HttpOnly`, `Secure`, `SameSite=Lax`이고 세션 식별자만 담는다.
- 이스케이프는 `html/template`이 한다. 입력을 `template.HTML`, `template.JS`, `template.URL`로 바꾸지 않는다.

이 규칙을 코드가 한 번 더 지키는 자리는 다음과 같다: `PutStored`가 고객정보 종류를 거부한다(ADR 0035). `manifest.Entry`, `report`, `dashboard`의 타입에는 값을 담을 필드가 없고 테스트가 필드 목록을 붙잡는다(ADR 0034, 0042, 0045). 스캐너와 git의 출력, OpenBao 클라이언트의 오류는 감싸지 않고 정해진 문장으로 바꾼다(ADR 0018, 0020, 0033). CI의 규칙 검토자는 코드 줄이나 값을 인용하지 않는다(ADR 0073).

### 5.2 테스트

- **단위 테스트.** 표준 `testing` 패키지와 표 형태의 하위 테스트를 쓰고, 구조 비교는 `cmp.Diff`다(ADR 0007). 테스트는 패키지의 공개 API로 하고, 가짜는 손으로 써서 테스트 옆에 둔다. `make check`가 `-race`로 돌린다.
- **통합 테스트.** 실행 중인 서비스가 필요한 테스트는 `TEST_DATABASE_URL`, `TEST_BAO_ADDR`, `TEST_VALKEY_ADDR`·`TEST_VALKEY_PASSWORD`, `TEST_PDF_URL`이 없으면 이유와 함께 건너뛴다. `make test-integration`은 넷 다 요구하고 compose의 postgres와 `test` 프로필의 `valkey-test`, `openbao-test`, `pdf-test`를 쓴다. 테스트는 실행마다 `test_<난수>` 스키마를 만들고 지운다. OpenBao 테스트는 `deploy/openbao/policies/`의 정책 파일로 같은 권한을 만든다(ADR 0069).
- **규칙 사례.** `internal/ruleset/testdata`의 두 예제를 실제 스캐너로 스캔해 기대 목록(`legacy-shop.json`, `rule-cases.json`)과 정확히 같은지 본다. 같은 결과가 두 번 나오거나 목록에 없는 줄이 나와도 차이다. `legacy-shop`은 스캔·적용 테스트가 함께 쓰는 예제 프로젝트이고, `rule-cases`는 찾아야 하는 모양과 건드리지 말아야 하는 모양을 하나씩 둔 사례 모음이다(ADR 0052). 실제 스캐너를 쓰는 테스트는 `bin/`에 스캐너가 없으면 건너뛰므로 `make scanners`를 먼저 실행한다.
- **끝에서 끝까지.** `TestIntegration_ScanApplyRescan`(`internal/apply`)이 예제 프로젝트를 실제 betterleaks, opengrep, 키 파일 탐지기, postgres, OpenBao, git으로 스캔 → 추천 판정 → 점검 → 적용 → 확인 스캔 → 대시보드까지 돌린다. 예제의 발견 목록을 고정하지 않고, 규칙이 무엇을 찾든 지켜져야 하는 것(스캔과 점검이 파일을 바꾸지 않음, 저장 값의 지문, 값이 어디에도 남지 않음, 확인 스캔의 결과, 리포트와 대시보드의 일치, 두 번째 점검의 `nothing-to-apply`)을 확인한다(ADR 0049).
- **변환기.** `TestReportPDF_PrintsAtEveryCap`이 모든 한도까지 채운 리포트를 실제 변환기로 인쇄하고, `TestReportPDF_NoLinkAnnotations`가 링크 주석이 없는지 본다(ADR 0044, 0050).
- **공개 예제.** `make sample-check`가 `scripts/samples.lock`에 커밋을 고정한 공개 예제(전자정부 표준프레임워크 `egovframe-web-sample`)를 저장소 밖(`~/.cache/secret-externalizer/samples`)에 받아, `TestIntegration_PublicSample`로 같은 흐름을 돌린다. 찾은 항목의 (파일, 분류, 종류, 설정 키) 목록이 `internal/apply/testdata/public-sample.golden`과 같은지, 확인 스캔이 적용한 비밀을 다시 찾지 않는지, 원본 비밀이 테이블과 worker 로그에 없는지, 적용이 자리를 바꾼 파일과 manifest만 바꿨는지 본다. 예제의 소스와 결과는 저장소에 넣지 않는다. CI의 `sample` 작업이 돌지만 필수 체크는 아니다(ADR 0075).
- **스크립트.** 스캐너 내려받기 스크립트(`make scanners-test`), 배포 스크립트(`make deploy-scripts-test`), 린트 설정이 규칙을 잡는지 보는 사례(`scripts/lint-rules_test.sh`)도 `make check`에 든다.

### 5.3 완료 판정

- 작업은 `make check`가 통과해야 끝난다. `make check`는 린터(golangci-lint, gofumpt), `go vet`, `-race` 테스트, 만든 CSS가 저장소의 파일과 같은지, 스크립트 테스트를 돌린다. 린트 결과는 고치고, 정말 맞는 경우에만 이유를 적은 `//nolint`를 쓴다.
- 커밋할 때 `pre-commit` hook이 검사 대상이 스테이징되어 있으면 Go 파일을 포맷하고 `make check`를 실행한다. `commit-msg` hook이 Angular 형식과 Issue 참조를 확인한다. 새로 받은 저장소에서는 `make setup`으로 연결한다(ADR 0072).
- PR은 CI의 네 체크 `check`(`make check`), `integration`(compose 테스트 서비스로 `make test-integration`), `pull-request`(PR 제목 형식과 `Closes #N`), `review`(`AGENTS.md` 규칙 검토)가 모두 통과해야 병합된다. `review: override` 라벨은 Security 절이 아닌 위반만 통과시킨다(ADR 0073, 0074).
- task 하나는 Issue 하나, 브랜치 하나, PR 하나이고 스쿼시로 병합한다. 행동이 바뀌면 `CHANGELOG.md`의 `[Unreleased]`에 한 줄을 쓰고, 나중에 물을 만한 결정은 `docs/adr/`에 남긴다(ADR 0074).

## 6. 위험과 한계

구조에서 오는 주요 위험만 적는다.

- **규칙이 놓친 값.** 탐지는 규칙에 기대므로 규칙이 잡지 못한 비밀은 판정 화면에도 리포트에도 없다. 같은 이유로 가린 주변 줄에 잡히지 않은 텍스트가 남을 수 있고, 그 줄은 `user`에게 보인다(ADR 0028, 0052).
- **스캔 사이의 식별.** 항목은 지문, 파일, 설정 키로 알아본다. 키 이름이 바뀌거나 어느 스캔이 키를 읽지 못하면 새 미판정 묶음이 생기고 원래 묶음이 화면에서 잠시 빠진다(ADR 0053).
- **판정은 지금의 것.** 리포트와 추이는 지난 스캔도 지금의 판정으로 센다. 그때의 판정을 보려면 PDF뿐이다(ADR 0042, 0045).
- **worker는 종류마다 하나를 전제한다.** 정리와 증감의 틈은 줄였지만 적용은 한 실행을 두 applier가 함께 잡는 경우를 다 막지 못한다(ADR 0038, 0060).
- **로컬 봉인과 사설 CA.** static 봉인과 호스트 파일의 키는 개발자 PC 한 대를 위한 것이다. 키 파일을 잃으면 저장한 값을 읽을 수 없고, 키 파일과 볼륨을 함께 가진 사람은 모든 값을 읽는다(ADR 0067).
- **자원.** PDF 변환기의 메모리가 리포트의 줄 한도(절마다 100줄)를 정한다. 작은 Docker VM에서는 빌드나 통합 테스트가 다른 서비스를 메모리 부족으로 죽일 수 있다(ADR 0044).
- **적용은 파일 단위의 기록에 기댄다.** `rename` 직전의 확인과 `rename` 사이에 다른 프로세스가 고친 내용은 덮어써질 수 있고, 도구는 git 작업본이 깨끗하다는 점검으로 이 틈을 좁힌다(ADR 0037).

남은 일과 알려진 한계는 GitHub Issue로 마일스톤마다 관리한다(https://github.com/SH-Hong1/secret-externalizer/milestones).
