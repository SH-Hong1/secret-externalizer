# 한글이 든 properties 비밀번호 값은 메시지다

- 날짜: 2026-11-26
- 상태: 확정

## 배경

`.properties` 파일에서 키의 끝이 `password`, `passwd`, `pwd`인 줄은 값을 비밀번호로 보고한다(0052). 메시지 묶음(`messages*.properties`)에도 같은 모양의 키가 많아서 `label.password=비밀번호`, `changePassword=비밀번호 변경`, 그리고 같은 글을 `비밀…`로 쓴 줄이 비밀번호로 보고되었다(0052의 "잘못 보고하는 것", #116).

## 결정

1. **`properties-password`와 `properties-comment-password`는 값에 한글이 있으면 보고하지 않는다.** 한글은 글자 그대로 쓴 것(`\p{Hangul}`)과, 한글 영역(U+1100–U+11FF, U+3130–U+318F, U+AC00–U+D7FF)을 가리키는 `\uXXXX` 이스케이프를 모두 센다.
2. 다른 규칙(YAML, XML, 계정, 호스트)은 그대로 둔다.

## 이유

- 한글은 키보드 배열과 인코딩 때문에 DB나 서비스 비밀번호에 거의 쓰지 않는다. 반대로 한국어 메시지 묶음의 값에는 거의 언제나 한글이 있다. 값을 보는 이 조건이 파일 이름보다 메시지와 설정을 더 잘 가른다.
- 메시지 묶음은 보통 한글을 `\uXXXX`로 이스케이프해서 쓰므로, 이스케이프도 세지 않으면 반만 줄어든다.

## 검토한 다른 방법

- **`messages*.properties`를 규칙에서 뺀다.** 0052에서 남겨 둔 방법이다. 이름만으로 파일을 빼면 그 이름의 설정 파일에 든 비밀 값을 놓치고, 영어 메시지 묶음은 줄지 않는 점은 같다.
- **값에 공백이 있으면 메시지로 본다.** 영어 메시지(`Change password`)까지 거르지만, 0052가 Java 규칙에서 따진 것처럼 공백이 든 암호문을 놓친다.

## 알려진 한계

- 한글이 든 실제 비밀번호는 보고하지 않는다.
- 영어로 쓴 메시지(`changePassword=Change password`)는 지금처럼 비밀번호로 보고한다.
- 규칙 파일이 바뀌어 규칙 버전이 바뀐다. 이미 스캔한 프로젝트를 다시 스캔하면 메시지 묶음의 항목이 줄 수 있다.
