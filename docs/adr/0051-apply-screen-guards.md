# 적용 중에는 판정 화면을 잠그고, 근거 없는 복구 불가 동의는 세지 않는다

- 날짜: 2026-11-23
- 상태: 확정

## 배경

계획 5에서 남은 일 가운데 적용 화면 둘레의 세 가지다.

- 점검이나 적용이 진행 중일 때 판정 화면은 판정 버튼과 옮기기 양식을 그대로 보였다. 누르면 저장소가 거부해 409와 "적용 중에는 판정을 바꿀 수 없습니다"가 나왔다. 메모와 이름을 다 적고 나서야 안 된다는 것을 알았다.
- `db.Store.ConfirmApply`는 점검이 복구 불가 파일을 하나도 보여 주지 않았어도 동의 값을 받아 `apply_run.allow_irreversible`과 감사 기록에 "yes"로 남겼다. handler만 "점검이 그런 파일을 보여 줬을 때만 동의로 센다"를 지켰다.
- 남은 일 목록에는 "점검 뒤에 요청된 스캔이 실패했거나 대기 중이면 적용 화면이 안내 없이 적용 단추를 보인다"고 적혀 있었다. 코드를 읽어 보니 화면은 이미 막고 있었다. 대기 중인 스캔은 "진행 중인 스캔이 없음: 실패", 실패한 스캔은 "마지막으로 성공한 스캔이 가장 새 스캔임: 실패"로 보이고 적용 단추는 눌리지 않는다. 남은 것은 문장이었다. 점검한 화면을 열어 둔 채 스캔이 끼어든 뒤 적용을 누르면 "판정이나 스캔이 바뀌었습니다. 다시 점검해 주세요."가 나왔는데, 바뀐 것이 무엇인지 말하지 않고, 스캔이 실패한 경우에는 다시 점검할 수도 없다.

## 결정

1. **판정 화면은 점검이나 적용이 진행 중이면 상세를 잠근다.** `TriageStore.ApplyActive`(`db.Store.ApplyActive`)가 프로젝트에 `checking`, `queued`, `running`인 실행이 있는지 알려 준다. 저장소가 판정과 옮기기를 거부하는 조건과 같은 쿼리다. 잠긴 상세는 판정·메모 저장·판정 취소 버튼, 보류 사유, 메모, 이름을 누를 수 없게 하고, 옮기기 양식은 그리지 않으며, "점검이나 적용이 진행 중이라 지금은 판정을 바꿀 수 없습니다."와 적용 화면 링크를 보인다. 목록과 필터, 원본 보기는 그대로다.
2. **저장소의 거부는 그대로 둔다.** 화면을 연 뒤에 적용이 시작되면 버튼이 살아 있고, 그때는 전처럼 409가 나온다. 거부된 화면에는 잠금 안내 대신 거부 사유만 보인다(같은 말을 두 번 하지 않는다).
3. **`ConfirmApply`는 점검이 복구 불가 파일을 보여 준 실행에서만 동의를 센다.** `irreversible_files`가 비어 있으면 받은 값이 무엇이든 `allow_irreversible`은 false, 감사 기록의 `irreversible`은 "no"다. 요청을 거부하지는 않는다.
4. **확인한 실행 뒤에 스캔이 있으면 `ErrPlanChanged`가 아니라 `ErrScanFollowed`다.** 화면은 "점검한 뒤에 새 스캔이 있습니다. 스캔 결과와 판정을 확인한 뒤 다시 점검해 주세요."를 보이고, `ErrPlanChanged`의 문장은 "판정이 바뀌었습니다. 다시 점검해 주세요."가 된다.
5. **점검 전 화면의 "낡은 점검" 안내도 둘로 나눈다.** 점검한 스캔이 지금의 기준 스캔과 다르면 "점검한 뒤에 새 스캔이 성공했습니다. 새 스캔의 판정을 확인하고 다시 점검해 주세요.", 같으면 "점검한 뒤 판정이 바뀌었습니다. 지금 판정으로 다시 점검해 주세요."다.

## 이유

- 잠금의 기준을 저장소의 거부와 같은 조건으로 두면 "버튼은 눌리는데 거부된다"와 "버튼은 막혔는데 실제로는 된다"가 둘 다 생기지 않는다. 틈은 화면을 연 뒤에 상태가 바뀌는 경우뿐이고, 그 틈은 저장소가 막는다.
- 메모만 고치는 것도 잠근다. `Decide`는 적용 중이면 메모만 바뀐 요청도 거부하므로, 메모 저장 버튼을 살려 두면 그 버튼만 409를 낸다.
- 동의는 감사 기록에 남는 값이다. 점검이 묻지 않은 것에 "yes"가 남으면, 나중에 기록을 읽는 사람이 복구 불가 파일이 있었다고 읽는다. 규칙이 handler에만 있으면 다른 호출자(테스트, 이후의 API)가 어긴다.
- 거부하지 않고 세지 않는 쪽을 골랐다. handler가 이미 그렇게 하고 있고, 체크박스가 없는 화면에서 값이 올 길은 손으로 만든 요청뿐이며, 그 요청의 나머지(실행, 다이제스트)는 유효하다. 거부하면 새 오류와 새 화면 문장이 필요한데 얻는 것이 없다.
- 스캔이 끼어든 것과 판정이 바뀐 것은 사용자가 할 일이 다르다. 판정이 바뀌었으면 다시 점검하면 되고, 스캔이 있으면 그 스캔이 끝났는지와 무엇을 찾았는지부터 봐야 한다.

## 검토한 다른 방법

- **잠금을 `ApplySummary`로 판단한다.** 이미 있는 메서드지만 판정 화면을 열 때마다 계획의 묶음과 고객정보 위치를 모두 읽고 다이제스트를 계산한다. 필요한 것은 `EXISTS` 한 줄이다.
- **잠긴 화면을 자동으로 새로 고친다.** 적용 화면은 점검 중에 3초마다 새로 고치지만, 판정 화면은 사용자가 목록을 읽고 메모를 적는 화면이라 새로 고치면 읽던 자리를 잃는다. 안내의 링크로 적용 화면에 가서 진행을 본다.
- **`ErrScanFollowed`가 `ErrPlanChanged`를 감싼다.** 호출자를 덜 고치지만, 두 경우를 나눠 말하려는 것이 목적이라 `errors.Is`의 순서에 기대는 코드가 된다.

## 알려진 한계

- 잠금은 화면을 그릴 때의 상태다. 적용이 끝나도 열려 있는 화면은 잠긴 채이고, 다시 열어야 풀린다.
- 적용된 묶음 탭(`status=applied`)은 판정 양식이 없어 잠금 안내도 없다.
- 점검 전 화면의 "적용할 판정이 있음: 통과"는 그대로다. 남은 외부화 묶음이 worker가 언제나 건너뛰는 것뿐이면 점검 뒤에야 실패한다(`docs/decisions/0049-end-to-end-test-and-empty-checks.md`).
