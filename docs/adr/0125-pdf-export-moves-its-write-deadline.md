# PDF 내보내기는 자기 쓰기 기한을 옮긴다

- 날짜: 2026-11-26
- 상태: 확정

## 배경

PDF 한 건은 세션 읽기, DB 5초(`databaseLimit`), 변환 20초(`pdfLimit`, 자리를 기다리는 시간 포함)를 따로 건다. web 서버의 `WriteTimeout` 30초는 요청 머리를 읽기 시작한 때부터 세므로 이 셋을 모두 덮는다. 셋이 제한 가까이 걸리면 변환이 끝난 뒤 응답을 쓰기 전에 기한이 지나, 브라우저는 오류 화면 없이 끊긴 연결을 본다(0044의 "PDF 한 건의 시간", 0050, #77). 테스트에서 서버의 `WriteTimeout`보다 긴 변환이 `EOF`로 끝나는 것을 재현했다.

0044는 고치는 방법으로 "변환 제한을 줄이거나 `WriteTimeout`을 이 경로만 늘린다"를 적어 두었다.

## 결정

1. PDF 내보내기 handler는 시작하자마자 `http.ResponseController.SetWriteDeadline`으로 그 연결의 쓰기 기한을 "지금 + `Limits.Store` + `Limits.PDF` + `Limits.Write`"로 옮긴다.
2. `web.Limits`에 `Write`(만든 PDF를 보내는 시간)를 더한다. `cmd/web`은 `pdfWriteLimit` 10초를 넘긴다. 그래서 PDF 경로의 기한은 handler가 시작한 때부터 35초다.
3. 다른 경로와 서버의 `WriteTimeout` 30초는 그대로다.
4. 기한을 옮길 수 없는 writer(`http.ErrNotSupported`, 테스트의 recorder)는 서버의 기한을 그대로 쓴다. 그 밖의 오류는 경고로 남기고 계속한다.

## 이유

- 기한을 옮기면 DB가 느려도 변환 시간을 줄이지 않는다는 0044의 결정이 그대로 남는다. 변환 제한을 줄이면 큰 리포트(0043의 한도까지 채운 리포트)가 느린 VM에서 인쇄되지 못할 수 있다.
- 서버 전체의 `WriteTimeout`을 늘리면 다른 모든 화면의 느린 클라이언트도 연결을 그만큼 오래 붙잡는다. 이 경로만 늘리면 영향이 PDF 한 건(한 번에 하나, 0050)에 그친다.
- 기한은 handler가 시작한 때부터 세므로 세션 읽기에 쓴 시간이 변환 몫을 줄이지 않는다. 각 단계에는 이미 자기 제한이 있어 handler가 기한을 넘겨 붙잡히지 않는다.
- 보내기 10초는 PDF(수 MB)를 느린 사내망에서 보내기에 넉넉하고, 끊긴 클라이언트가 연결을 붙잡는 시간은 짧게 둔다.

## 검토한 다른 방법

- **변환 제한을 줄이기(예: 15초).** Gotenberg의 자체 제한 15초보다 짧아져 변환기의 답보다 web의 제한이 먼저 걸린다(0043의 순서가 깨진다).
- **서버의 `WriteTimeout`을 늘리기.** 모든 경로에 영향을 준다.
- **PDF 경로에 전체 기한 하나를 걸기.** 느린 DB가 변환 몫을 줄인다(0044가 버린 방법).
