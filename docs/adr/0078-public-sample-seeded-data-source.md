# 공개 예제 사본에 가짜 접속 정보를 넣어 적용을 검증한다

- 날짜: 2026-11-25
- 상태: 확정

## 배경

#126에서 `.properties`의 계정 규칙(`properties-username`)이 키 끝만 보고 값을 받아, 메시지 파일의 안내 문장(`confirm.required.user=User is required.`, 같은 문장을 `\uXXXX`로 쓴 줄)을 계정으로 보고했다. 계정 이름은 한 낱말이므로 공백이 든 값을 받지 않게 고치면 이 오탐이 사라진다.

그런데 ADR 0075의 공개 예제(`egovframe-web-sample`)에서 스캔이 찾은 것은 이 오탐 세 줄뿐이었다. 고치고 나면 찾는 항목이 없어, `TestIntegration_PublicSample`의 점검이 "적용할 것 없음"으로 막히고 적용, 확인 스캔, 원본이 남지 않았는지의 확인이 아무것도 검사하지 못한다. 또 그 테스트가 원본을 읽는 부분은 비밀 종류 항목이 처음으로 생기자 worker 역할로 `pending`을 읽으려다 403으로 실패했다. worker 정책은 원본을 읽지 못하게 되어 있고(ADR 0069), 원본을 읽는 것은 원본 보기를 하는 web 역할이다.

## 결정

- `properties-username`의 값은 공백 없는 한 낱말(`\S+`)이다. 줄 끝의 공백은 값이 아니다. YAML과 Spring XML의 계정 규칙은 바꾸지 않는다.
- `TestIntegration_PublicSample`은 예제를 임시 작업 공간에 복사한 뒤, 사본의 `src/main/resources/egovframework/spring/context-datasource.xml`에서 `</jdbc:embedded-database>` 바로 뒤에 dataSource bean 하나를 넣는다. URL은 `jdbc:mysql://db.example.invalid:3306/sample`, 계정은 `fake_sample_user`, 비밀번호는 `fake-sample-password-not-real`로 누가 봐도 가짜다. 그 자리가 없으면 테스트가 실패한다. 받은 예제 원본과 이 저장소에는 예제 파일을 넣지 않는다.
- 기대 목록(`public-sample.golden`)은 이 bean의 계정, 호스트, 포트, 비밀번호 네 항목이다. 적용은 네 곳을 바꾸고, 확인 스캔과 원본 확인이 그 값을 대상으로 돈다.
- 테스트는 원본을 web 정책의 AppRole로 읽는다.

## 이유

- 사용자 이름에는 공백이 들어가지 않는다. 메시지 묶음의 문장은 거의 언제나 공백을 담는다. 비밀번호에는 공백이 들어갈 수 있으므로 비밀번호 규칙은 그대로 둔다.
- 예제를 고른 이유는 실제 구조의 프로젝트에서 스캔, 적용, 확인 스캔이 실패 없이 돌고 값을 남기지 않는지 보는 데 있다(ADR 0075). 적용할 자리가 없으면 그 확인이 비어 버린다. 레거시 프로젝트가 접속 정보를 두는 바로 그 파일에 그 모양으로 넣으면, 예제의 실제 구조(폴더, 다른 bean, 주석으로 막은 bean)를 유지하면서 적용 경로를 끝까지 지난다.
- 테스트가 운영 정책과 같은 역할로 원본을 읽어야 정책이 바뀌어 원본 보기가 깨질 때도 드러난다. root 토큰으로 읽으면 그것을 놓친다.

## 검토한 다른 방법

- 찾은 항목이 없으면 적용 단계를 건너뛰기: 테스트가 "스캔이 실패하지 않는다"만 확인하게 된다.
- #127을 먼저 정해 주석 안의 dataSource를 탐지하기: 결정이 필요한 일이고, 정한 뒤에도 적용이 주석 안의 값을 바꿀지는 따로 정해야 한다.
- 비밀이 있는 다른 공개 예제로 바꾸기: 실제 비밀이 든 공개 저장소를 고정해 받는 것은 바람직하지 않고, 예시 값이 든 예제를 새로 찾아도 같은 문제가 다시 생길 수 있다.
- 메시지 파일을 제외 경로로 다루기: 메시지 파일에도 비밀번호가 적힐 수 있고, 오탐의 원인은 파일이 아니라 값의 모양이다.
