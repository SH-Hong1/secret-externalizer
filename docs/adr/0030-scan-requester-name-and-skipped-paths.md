# 스캔에 남기는 요청자 이름과 건너뛴 파일 경로

- 날짜: 2026-11-20
- 상태: 확정

## 배경

계획 4에서 스캔 화면을 요약으로 줄이면서 두 가지를 화면에 보이게 했다. 하나는 스캔을 요청한 사람이고, 다른 하나는 스캔이 읽지 못해 건너뛴 파일이다.

- `scan` 행에는 요청한 사용자의 subject(`requested_by`)만 있었다. subject는 Keycloak이 만든 식별자라 사람이 읽을 수 없다. 이 도구에는 사용자 표가 없어, 화면을 그릴 때 subject로 이름을 찾을 곳이 없다.
- 건너뛴 파일은 수(`skipped`)만 저장하고 경로는 worker 로그(`scan skipped files`, 처음 50개와 전체 수)에만 있었다. 경로는 파일 내용이 아니지만, 사용자가 만든 이름이라 UTF-8이 아니거나 제어 문자가 들어 있을 수 있고, 프로젝트에 따라 수천 개가 될 수 있다.

## 결정

- `scan`에 `requester_name` 열을 두고(마이그레이션 0006), 스캔을 요청할 때 로그인한 사용자의 표시 이름을 함께 저장한다. 스캔 화면과 프로젝트 화면의 스캔 목록은 이 이름을 보인다. 이 열이 생기기 전의 행은 이름이 비어 있고, 화면은 subject를 대신 보인다.
- `scan`에 `skipped_files text[]` 열을 두고, 건너뛴 파일 가운데 프로젝트 폴더 기준 상대 경로를 경로순(바이트 순)으로 처음 200개(`scan.MaxSkippedFiles`)만 저장한다. UTF-8이 아니거나 제어 문자가 든 경로는 저장하지 않는다. 탭도 제어 문자로 본다. 저장하지 않은 경로와 읽지 못한 폴더는 `skipped` 수에만 센다.

## 이유

- 요청자 이름: 화면이 보여 줄 것은 "누가 요청했는가"이고, 이름을 얻을 수 있는 때는 요청하는 순간의 세션뿐이다. 감사 기록(`audit_event`)도 같은 이유로 `actor_name`을 저장한다.
- 이 선택의 대가: 사용자의 이름이 Keycloak에서 바뀌어도 지난 스캔에는 옛 이름이 남는다. 또 이름을 담는 곳이 감사 기록 말고 하나 더 생긴다. 이름은 비밀 값도 고객정보도 아니고, 누가 요청했는지는 subject로 언제든 확인할 수 있어 받아들였다.
- 건너뛴 경로: 화면은 목록을 펼침 상자 안에 보이므로 수백 개를 넘으면 읽을 수 없고, 한 행이 커지지 않게 상한이 필요하다. 경로순으로 자르면 같은 프로젝트를 다시 스캔했을 때 같은 목록이 나온다(디렉터리를 읽는 순서는 파일 시스템마다 다르다).
- UTF-8이 아닌 문자열은 postgres의 `text`에 넣을 수 없고, 줄바꿈이나 탭이 든 경로는 목록 한 줄로 보일 때 다른 경로처럼 읽히거나 줄이 어긋난다. 그런 경로를 바꿔 쓰면(예: `finding.Printable`처럼 대체 문자로) 실제 파일 이름과 다른 이름이 화면에 나오므로 저장하지 않고 수에만 센다. 탐지 항목의 경로는 탭을 허용하지만(`storablePath`), 그 경로는 저장해야 항목을 남길 수 있어서이고 건너뛴 경로는 보이기 위한 것이라 더 엄격하게 거른다.

## 검토한 다른 방법

- **요청자 이름을 저장하지 않고 subject만 보이기**: 열이 늘지 않지만 화면에서 누가 요청했는지 알 수 없다.
- **사용자 표를 두고 subject로 이름을 찾기**: 이름이 바뀌면 화면도 바뀌지만, 로그인 때마다 표를 갱신해야 하고 Keycloak과 이름을 맞추는 일이 생긴다. 이름을 보일 곳이 스캔과 감사 로그뿐이라 표를 둘 만큼 쓰임이 없다.
- **건너뛴 경로를 모두 별도 표에 저장하기**: 상한이 없어 빠짐이 없지만, 스캔마다 행이 수천 개 생길 수 있고 화면은 어차피 처음 일부만 보인다.
- **건너뛴 경로를 로그에만 남기기(이전 방식)**: 저장할 것이 없지만, 화면을 보는 사용자는 worker 로그를 볼 수 없다.
- **보이지 않는 문자를 대체 문자로 바꿔 저장하기**: 수와 목록이 맞지만 화면의 이름이 실제 파일 이름과 달라 찾을 수 없다.
