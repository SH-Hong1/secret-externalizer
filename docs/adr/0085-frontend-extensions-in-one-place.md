# 프론트엔드 확장자 목록은 triage 한 곳에 두고 리포트 쿼리는 매개변수로 받는다

- 날짜: 2026-11-25
- 상태: 확정

## 배경

ADR 0059에서 리포트의 절을 DB가 나누게 하면서, 프론트엔드 파일(JSP, JS, HTML)의 확장자 목록이 두 곳에 생겼다. `triage.Frontend`의 `switch`와 `db`의 `frontendFile`(SQL 상수 안의 `LIKE ANY ('{%.jsp,…}')`)이다. 한쪽만 바꾸면 리포트의 절과 줄의 `Frontend`가 판정 화면과 어긋난다. 0059의 "알려진 한계"에 적었고 #85로 옮겼다.

## 결정

1. 목록은 `triage.FrontendExtensions()` 하나에 있다. 소문자이고 점을 포함한 확장자를 새 슬라이스로 돌려준다. `triage.Frontend`는 이 목록으로 판단한다.
2. 리포트 쿼리(`reportLines`)는 확장자 목록을 SQL에 적지 않고 매개변수 `$7`로 받는다. `db`의 `frontendPatterns`가 확장자마다 `%` + 확장자 패턴을 만들고, 쿼리는 `lower(file_path COLLATE "C") LIKE ANY ($7::text[])`로 비교한다.
3. 확장자에는 `LIKE`가 특별히 보는 글자(`%`, `_`, `\`)가 없다. `TestFrontendExtensions`가 목록 자체를 고정하므로, 목록을 바꾸는 사람이 이 점을 함께 본다.

## 이유

- 매개변수로 넘기면 쿼리 문자열은 여전히 상수이고, 목록의 출처는 하나다.
- `LIKE ANY`의 비교 방식은 0059에서 잰 그대로라 성능이 달라지지 않는다.

## 검토한 다른 방법

- **목록에서 SQL 조각을 만들어 쿼리 문자열에 넣는다.** 쿼리가 상수가 아니게 되고, 실행 중에 문자열을 이어 붙인 SQL이 생긴다. 들어가는 값이 입력이 아니어도 "입력을 문자열로 이어 SQL을 만들지 않는다"는 규칙과 모양이 닮아 읽는 사람이 다시 확인해야 한다.
- **두 곳을 두고 테스트로만 맞춘다.** 지금까지의 방법이다. `TestReport_Sections`가 어긋남을 잡지만 DB가 있어야 돌고, 바꿀 곳이 둘인 것은 그대로다.
- **SQL의 정규식으로 `path.Ext`를 흉내 낸다.** 0059에서 정규식이 `LIKE`보다 느렸다.
