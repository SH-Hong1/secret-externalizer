# 프로젝트별 제외 경로를 스캔마다 스캐너에 넘긴다

- 날짜: 2026-11-25
- 상태: 일부 대체됨 (betterleaks에 제외 경로를 넘기는 방식은 0091 참조)

## 배경

`opengrep.New`는 제외 경로를 생성자 인자로 받았다. worker는 스캐너를 시작할 때 한 번 만들기 때문에 이 인자에 `nil`을 넘겼다(0020). 그래서 프로젝트별 제외 경로는 opengrep에 전달되지 않았다. opengrep과 키 파일 탐지기는 제외한 폴더도 모두 읽었고, 스캔 실행기가 자기 파일 목록에 없는 파일의 결과를 버리는 것으로만 제외했다(0021). 제외한 폴더가 크면(내려받은 라이브러리, 산출물 사본) 그 폴더를 읽고 분석하는 시간이 스캔마다 들었다.

## 결정

- `scan.Scanner.Scan`과 `ScanWithCounts`가 스캔할 때마다 제외 경로(스캔 폴더 기준, `/` 구분 상대 경로)를 받는다. `opengrep.New`는 제외 경로를 받지 않는다.
- 스캔 실행기는 프로젝트의 제외 경로를 모든 스캐너에 넘긴다. EUC-KR 사본 폴더도 원본과 같은 상대 경로를 쓰므로 같은 제외 경로를 넘긴다.
  - opengrep: 0020대로 `--exclude=/<이스케이프한 경로>`를 붙인다.
  - 키 파일 탐지기: `textfile.Walk`에 넘겨 그 경로로 내려가지 않는다. 파일 목록을 만드는 걷기와 같은 규칙이다.
  - betterleaks: 경로를 제외하는 실행 옵션이 없어 받은 제외 경로를 쓰지 않는다. 제외한 폴더도 읽는다.
- 스캔 실행기가 파일 목록에 없는 파일의 결과를 버리는 규칙(0021)은 그대로 둔다. betterleaks의 결과와, 제외 경로를 따르지 않는 스캐너의 결과도 이 규칙으로 걸러진다.

## 이유

- 스캐너 값 하나를 프로젝트마다 다시 만드는 것보다 스캔 호출의 인자로 넘기는 편이 단순하다. 스캐너는 실행 파일, 규칙, 환경처럼 worker 전체에서 같은 것만 갖고, 스캔마다 다른 것은 호출이 받는다.
- 결과를 버리는 규칙을 남기는 이유: 스캐너가 제외 경로를 따르는지에 스캔 결과의 정확성이 달려 있지 않게 한다.

## 검토한 다른 방법

- 스캔마다 프로젝트의 제외 경로로 스캐너를 새로 만들기(`opengrep.New`의 인자를 그대로 쓰기): 실행기가 스캐너 목록 대신 만드는 함수를 받아야 하고, 테스트의 가짜 스캐너도 같은 모양이 되어야 한다.
- betterleaks에 스캔마다 `[allowlist] paths`를 더한 설정 파일을 만들어 넘기기: 규칙 파일을 스캔마다 임시 폴더에 다시 써야 하고, 제외 경로를 정규식으로 이스케이프하는 규칙이 하나 더 생긴다. 이 일은 이 결정의 범위보다 커서 따로 남기고, 그때까지 betterleaks가 제외한 폴더도 읽는 한계를 받아들였다.
- betterleaks에 제외하지 않은 최상위 항목만 경로 인자로 넘기기: 제외 경로가 깊은 곳에 있으면 그 위의 폴더를 모두 풀어 넘겨야 하고, 인자 수에 한도가 없다.
