# 주석으로 막아 둔 Java 코드의 비밀 리터럴을 보고한다

- 날짜: 2026-11-25
- 상태: 확정

## 배경

ADR 0081은 XML 주석과 `.properties`, `application*.yml`의 주석 줄을 탐지 대상으로 정하면서 Java 주석은 미뤘다(#144). Java 규칙(`rules/opengrep/java.yml`)은 opengrep이 코드로 읽은 대입과 메서드 호출을 보는데, 주석 안의 코드는 opengrep에게 코드가 아니다. 이슈는 주석 안의 대입과 `setPassword(…)`, `getConnection(…)` 호출을 정규식 규칙으로 잡을지, 잡는다면 `java-secret-variable`의 이름 규칙(이름이 무엇을 뜻하는지에 따라 보고하지 않는 이름)을 어디까지 옮길지 정하라고 했다.

사용자의 상시 지시에 따라 권장안으로 정했다.

## 결정

1. **잡는다.** `rules/opengrep/comment.yml`에 정규식 규칙 넷을 더한다. 모두 `*.java`에만 적용하고, 범주와 종류는 `java.yml`의 같은 규칙과 같은 `other-secret`/`password`다.
   - `java-comment-secret-variable`: 이름이 `java-secret-variable`이 보고하는 이름인 변수나 필드에 문자열 리터럴 하나를 대입하고 `;`로 끝나는 문장. 타입과 `this.` 같은 한정자는 있어도 없어도 된다.
   - `java-comment-set-password`: `.setPassword("…")`.
   - `java-comment-set-property-password`: 키에 passw나 pwd가 든 `.setProperty("…", "…")`.
   - `java-comment-get-connection-password`: `getConnection(…, …, "…")`의 세 번째 인자.
2. **이름 규칙은 모두 옮긴다.** 이름에 passw, secret, token, pwd가 들거나 Pass, PASS, Pw, PW로 끝나는 조건과, header, name, param 등으로 끝나거나 MSG_, msg 등으로 시작하는 이름을 빼는 조건을 마지막 식별자에 거는 lookahead로 그대로 옮긴다. 그래서 주석 안팎에서 같은 이름이 같게 다뤄진다.
3. **주석은 줄 처음에 표시가 있는 것만 본다.** `//` 주석, 그리고 `/*`로 여는 블록 주석(Javadoc 포함)은 그 표시가 줄에서 공백 다음 처음 오는 것이어야 한다. 코드 뒤에 붙은 주석(`foo(); // String pwd = "…";`)은 보지 않는다.
4. **리터럴은 한 줄 안의 큰따옴표 문자열이고 비어 있지 않다.** 백슬래시 이스케이프는 담을 수 있다. 여러 줄에 걸친 문장, 문자열 이어 붙이기, 한 줄에 여럿 선언한 변수는 잡지 않는다.
5. **적용은 ADR 0081의 3과 같다.** 판정대로 placeholder나 표시로 바꾼다.

## 이유

- 레거시 Java 소스는 예전 접속 비밀번호를 주석으로 막은 코드로 남기는 일이 흔하고, 값은 저장소에 그대로 있다. XML과 properties의 주석만 보고 Java 주석을 보지 않을 까닭이 없다.
- 이름 규칙을 일부만 옮기면 같은 이름이 주석 안에서만 보고되거나 빠져, 판정하는 사람이 규칙을 두 가지로 이해해야 한다. 정규식 lookahead로 같은 조건을 쓸 수 있다.
- `"http://…"`, `"/api/**"`처럼 문자열 리터럴 안에도 `//`와 `/*`가 나온다. 줄 어디서든 주석 표시를 받으면 그 뒤의 실제 코드(이미 `java.yml`이 보는 것)를 주석으로 잘못 읽어 같은 값을 두 번 보고하거나, `/*`부터 다음 `*/`까지 넓은 범위를 주석으로 읽는다. IDE의 줄 주석 처리와 손으로 막은 블록은 거의 다 표시가 줄 처음에 오므로, 줄 처음만 보면 놓치는 것은 적고 잘못 읽는 일은 거의 없다. 테스트 픽스처는 `"/api/**"`가 든 줄과 `"http://…"` 뒤에 붙은 주석을 넣어 이것을 확인한다.
- 정규식으로 Java를 분석하지 않고 opengrep이 이미 쓰는 범위 교집합(`patterns`)을 써서 "주석 안이면서 이 모양인 문장"을 한 규칙으로 쓸 수 있다. 주석을 벗긴 사본을 만들어 `java.yml`에 넘기는 방법은 보안 규칙(스캔 대상 내용의 사본은 EUC-KR 변환본 하나)에 어긋난다.

## 한계

- 값 해석(`internal/literal`)은 Java 파일의 한 줄을 그 줄만 보고 읽는다. `//` 줄과 `/*`가 있는 줄의 값은 글자 그대로, `/*` 없이 블록 주석 안에 이어지는 줄의 값은 문자열 리터럴로 읽어 이스케이프를 푼다. 백슬래시가 든 값이 블록 주석의 가운데 줄에 있을 때만 차이가 나고, 어느 쪽이든 적용은 같은 자리를 바꾼다.

## 검토한 다른 방법

- 대입과 호출 가운데 일부(`setPassword`만 등)만 잡기: 같은 코드가 주석 안팎에서 다르게 다뤄진다.
- 이름 규칙 없이 이름에 password가 든 대입만 잡기: `token`, `secret`, `DB_PASS`를 놓치고, `PASSWORD_PARAM` 같은 이름은 보고한다.
- 줄 어디에 있든 주석 표시를 받기: 위 이유의 중복 보고와 넓은 범위 문제가 생긴다.
- 주석 안의 Java 코드를 opengrep에 Java로 다시 넘기기(주석을 벗긴 사본): 사본을 만들 수 없다.
