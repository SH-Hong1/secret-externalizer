# 계획 6을 구현하면서 대신 정한 것

- 날짜: 2026-11-22
- 상태: 일부 대체됨 (고객정보 줄의 적용 표시는 0117 참조)

## 배경

계획 6(`docs/superpowers/plans/2026-11-20-06-report-and-pdf.md`)은 계획 4, 5와 같은 방식으로 진행했다. 하위 에이전트가 Task를 하나씩 구현하고 다른 에이전트가 검토했다. 사용자는 2026-11-20에 "확인받지 말고 권고안대로 정하고 문서로 남기라"고 했다. 그래서 계획 문서의 "검토 때 정해 주실 것" 16개를 사용자 검토 없이 권고안으로 확정했다. 구현하는 동안 계획이 답하지 않았거나 계획의 가정이 틀린 것도 멈추지 않고 정했다. 이 문서는 그렇게 정한 것을 한곳에 모은다. 주제별 결정 기록(0042 스캔 리포트가 보이는 것, 0043 PDF 변환기의 구성과 제한)에 이미 적은 것은 번호를 붙였다. 틀렸다면 각 항목의 "틀렸을 때" 만큼만 고치면 된다.

### 리포트가 보이는 것(0042)

| 정한 것 | 이유 | 틀렸을 때 |
|---|---|---|
| 리포트는 저장하지 않고 열 때마다 만든다. 시점을 고정한 사본은 PDF다(검토 항목 2) | 판정은 스캔이 끝난 뒤에 하므로 스캔 종료 시점의 스냅숏에는 판정이 없다 | 지난 스캔의 리포트는 지금의 판정을 보인다. 그때의 판정이 필요하면 판정 이력을 되감는 조회를 새로 만든다 |
| "앞선 실행"의 규칙에 "이 스캔이 확인하는 실행"(`apply_run.id = scan.apply_id`)을 더했다(검토 항목 3, 0042의 결정 2) | 작업을 돌려받은 뒤 다시 시작하지 못하고 `FailApply`로 닫힌 실행은 `started_at`이 NULL이고 `finished_at`이 확인 스캔의 요청 시각과 같다. 시각만으로는 그 실행이 자기 확인 스캔의 앞에 들지 않아, 방금 바꾼 항목이 "이후 적용됨"으로 보였다 | 확인 스캔의 리포트가 실행의 항목을 싣지 말아야 할 경우에 싣는다 |
| 시작 시각도 끝난 시각도 없는 실행(돌려받아 다시 대기 중인 실행)의 `applied` 항목은 어느 스캔의 앞에도 뒤에도 두지 않는다 | 시각이 없으면 순서를 정할 수 없다. 그 실행이 끝나면 시각이 생긴다 | 그 실행이 대기 중인 동안 리포트에 그 항목이 빠진다. 스캔과 적용이 겹치지 않으므로(0036) 그동안 새 스캔은 없다 |
| 요약의 증감은 묶음 수만 보인다. 위치 수의 증감은 보이지 않는다 | 화면 폭. 위치 수는 같은 칸에 그대로 보인다 | 칸 하나를 더한다 |
| 고객정보 줄 하나가 여러 묶음을 묶으면, 그 줄의 상태는 묶음 가운데 하나라도 적용된 것을 따른다. "이후 적용됨"이 "이전에 적용됨"보다, 적용 표시가 보류 사유보다 앞선다 | 줄 하나에 상태를 하나만 보인다 | 한 줄의 묶음 일부만 적용된 경우 나머지의 상태가 가려진다. 줄을 상태로도 나눈다 |
| 2절 표에서 "이름 · 저장 위치", "분류 · 종류"를 한 칸으로 합쳤다. 상태 표시의 색은 "적용됨 · 다시 발견"이 실패 색, "이후 적용됨"이 성공 색이다 | 800px 폭과 A4 폭에 맞추려고 | 모양만 바뀐다 |

### 줄 한도와 PDF 변환기(0042, 0043)

| 정한 것 | 이유 | 틀렸을 때 |
|---|---|---|
| 절마다 100줄(`report.MaxRows`), 외부화 항목 하나의 자리 50곳(`MaxPlaces`)까지 싣는다. 화면과 PDF가 같은 한도를 쓰고 건수는 언제나 전체를 센다(검토 항목 9) | 계획의 1,000줄로 여섯 절을 채운 리포트는 메모리 한도 1GB의 변환기가 인쇄하지 못했다. 300줄과 200줄도 실패했고, 150줄은 세 번에 한 번 통과했고, 100줄은 3.4~3.7초, 480~582MiB로 통과했다. 화면과 PDF는 같은 내용이어야 한다 | 메모리가 더 큰 호스트에서는 필요보다 일찍 자른다. `report.MaxRows`를 올리고 `TestReportPDF_PrintsAtEveryCap`(통합 테스트)로 확인한다 |
| 변환기 컨테이너에 메모리 한도 1GB와 `/tmp` tmpfs 256MB를 두었다(0043) | 한도가 없을 때 큰 문서가 VM의 메모리를 다 써서 다른 서비스(`openbao-test`)가 커널에 죽었다. 한도가 있으면 그 변환만 400으로 실패한다 | 변환기가 더 일찍 실패한다. 한도를 올린다 |
| Chromium이 여는 주소를 `^file:///tmp/<uuid>/<uuid>/[^/]+$`로 좁혔다(0043) | 처음 정한 `^file:///tmp/`는 Chromium 프로필과 캐시도 열었다 | Gotenberg가 폴더 모양을 바꾸면 모든 변환이 실패하고 `TestConvert_Real`이 잡는다 |
| 변환기가 문서를 거부하면(400) 500 화면에 "리포트가 너무 커서 변환기가 인쇄하지 못했을 수 있습니다"를 보인다 | 실제로 본 400은 모두 메모리 부족이었다 | 다른 이유의 거부에도 같은 문장이 나온다 |
| PDF 한 건의 시간: 세션 읽기, DB 5초, 변환 20초를 따로 건다. 합이 web의 `WriteTimeout` 30초에 가깝다 | DB가 느려도 변환 시간을 줄이지 않으려고 | DB와 변환이 둘 다 제한까지 걸리면 응답을 쓰기 전에 `WriteTimeout`이 지날 수 있다. 그때 브라우저는 끊긴 연결을 본다. 변환 제한을 줄이거나 `WriteTimeout`을 이 경로만 늘린다 |
| 바닥글은 `secret-externalizer | scan #N | 쪽 / 전체`이고 ASCII만 쓴다. 바닥글의 `<style>`은 CSP가 닿지 않는 문서라 허용하고, 테스트(`TestNoInlineScriptOrStyle`)는 `print-footer` 정의 안의 `<style>` 하나만 빼고 검사한다 | 변환기는 바닥글을 본문과 따로 그리고 스타일시트를 읽지 않는다. 보낸 글꼴도 쓰지 못한다 | 바닥글의 `text-align: right`가 먹지 않아 글이 왼쪽에 붙는다. 모양만의 문제라 남겼다 |

### 고치지 않고 넘긴 것

`docs/next-steps.md`의 "계획 6에서 남은 일"에 적었다.

## 이유

멈춰서 묻는 것보다 정하고 기록하는 편이 빠르고, 위의 결정은 대부분 고치는 데 드는 일이 작다. 리포트와 PDF에 무엇을 싣는가에서는 언제나 덜 싣는 쪽을 골랐다(미리보기와 지문을 빼고, 줄을 자르고 건수만 전체를 센다). 빠진 것은 판정 화면에서 볼 수 있지만, 도구 밖으로 나간 문서는 되돌릴 수 없다.

## 검토한 다른 방법

- **항목마다 사용자에게 묻는다**: 사용자가 하지 말라고 했다.
- **PDF에만 줄 한도를 둔다**: 화면과 PDF의 내용이 달라진다. 계획의 Global Constraints가 같은 블록을 그리라고 한다.
- **주제별 결정 기록에만 적는다**: 무엇이 사용자 대신 정해졌는지 한눈에 볼 수 없다.
