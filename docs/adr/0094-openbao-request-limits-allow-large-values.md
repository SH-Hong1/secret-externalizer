# OpenBao 요청 한도는 큰 값을 보낼 시간을 둔다

- 날짜: 2026-11-25
- 상태: 확정

## 배경

worker의 OpenBao HTTP 클라이언트는 요청 한 번의 전체 제한 시간이 10초였다. 적용이 저장하는 값은 16MiB(`apply.DefaultMaxStoredBytes`)까지이고, base64로 보내면 약 21.4MiB다. 지문 요청, 저장, 저장 뒤 다시 읽기가 모두 그 크기를 한 요청에 싣는다. 10초 안에 끝내려면 초당 약 2.1MiB가 필요하므로, 느린 호스트나 망에서는 큰 키 파일이 `store-failed`가 되었다(이슈 #98). 값이 사라지지는 않지만 적용할 수 없다.

또 공식 클라이언트(`openbao/api`)는 HTTP 클라이언트의 제한과 따로, 요청 하나(재시도 포함)에 60초 한도를 둔다(`Config.Timeout`). HTTP 클라이언트의 제한만 늘리면 이 한도에 걸린다.

## 결정

1. `bao.NewHTTPClient(ca, timeout, answer)`는 두 한도를 받는다. `timeout`은 요청 한 번(본문을 보내고 답을 읽기까지)의 한도이고, `answer`는 요청을 다 보낸 뒤 서버의 답(응답 헤더)을 기다리는 한도다(`http.Transport.ResponseHeaderTimeout`). `answer`는 0보다 크고 `timeout` 이하여야 한다.
2. `bao.New`는 공식 클라이언트의 자체 한도를 끈다(`Config.Timeout = 0`). 요청 한 번은 HTTP 클라이언트의 `timeout`이, 재시도를 합친 전체는 호출한 쪽의 context가 묶는다. worker의 context는 점검 10분, 적용과 스캔 30분 한도를 가진다.
3. worker는 `timeout` 2분, `answer` 30초를 쓴다. 2분이면 21.4MiB를 초당 약 180KiB로도 보낸다. 30초는 OpenBao가 큰 값을 저장소에 쓰고 답할 시간이다.
4. web은 지금처럼 두 한도 모두 10초(`outboundTimeout`)다.

## 이유

- 전체 한도만 늘리면, 요청을 받고 답하지 않는 서버를 알아채는 데도 그만큼 걸린다. 답을 기다리는 한도를 따로 두면 작은 요청은 지금처럼 빨리 실패하고, 느린 것은 본문을 보내고 받는 시간뿐이다. 연결은 기본 transport의 30초, TLS 핸드셰이크는 10초 한도가 그대로 묶는다.
- 공식 클라이언트의 60초 한도는 재시도를 모두 합친 시간이라, HTTP 클라이언트 한도를 2분으로 둔 뜻을 지운다. 호출한 쪽의 context가 이미 작업 단위의 한도를 가지므로 세 번째 한도는 필요 없다.
- web은 원본 보기 요청 하나를 서버의 `WriteTimeout`(30초) 안에 끝내야 하므로 OpenBao 한도를 늘릴 수 없다. 16MiB 원본을 느린 망에서 보는 경우는 이 결정에 들지 않는다.

## 검토한 다른 방법

- 요청의 크기에 따라 요청마다 context 한도를 계산한다. 저장 뒤 다시 읽기처럼 답의 크기를 미리 모르는 요청이 있어 한도를 정할 수 없다.
- worker의 전체 한도만 2분으로 늘린다. 답하지 않는 서버에 대한 요청 하나가 재시도까지 6분 걸리고, 공식 클라이언트의 60초 한도에 먼저 걸린다.
- 저장하는 값의 크기 한도를 줄인다. 큰 키 파일(인증서 묶음, keystore)을 외부화할 수 없게 된다.
