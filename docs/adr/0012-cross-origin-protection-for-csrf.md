# CSRF 방어에 표준 라이브러리의 교차 출처 보호를 쓴다

- 날짜: 2026-11-18
- 상태: 확정

## 배경

`AGENTS.md`는 상태를 바꾸는 요청(`POST`, `PUT`, `PATCH`, `DELETE`)을 CSRF 방어로 덮으라고 정한다. 지금은 로그아웃(`POST /logout`) 하나뿐이지만, 계획 3 이후에는 프로젝트 등록, 스캔 실행, 판정, 적용 같은 폼이 늘어난다. 세션 쿠키는 `SameSite=Lax`라서 다른 사이트에서 보낸 `POST`에는 실리지 않지만, 같은 사이트의 다른 하위 도메인에서 보낸 요청이나 쿠키 속성을 지키지 않는 환경까지 쿠키 속성 하나에 맡기지 않는다.

## 결정

`NewServer`의 middleware에 Go 표준 라이브러리의 `http.CrossOriginProtection`을 넣는다. 위치는 보안 헤더 안쪽, 경로 처리 바깥쪽이다. 거부한 요청에는 기본 응답 대신 403 오류 화면을 보여준다. 신뢰할 출처(`AddTrustedOrigin`)와 우회 경로(`AddInsecureBypassPattern`)는 등록하지 않는다.

## 이유

- 추가 의존성이 없다. Go 1.25부터 표준 라이브러리에 있다.
- 폼마다 토큰을 넣고 검증할 필요가 없다. 토큰을 빠뜨린 폼이 생길 일이 없고, 토큰을 세션에 저장하거나 서명 키를 관리하지 않아도 된다.
- 지원하는 브라우저는 모두 `Sec-Fetch-Site` 헤더를 보내고(2023년부터 주요 브라우저 전부), 그렇지 않으면 `Origin` 헤더를 보낸다. 보호기는 `Sec-Fetch-Site`가 `same-origin`이나 `none`이 아니면, 이 헤더가 없을 때는 `Origin`의 호스트가 `Host`와 다르면 거부한다.
- `GET`, `HEAD`, `OPTIONS`는 항상 통과시키므로, 상태를 바꾸는 요청은 이 방식들을 쓰지 않는다는 기존 규칙과 맞물린다. `GET /logout`이 405인 것도 이 때문이다.
- 헤더(`Sec-Fetch-Site`, `Origin`)가 모두 없는 요청은 브라우저가 아닌 클라이언트로 보고 통과시킨다. 이런 클라이언트는 사용자의 쿠키를 자동으로 싣지 않으므로 CSRF의 대상이 아니다. 이 점은 표준 라이브러리의 동작을 그대로 받아들인다.

## 검토한 다른 방법

- 폼마다 넣는 동기화 토큰(예: `gorilla/csrf`): 의존성이 늘고, 모든 폼과 템플릿에 토큰을 넣어야 한다. 하나라도 빠지면 그 폼은 무방비다.
- 이중 제출 쿠키: 토큰 방식과 같은 부담이 있고, 하위 도메인이 쿠키를 심을 수 있으면 뚫린다.
- `SameSite` 쿠키 속성만 믿기: `Lax`는 같은 사이트의 다른 출처에서 온 요청을 막지 못한다.
