# 끝에서 끝까지 테스트가 대시보드 화면을 기간마다 읽는다

- 날짜: 2026-11-26
- 상태: 확정

## 배경

`TestIntegration_ScanApplyRescan`은 확인 스캔까지 돈 뒤 대시보드를 저장소 메서드(`Store.Dashboard`)로만 읽었다(0049의 "알려진 한계", #73). 기간 필터는 `internal/db`의 테스트가 손으로 만든 스캔으로, 화면은 `internal/web`의 테스트가 가짜 저장소로 따로 붙잡았다. 계획 7에서는 예제 스캔의 `finished_at`을 손으로 옮겼다가 되돌려 확인했다(0047). 예제의 스캔은 모두 테스트를 돌린 때에 끝나므로 어느 기간을 골라도 같은 막대가 나온다.

## 결정

1. 끝에서 끝까지 테스트의 마지막에, 테스트의 관리 연결로 첫 스캔의 요청과 끝난 시각을 40일 앞으로 옮긴다. 확인 스캔은 지금에 둔다.
2. `cmd/web`처럼 모든 저장소 자리에 실제 `db.Store`를 넣어 `web.NewServer`를 만든다. 로그인은 테스트의 세션 저장소가 아는 세션 하나로 하고, 식별 제공자와 로그인 시도는 부르지 않는 가짜를 둔다.
3. 그 프로젝트의 `/dashboard`를 전체, 90일, 30일, 7일로 요청한다. 추이 표의 스캔 링크로 어느 스캔이 막대가 되었는지 보고, "외부화 완료" 타일이 확인 스캔 리포트의 외부화 묶음 수와 같은지 본다.
4. 확인 스캔도 10일 앞으로 옮긴 뒤 30일에는 확인 스캔만, 7일에는 막대 없이 "이 기간에 끝난 스캔이 없습니다."가 보이고 타일은 그대로인지 본다.
5. 시각을 옮기는 일은 다른 확인이 모두 끝난 뒤에 한다. 이 테스트의 스키마는 끝나면 지워진다.

## 이유

- 기다리거나 서버의 시계를 바꿀 수 없으므로, 끝난 시각을 옮기는 것이 실제 스캔으로 기간을 가르는 가장 짧은 길이다. 계획 7의 손 확인과 같은 방법을 테스트 스키마 안에서 한다.
- 화면까지 지나야 handler가 기간을 `Since`로 바꾸어 저장소에 넘기는 연결, 저장소의 기간 쿼리, `dashboard.Build`, 템플릿이 한 번에 확인된다. 핸들러에서 기간을 넘기는 줄을 지우면 이 테스트가 실패하는 것을 보았다.
- 세션 저장소(valkey)와 로그인은 대시보드와 상관이 없고 `internal/web`의 테스트가 붙잡는다. 통합 테스트에 valkey를 더 요구하지 않는다.

## 검토한 다른 방법

- **`internal/web`에 실제 postgres를 쓰는 테스트를 따로 둔다.** 스캔을 손으로 만들어 넣어야 해서 `internal/db`의 기간 테스트와 다르지 않고, 실제 스캔에서 이어지지 않는다.
- **handler에 시계를 넣어 테스트가 "지금"을 옮긴다.** `routes.go`가 `time.Now`를 넘기는 구조를 테스트 때문에 바꾸어야 하고, 두 스캔이 같은 순간에 가깝게 끝나 기간으로 가를 수 없는 점은 같다.
- **compose 스택 전체를 띄워 브라우저로 누른다.** 0049에서 버린 이유(Keycloak, 2GB Docker VM)가 그대로다.
