# 파일 변경 기록은 일시적인 DB 오류를 다시 시도한다

- 날짜: 2026-11-25
- 상태: 확정

## 배경

적용은 파일마다 `BeginFile`로 바꿀 것을 먼저 적고, 파일을 바꾼 뒤 `EndFile`로 바꾼 것을 적는다(0032의 7). 둘 중 하나가 실패하면 실행이 멈추고 `failed`로 끝난다. 데이터베이스가 잠깐 오류를 낸 경우(연결이 끊김, 서버 재시작, 직렬화 실패, 교착)에도 그렇다. 사람이 적용을 다시 요청해야 했다(이슈 #95).

`EndFile`이 실패하면 파일은 이미 바뀌었고 기록만 열려 있다. 다음 점검이나 적용의 맞추기가 닫지만, 그때까지 실행은 실패로 보인다.

## 결정

1. **`db.Store.BeginFile`과 `EndFile`은 일시적인 오류에서 트랜잭션 전체를 다시 시도한다.** 모두 세 번까지 하고, 사이에 100ms, 300ms를 기다린다. 기다리는 동안 context가 끝나면 마지막 오류와 context의 원인을 함께 돌려준다.
2. **일시적인 오류는 같은 트랜잭션이 다시 만나지 않을 수 있는 것이다.** PostgreSQL의 `40001`(직렬화 실패), `40P01`(교착), 클래스 `08`(연결 예외), `57P01`·`57P02`·`57P03`(서버 종료, 시작 중)과, 서버의 답이 아닌 연결 오류(`net.Error`, `pgconn.ConnectError`, EOF)다. 그 밖의 서버 오류, `ErrNotFound`, `ErrItemSettled`, `ErrSuperseded`, context의 끝은 다시 시도하지 않는다.
3. **재시도는 `db`에 둔다.** `apply`는 `db`의 오류를 모른다(의존 방향, 0032). 오류를 가릴 수 있는 곳은 pgx의 오류를 보는 `db`다.

## 이유

- 두 메서드는 다시 불러도 한 번 부른 것과 결과가 같다. `BeginFile`은 같은 파일의 기록을 바꿔 쓰고 `writing` 항목을 다시 `writing`으로 둔다. `EndFile`은 이미 적은 같은 알림이면 아무것도 하지 않는다. 그래서 커밋은 되었는데 답을 받지 못해 실패로 보인 경우에도 다시 시도해 문제가 없다.
- 세 번과 0.4초 기다림은 연결 하나가 끊기거나 경합 한 번을 넘기기에 충분하고, `EndFile`의 기록 제한(5초, 0032)과 실행의 시간 한도 안에 든다. 데이터베이스가 오래 내려가 있으면 지금처럼 실행이 멈추고, 열린 기록은 다음 시작의 맞추기가 닫는다.
- 클래스 `08`과 연결 오류는 pgx 풀이 깨진 연결을 버리므로 다음 시도가 새 연결을 쓴다.

## 검토한 다른 방법

- **`apply`에서 모든 오류를 다시 시도한다.** `ErrItemSettled`나 `ErrSuperseded`처럼 다시 해도 같은 결과인 오류까지 기다리게 되고, `ErrSuperseded`는 다른 worker가 그 파일을 잡았다는 뜻이라 서둘러 멈춰야 한다.
- **`pgconn.SafeToRetry`만 본다.** 요청을 보내기 전에 실패한 경우만 참이라, 트랜잭션 중간에 끊긴 연결이나 직렬화 실패를 다시 시도하지 않는다. 여기서는 트랜잭션 전체를 다시 하므로 더 넓게 볼 수 있다.
- **다른 기록(`ResolveFile`, `FinishApply` 등)도 함께 다시 시도한다.** 이슈의 범위가 파일 변경의 앞뒤 기록이고, 다른 메서드는 다시 불러도 같은지 따로 확인해야 한다. 필요해지면 같은 `retried`로 감싼다.

## 알려진 한계

- 오류 분류는 서버가 보낸 SQLSTATE와 pgx가 감싼 연결 오류에 기대므로, pgx를 올릴 때 연결 오류의 모양이 바뀌면 다시 시도하지 않을 수 있다. 그래도 지금처럼 실행이 멈출 뿐이다.
