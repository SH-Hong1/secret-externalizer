# 실제 스캐너 테스트의 실패 메시지는 worker 로그의 요약만 보인다

- 날짜: 2026-11-25
- 상태: 확정

## 배경

`internal/apply`의 실제 스캐너 테스트(`TestIntegration_ScanApplyRescan`, `TestIntegration_PublicSample`, 실제 OpenBao와 git을 쓰는 적용 테스트)는 스캔, 점검, 적용이 실패하면 worker 로그 전체를 실패 메시지에 넣었다(#134). 공개 예제의 값은 가짜가 아니라 예제에 적힌 실제 글자다. 값을 로그에 남기는 회귀와 스캔 실패가 한 번에 나면 그 값이 CI 로그에 찍힌다. 테스트 끝의 "로그에 값이 없다" 검사는 `t.Fatalf`로 먼저 멈추면 돌지 않는다.

## 결정

- 이 테스트들의 실패 메시지는 `workerLog`가 만든 요약을 넣는다. 요약은 JSON 레코드마다 level, 메시지, 속성 이름만 한 줄로 보이고 속성 값은 보이지 않는다.
- 메시지와 속성 이름도 프로그램 소스(`cmd/`, `internal/`의 테스트가 아닌 `.go` 파일, `testdata` 제외)에 문자열 리터럴로 적힌 것과 정확히 같을 때만 보이고, 아니면 "(message withheld)", "(name withheld)"로 바꾼다. level은 slog가 쓰는 네 값일 때만 보인다. JSON 레코드가 아닌 줄은 그런 줄이 있었다는 표시만 남긴다.
- 로컬에서 전체 로그가 필요하면 `SHOW_WORKER_LOG=1`을 준다. CI는 이 변수를 주지 않는다.
- 가짜 값만 쓰는 단위 테스트의 실패 메시지는 그대로 둔다.

## 이유

- 규칙상 로그 메시지는 상수 문자열이고 변하는 것은 모두 속성이다. 그래서 level, 메시지, 속성 이름만으로 어느 단계에서 무엇이 실패했는지는 알 수 있다.
- 그래도 메시지나 이름에 값을 넣는 회귀(`fmt.Sprintf`로 만든 메시지 등)는 있을 수 있다. 소스의 리터럴과 같은 글자만 보이면 그런 회귀도 값을 내보내지 못한다. 스캔한 프로젝트의 값이 이 저장소 소스의 리터럴과 같을 일은 없고, 허용 목록을 손으로 관리하지 않아도 새 메시지가 저절로 보인다.
- 스캔과 적용의 실패 사유(`FailureReason`)는 데이터베이스에 저장되는 문자열이라 이미 값이 없어야 하고 테스트가 테이블을 검사한다. 실패 메시지는 이 사유를 계속 보인다.

## 검토한 다른 방법

- 메시지를 그대로 보이기: 메시지에 값을 넣는 회귀가 그대로 CI 로그에 닿는다.
- 보일 메시지를 손으로 적은 목록으로 정하기: 메시지를 더하거나 바꿀 때마다 목록을 고쳐야 하고, 빠뜨리면 진단할 수 없다.
- 로그에서 알려진 값을 지우고 보이기: 공개 예제는 스캔이 실패하면 어떤 값이 있었는지 알 수 없다.
- `error` 속성의 값만 보이기: 값을 오류 메시지에 넣는 회귀가 바로 막으려는 경우다.
- 로그를 CI 아티팩트로 올리기: 값이 CI 로그 대신 아티팩트에 남을 뿐이다.
