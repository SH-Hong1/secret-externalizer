# 설정 키로 항목을 나누기 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 한 파일 안에서 같은 값이 서로 다른 설정 키에 있으면 키마다 항목, 묶음, 추천 이름이 따로 생기게 한다.

**Architecture:** 스캔이 값이 대입된 설정 키를 파일 원문에서 읽어 `finding.Finding.Key`에 싣고, 한 파일의 위치를 "지문, 키"로 모아 항목을 만든다. DB는 항목의 유일 제약을 `(project_id, fingerprint, file_path, key)`로 바꾸고, 새 항목의 묶음을 정할 때 같은 파일의 다른 키 항목이 있는 `shared` 묶음을 피한다. 판정 화면과 추천 이름은 저장된 키를 읽는다. 적용, manifest, OpenBao 경로는 바뀌지 않는다(이미 항목과 위치 단위로 동작한다).

**Tech Stack:** Go 1.27, postgres 18(pgx), `html/template`. 새 의존성 없음.

**Spec:** `docs/superpowers/specs/2026-11-23-finding-key-design.md`. 관련 결정 기록 0021, 0026, 0027, 0048.

## Global Constraints

- `AGENTS.md`의 모든 규칙. 특히: 테스트를 먼저 쓰고 실패를 본다, `make check`가 통과해야 Task가 끝난다, 코드와 주석과 커밋 메시지는 영어, `docs/`와 `CHANGELOG.md`는 한글.
- 키가 될 수 있는 글자는 ASCII 글자, 숫자, `.`, `_`, `-`이고 길이는 1~200바이트다. 그 밖은 빈 문자열이다.
- 키에는 검출한 값이나 그 일부가 들어가지 않는다. 키로 읽은 범위가 주변 줄에서 가리는 범위(`pf.spans()`와 `elsewhere.find(pf.file.Text)`)와 겹치면 빈 문자열이다.
- 고객정보 항목, 주변 줄을 저장하지 않는 파일(`placedFile.noContext`), 파일 전체 결과, 두 줄 이상에 걸친 값의 키는 빈 문자열이다.
- 마이그레이션 `0001`~`0008`은 고치지 않는다. 새 파일 `0009`를 더한다.
- DB가 필요한 테스트는 `TEST_DATABASE_URL`이 없으면 건너뛴다(기존 `newMigratedStore`가 한다). 이 계획의 DB 테스트는 `TEST_DATABASE_URL=postgres://se_app:dev-only-se-app-password@127.0.0.1:15432/secret_externalizer_test`로 실제로 돌려 통과를 본다.
- 브랜치: 지금의 `fix/scan-rule-gaps` 위에서 `feat/finding-key`를 만든다. 커밋은 Task마다 한 번이다.

## Review Focus

스펙이 암시하지만 놓치기 쉬운 입력이다. 각 줄의 테스트는 괄호 안의 Task에 넣었다.

### Task 1: 설정 키 읽기

**Files:**
- Create: `internal/scan/key.go`
- Test: `internal/scan/key_internal_test.go`

**Interfaces:**
- Produces: `func configKey(rel string, text []byte, at int) (string, []finding.Span)`. `rel`은 슬래시로 나눈 파일 경로(확장자를 본다), `text`는 `textfile.File.Text`, `at`은 값이 시작하는 바이트 위치다. 돌려주는 범위는 `text`에서 키로 읽은 조각마다 하나다(YAML 경로의 마디마다, XML의 bean `id`와 잎). 부르는 쪽이 조각마다 검출한 값과 겹치는지 확인한다. 키가 없으면 `"", nil`.
- Produces: `const maxKeyBytes = 200`.

읽는 규칙(스펙 1절):

- **공통.** `at`이 있는 줄만 "값의 줄"이다. 줄 끝은 `\n`이고 줄 끝의 `\r`은 줄에 넣지 않는다. 값 앞 글자에서 여는 따옴표(`"`, `'`) 하나와 공백, 탭을 건너뛴 뒤의 글자가 대입 기호다.
- **그 밖의 파일.** 대입 기호가 `=` 또는 `:`이면 그 앞의 공백과 닫는 따옴표 하나를 건너뛰고, 거기서 왼쪽으로 이어진 키 글자(`[A-Za-z0-9_.-]`)가 키다. 대입 기호가 `(`이면 그 앞에 붙은 키 글자가 키다(`ds.setPassword(` → `ds.setPassword`). 다른 글자면 키가 없다.
- **YAML(`.yml`, `.yaml`).** 값의 줄에서 `:` 앞의 키를 위 규칙으로 읽는다. 그 줄의 들여쓰기(앞의 공백 수, 탭은 1로 센다)보다 얕은 위쪽 줄 가운데 `키:`로 끝나거나 `키: `로 시작하는 줄을 가까운 것부터 찾아 앞에 `.`으로 잇고, 들여쓰기가 0인 줄까지 간다. 빈 줄과 `#`으로 시작하는 줄은 건너뛴다. 올라가다 `- `로 시작하는 줄(목록 항목)을 만나면 아무것도 더 넣지 않고 멈춘다(목록 위의 키도 넣지 않는다). 값의 줄 자체가 `- 키: 값`이면 `- ` 뒤부터 키로 읽고 더 올라가지 않는다. 부모 줄의 키가 키 글자만으로 되어 있지 않으면 전체 키가 없다.
- **XML(`.xml`).** 값의 줄에서 값이 든 태그(`at` 왼쪽의 가장 가까운 `<`부터 `at`까지)에 `name="…"` 속성이 있으면 그 값이 잎이다. 없고 대입 기호가 `=`이면 속성 이름(`:` 앞의 이름공간은 뺀다)이 잎이다. 값 바로 앞이 `>`이면 그 요소 이름이 잎이다. `at` 앞에서 가장 가까운 `<bean`을 찾아, 그 뒤부터 `at`까지 `</bean>`이 없고 그 태그(`<bean`부터 다음 `>`까지)에 `id="…"`가 있으면 `id.잎`이 키다.
- 조립한 키가 키 글자만이 아니거나 `maxKeyBytes`를 넘으면 `"", nil`.

마이그레이션 `0009`:

```sql
ALTER TABLE finding ADD COLUMN key text NOT NULL DEFAULT ''
    CHECK (key ~ '^[A-Za-z0-9_.-]{0,200}$');
ALTER TABLE finding DROP CONSTRAINT finding_project_id_fingerprint_file_path_key;
ALTER TABLE finding ADD CONSTRAINT finding_identity UNIQUE (project_id, fingerprint, file_path, key);
```

지울 제약의 실제 이름은 `\d finding`으로 확인한다(postgres가 붙인 이름이다). 주석으로 열의 뜻을 적는다(영어).

`insertFinding`의 순서:

1. `UPDATE … WHERE project_id, fingerprint, file_path, key`가 일치하는 항목(지금 쿼리에 `key`를 더한다). 있으면 그 항목이다.
2. 없고 `f.Key != ""`이면 **이어 쓰기**: 같은 `project_id, fingerprint, file_path`에 저장된 항목이 정확히 하나이고, 그 항목의 `key = ''`이고 `last_scan_id <> 이번 스캔`이면, 그 항목의 `key`를 `f.Key`로 바꾸고 1과 같은 열을 갱신해 그 항목으로 쓴다. 한 문장의 `UPDATE … WHERE … AND (SELECT count(*) …) = 1 RETURNING id`로 한다.
3. 그래도 없으면 `bundleForNew`로 묶음을 정해 `INSERT`한다(`key` 포함).
