# 적용 Implementation Plan (계획 5/7)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 로그인한 사용자가 프로젝트의 적용 확인 화면에서 조건 점검 결과를 보고 "적용"을 누르면, 외부화로 판정한 값은 OpenBao KV에 저장된 뒤 소스에서 `${ext.이름}` / `${EXT_이름}`으로 바뀌고, 키 파일은 저장된 뒤 제거되고, 삭제·마스킹으로 판정한 고객정보는 `[REDACTED:종류]`로 바뀌며, `secrets-manifest.yml`이 쓰이고, 확인 재스캔이 자동으로 돌아 사라졌는지 보여 준다.

**Architecture:** 적용은 worker가 postgres 작업 큐에서 가져가는 두 종류의 작업이다. `apply-check`는 소스와 OpenBao를 바꾸지 않고 조건(git 작업본, 파일 해시, 값의 지문)을 점검해 결과를 `apply_run`, `apply_item`에 남기고, 사용자가 확인하면 `apply`가 같은 점검을 처음부터 다시 한 뒤 실행한다. 실행은 "저장 단계(모든 값을 OpenBao에 쓰고, 저장된 바이트를 다시 읽어 HMAC으로 확인) → 치환 단계(파일 하나를 한 번에, 뒤에서 앞으로, 같은 폴더의 임시 파일을 거쳐 원자적으로) → manifest → 기록" 순서이고, 파일을 바꾸기 전에 의도를 postgres에 먼저 적어(write-ahead) 중간에 죽어도 다음 점검이나 적용이 기록을 맞춘다. worker는 작업 공간을 두 번 마운트한다. 스캔과 스캐너는 읽기 전용 마운트를, 적용만 읽기-쓰기 마운트를 쓴다. web은 소스를 볼 수 없으므로 화면은 worker가 남긴 점검 결과만 그린다. 값은 worker의 메모리와 OpenBao에만 있다.

**Tech Stack:** Go 1.27(`os.Root`, `os/exec`), git 2.54(worker 이미지에 이미 있음, 읽기 전용 명령만), postgres 18, OpenBao 2.7(KV v2 check-and-set, transit HMAC), `golang.org/x/text`(EUC-KR, 이미 있음), `html/template`, htmx 2, tailwindcss 4. 새 의존성은 없다.

**Spec:** `docs/superpowers/specs/2026-11-18-secret-externalizer-design.md` (2절 실패 조건, 3절 인코딩과 줄바꿈, 6절 "placeholder"·"적용"·"manifest"·"OpenBao 사용 범위", 7절, 8절 "그 밖의 화면", 10절 6단계). 결정 기록 0003, 0017, 0021, 0022, 0026, 0027, 0028, 0031.

## 검토 때 정해 주실 것

설계 문서가 정하지 않았거나 계획 4가 이 계획으로 넘긴 내용이다. 각 항목의 첫 문장이 이 계획이 따르는 안이다. **[권고안으로 확정]** 은 2026-11-20의 지시("묻지 말고 권고안으로 정하고 문서로 남긴다")에 따라 작성자가 정한 항목이다. 코드를 읽거나 검토를 받고 처음의 권고안을 바꾼 항목은 **(바꿈)** 으로 표시했다.

1. **[권고안으로 확정] 계획은 하나로 두고 PR을 둘로 나눈다.** PR 1은 Task 1~11(git 점검, 파일 치환, manifest, OpenBao 저장, 작업 종류, 요청과 상호 배제, 기록, 계획 세우기, 점검, 실행, worker 연결)이고 화면이 없다. PR 2는 Task 12~15(확인 재스캔, 임시 원본 정리, 확인 화면, 결과 화면, 실제 확인)다. 다른 안: 계획을 둘로 나눈다. PR 1만으로는 사용자가 쓸 수 있는 것이 없어 계획 하나가 맞다.
2. **[권고안으로 확정] 적용은 프로젝트 단위이고, 마지막으로 성공한 스캔이 찾은 구성원 가운데 판정이 `externalize`, `redact`인 묶음의 것만 바꾼다.** `false-positive`, `hold`, 미판정 묶음은 같은 파일, 같은 줄에 있어도 한 바이트도 바뀌지 않는다. 지난 스캔에만 있던 구성원은 위치를 믿을 수 없으므로 대상이 아니다.
3. **[권고안으로 확정] (바꿈) 적용은 worker의 작업이고, worker는 작업 공간을 두 번 마운트한다.** 소스를 보고 OpenBao에 쓸 수 있는 것이 worker뿐이기 때문이다. `/workspace`는 지금처럼 읽기 전용이고 스캔과 스캐너(betterleaks, opengrep)가 쓴다. 같은 호스트 폴더를 `/workspace-rw`에 읽기-쓰기로 한 번 더 마운트하고 적용만 그 경로(`APPLY_WORKSPACE_ROOT`)를 쓴다. 외부에서 받은 스캐너 실행 파일이 쓸 수 있는 작업 공간 위에서 돌지 않게 하려는 것이다. 두 마운트가 독립으로 동작하는지는 "구현 전에 확인할 사실"에 있고, 안 되면 마운트 하나를 읽기-쓰기로 두고 남는 위험(스캐너가 소스를 바꿀 수 있다)을 결정 기록 0032에 적는다. `APPLY_WORKSPACE_ROOT`가 없으면 모든 점검이 `workspace-read-only`로 막힌다. 다른 안: 적용 전용 컨테이너. 권한은 더 좁아지지만 이미지와 작업 분배가 하나 더 생긴다.
4. **[권고안으로 확정] (바꿈) 조건 점검은 worker의 별도 작업(`apply-check`)이 하고, 확인 화면은 그 결과를 보여 준다.** 처음 안은 "worker가 작업 시작 때 점검하고 확인 화면에 미리 보여 준다"였는데, web은 소스와 git을 볼 수 없어 미리 보여 줄 방법이 없다. 그래서 흐름은 "점검 요청 → worker가 소스를 바꾸지 않고 점검 → 확인 화면 → 적용 요청 → worker가 처음부터 다시 점검하고 실행"이다. 점검과 실행 사이에 작업본이 바뀔 수 있으므로 실행은 점검 결과를 믿지 않는다. 다른 안: 점검 없이 바로 실행하고 실패를 결과 화면에 보인다. 설계 8절의 "적용 확인(조건 점검 결과)"과 "복구 불가의 별도 확인"을 만족하지 못한다.
5. **[권고안으로 확정] 조건은 여섯 가지다.** (가) 프로젝트 폴더가 git 작업본이고, 그 저장소의 작업본 루트, git 폴더, 공용 git 폴더가 모두 작업 공간 루트 안에 있으며, 커밋이 하나 이상 있다. (나) **프로젝트 폴더 아래** 추적되는 파일에 staged, unstaged 변경이 없고, assume-unchanged나 skip-worktree로 표시된 파일이 없다. 저장소가 프로젝트 폴더보다 크면 폴더 밖의 변경은 보지 않는다(도구가 건드리지 않는 곳이다). (다) 저장소 설정에 외부 명령을 실행하는 `filter.*`와 `core.worktree`가 없다. (라) 그 프로젝트의 스캔과 다른 적용이 돌고 있지 않다. (마) 마지막으로 성공한 스캔이 그 프로젝트의 가장 새 스캔이다. (바) 이미 있는 `secrets-manifest.yml`을 읽을 수 있다. 하나라도 어긋나면 어떤 파일도, OpenBao도 건드리지 않는다.
6. **[권고안으로 확정] git은 `git` 실행 파일을 `exec.CommandContext`와 인자 목록으로 부르고, 읽기 전용 명령만 쓴다.** `rev-parse`(작업본 여부, `HEAD`, 접두어, `--absolute-git-dir --git-common-dir --show-toplevel`), `config --name-only --list -z`, `status --porcelain=v1 -z --untracked-files=no --ignore-submodules=all --no-renames -- .`, `ls-files -z -v -t -- .`이다. 스캔 대상 저장소의 `.git/config`는 신뢰할 수 없는 입력이므로 모든 호출에 Task 1의 옵션과 환경을 붙인다: fsmonitor, hook, pager, 시스템·전역 설정, 선택적 잠금(인덱스 쓰기), 모든 전송 프로토콜과 partial clone의 지연 가져오기를 끄고, 끌 방법이 없는 `filter.<이름>.clean/process`는 설정에 있으면 점검을 실패로 끝낸다(조건 다). 스캔이 커밋 해시를 읽는 기존 호출(`internal/scan/commit.go`)도 같은 인자와 환경을 쓰게 한다. 다른 안: Go git 라이브러리(go-git). 의존성이 크고 `autocrlf`, `.gitattributes`, 무시 규칙의 해석이 git과 달라 "변경 없음"의 뜻이 개발자의 `git status`와 어긋난다. 다른 안: 인덱스의 blob 해시를 직접 계산해 비교한다. 외부 명령이 실행될 여지는 없지만 `core.autocrlf=true`인 저장소(윈도우에서 만든 레거시 프로젝트에 흔하다)의 CRLF 파일이 모두 "변경됨"이 되어 적용할 수 없다.
7. **[권고안으로 확정] 파일마다 건드리기 전에 지금의 내용 해시가 스캔 때 저장한 해시(`location.file_hash`)와 같은지 본다.** 다르면 그 파일의 모든 대상을 "재스캔 필요"(`file-changed`)로 건너뛰고 파일은 그대로 둔다. 값은 저장된 위치(줄, 글자 열)로 소스에서 다시 읽고, OpenBao의 HMAC으로 지문을 다시 계산해 묶음의 지문과 같을 때만 쓴다. 임시 경로(`pending/`)의 원본은 적용의 근거로 쓰지 않는다.
8. **[권고안으로 확정] (바꿈) 실행 순서는 묶음 단위가 아니라 단계 단위다: 저장 단계, 치환 단계, manifest, 기록.** 처음 안은 묶음마다 "저장 → 확인 → 치환 → 기록"이었는데, 한 파일에 여러 묶음의 값(JDBC URL의 호스트, 포트, 계정, 비밀번호)이 있고 파일은 한 번에 써야 한다. 묶음마다 파일을 쓰면 첫 묶음이 쓴 뒤 해시와 열이 달라져 나머지가 모두 건너뛰어진다. 그래서 먼저 모든 묶음의 값을 저장하고 확인한 다음, 파일마다 "저장이 확인된 묶음의 위치와 삭제·마스킹 위치"만 한 번에 바꾼다. 저장하지 못한 묶음의 위치는 그 파일에서 그대로 남는다. "OpenBao 저장에 실패하면 소스를 건드리지 않는다"는 위치마다 지켜진다.
9. **[권고안으로 확정] (바꿈) 저장 경로는 `secret/data/projects/<프로젝트 ID>/ext.<이름>`이다.** 프로젝트 키는 숫자 ID다. 프로젝트 이름은 한글, 공백, `/`가 들어갈 수 있어 경로에 쓸 수 없고, 임시 경로(`pending/<프로젝트 ID>/…`)도 ID를 쓴다. 마지막 마디는 파일 종류와 상관없이 설정 표기(`ext.db.main.password`) 하나다. 한 묶음이 `.yml`과 `.sh`에 걸쳐 있어도 값은 한 곳에 있다. 설계 예시의 `projects/shop/…`과 `…/EXT_DEPLOY_SSH_KEY`와는 다르다. 다른 안: 프로젝트에 경로용 키 열을 더한다. 등록 화면과 마이그레이션이 늘고, 사람이 읽기 좋다는 것 말고는 얻는 것이 없다.
10. **[권고안으로 확정] 저장하는 자료는 `value`(base64), `encoding`(`base64`), `format`(`text` 또는 `file`), `fingerprint`, `kind`다.** 텍스트 값은 스캔이 지문을 만든 것과 같은 UTF-8 바이트(EUC-KR 파일의 값도 UTF-8로 바꾼 것)이고, 키 파일은 디스크의 바이트 그대로다. 언제나 base64라서 키 저장소 같은 바이너리도 같은 길로 간다. **저장되는 값은 소스에 적힌 글자 그대로다.** XML의 `&amp;`, properties와 Java의 `\` 이스케이프, YAML의 따옴표 안 이스케이프를 풀지 않는다. 풀어 쓴 값이 필요한 사람은 파일 종류를 보고 풀어야 한다. 결정 기록 0035와 `docs/next-steps.md`에 적는다.
11. **[권고안으로 확정] (바꿈) 경로에 이미 값이 있으면 저장된 바이트의 HMAC을 다시 계산해 묶음의 지문과 비교한다.** worker가 스스로 쓴 `fingerprint` 필드는 비교에 쓰지 않는다(표시만 맞고 값이 다른 기록을 걸러내지 못한다). 같으면 쓰지 않는다(다시 실행해도 버전이 늘지 않는다). 다르면 check-and-set으로 새 버전을 쓰고, 이전 값은 이전 버전에 남으며, 결과에 버전 번호를 적는다. 쓴 뒤에도 다시 읽어 같은 방법으로 확인한다. 마지막 버전이 soft-delete된 경로는 읽으면 없는 것처럼 보이지만 버전은 N이므로, 읽기가 돌려준 버전으로 check-and-set한다. worker 정책에는 삭제 권한이 없다. KV v2는 경로마다 기본 10개 버전만 남기므로 "값이 다를 때만 쓴다"가 이전 값이 밀려나지 않게 하는 규칙이다. 다른 안: 다른 값이 있으면 거부하고 이름을 바꾸게 한다. 더 보수적이지만, 이름을 다시 쓰게 되는 경우(묶음이 지워진 뒤)가 드물고 이전 버전이 남으므로 택하지 않았다.
12. **[권고안으로 확정] 파일은 바꾸는 범위 밖을 바이트 그대로 둔다.** 치환은 디스크의 원래 바이트에 한다. 텍스트(UTF-8)의 범위를 원래 바이트의 범위로 옮기고(BOM 3바이트, EUC-KR은 파일의 처음부터 글자를 따라가며 센다), 넣는 문자열은 ASCII뿐이라 인코딩이 필요 없다. 한 파일의 모든 범위를 뒤에서 앞으로 한 번에 바꾸고, 같은 폴더의 임시 파일(이름 끝이 난수, `O_EXCL`)에 써서 `fsync` 뒤 `rename`한다. `rename` 직전에 파일의 크기, 수정 시각, inode를 다시 보고 읽었을 때와 다르면 그 파일을 그만둔다. 그 확인과 `rename` 사이의 틈은 남는다(알려진 한계). 모드는 유지한다. 소유자는 맞추지 않는다. worker는 `cap_drop: ALL`이라 `chown`이 언제나 실패하므로 새 파일은 worker 사용자의 것이 된다(검토 항목 30의 `SE_UID`로 개발자와 같게 한다). 모든 파일 접근은 프로젝트 폴더를 연 `os.Root`를 거치고 심볼릭 링크를 따라가지 않는다.
13. **[권고안으로 확정] placeholder 표기는 파일 확장자로 정한다.** `.sh`(대소문자 무시)는 `${EXT_<이름>}`, 그 밖의 모든 파일은 `${ext.<이름>}`이다. 판정 화면이 지금 쓰는 규칙(`web.shellFile`)과 같고, 함수를 `triage.ShellFile`로 옮겨 화면과 적용이 한 곳을 쓴다. 확장자가 `.sh`가 아닌 shell 스크립트(`deploy`, `run.ksh`)는 `${ext.…}`를 받는다. `docs/next-steps.md`에 남긴다.
14. **[권고안으로 확정] 접속 문자열은 적용 때 다시 나누지 않는다.** 스캔이 이미 호스트, 포트, 계정, 비밀번호를 항목으로 나눠 저장했으므로(결정 기록 0026) 각 항목의 위치를 바꾸면 구성 요소별 치환이 된다. 나누지 못해 통째로 남은 URL 항목은 통째로 바뀐다.
15. **[권고안으로 확정] `.java` 파일의 위치는 리터럴 안에서 바꾸고 "코드 수정 필요"로 표시한다.** 표시는 `apply_item.code_change`에 남고 계획 6의 리포트가 쓴다. shell의 작은따옴표 안(`sshpass -p '${EXT_…}'`)도 그대로는 풀리지 않지만 이 계획은 표시하지 않는다(따옴표 판별은 heredoc, 주석에서 틀리기 쉽다). `docs/next-steps.md`에 남긴다.
16. **[권고안으로 확정] (바꿈) 종류가 `key-file`인 항목은 파일 전체를 저장한 뒤 파일을 제거하되, 제거해도 되는 파일을 좁게 정한다.** 키 파일 탐지기는 앞 4KiB에 PEM 표시 줄이 있는 모든 파일을 보고하므로(`application.yml`이나 로그에 붙은 키) 판정 하나로 엉뚱한 파일이 통째로 OpenBao에 가고 사라질 수 있다.
    - 고객정보 경로(`finding.CustomerDataPath`)에 있거나, 마지막 스캔이 그 파일에서 고객정보 항목을 하나라도 찾았으면(판정과 상관없이) 저장도 제거도 하지 않는다. 사유는 `key-holds-customer-data`다. 그 파일의 삭제·마스킹 위치는 평소대로 적용한다. 고객정보의 사본이 OpenBao에 생기지 않게 하는 규칙이다.
    - 제거할 수 있는 파일은 다음뿐이다: 확장자가 `.jks`, `.p12`, `.pfx`, `.keystore`, `.ppk`, `.pem`, `.key`, `.crt`, `.cer`, `.der`인 파일, 이름이 `id_rsa`, `id_dsa`, `id_ecdsa`, `id_ed25519`인 파일, 그리고 내용이 PEM 블록과 공백뿐인 텍스트 파일. 그 밖은 `key-in-source-file`이다. 그 경우 PEM 블록(`private-key` 항목)을 외부화하면 블록만 바뀐다.
    - 파일은 그 파일 전체 값(`key-file` 대상)이 이번 시도에서 저장되고 확인되었을 때만 제거한다. 저장하지 못했으면(`store-failed`, `too-large`, `value-mismatch`) 그 파일의 모든 대상을 같은 사유로 건너뛰고 파일은 그대로 둔다. 같은 파일의 다른 묶음(`private-key`)만 저장되었다고 파일이 사라지지 않는다.
    - 제거하는 파일의 다른 외부화 위치는, 자기 값이 저장되고 확인되었으면 "파일 제거"로 적용된 것이고, 아니면 `file-removed`로 건너뛴 것이다(값은 파일 전체 값 안에 있다).
17. **[권고안으로 확정] 삭제·마스킹은 위치마다 `[REDACTED:<종류>]`(`phone`, `rrn`, `email`, `card`, `address`)로 바꾸고 줄은 남긴다.** 어디에도 저장하지 않는다. 값이 맞는지 확인하려고 지문을 계산할 때 OpenBao transit에 값을 보내지만(스캔과 같다) transit은 저장하지 않는다. git이 추적하지 않는 파일의 고객정보는 되돌릴 수 없으므로 확인 화면에 "복구 불가"로 따로 보이고, 체크하지 않으면 `untracked-irreversible`로 건너뛴다. 동의는 화면에 보인 것에만 미친다: 점검이 그 파일 목록을 실행 기록에 저장하고, 적용은 추적되지 않는 파일 가운데 그 목록에 있는 것만 가린다.
18. **[권고안으로 확정] 추적되지 않는 파일의 비밀 값은 추적되는 파일과 같이 적용한다.** 원본이 OpenBao에 남기 때문이다. 단, 프로젝트 폴더 안의 다른 저장소(하위 폴더에 `.git`이 있는 경우, submodule 포함)에 든 파일은 `nested-repository`로 건너뛴다. 바깥 저장소에서는 "추적되지 않는 파일"로 보이지만 안쪽 저장소의 커밋되지 않은 변경일 수 있다.
19. **[권고안으로 확정] manifest는 프로젝트 폴더의 `secrets-manifest.yml`이고, YAML 라이브러리 없이 이 형식 하나만 쓰고 읽는다.** 형식은 설계의 예와 같다(`version: 1`, `entries`의 `name`, `category`, `action`, `store`, `locations`의 `file`, `line`). 쓰는 쪽은 정해진 모양만 내고, 읽는 쪽은 그 모양만 받는다. 주석, 모르는 키, 다른 `version`, 앵커, 흐름 표기가 있으면 읽기를 거부하고 적용은 시작하지 않는다(조건 바). 이어 쓰면서 사람이 넣은 내용을 조용히 잃지 않기 위해서다. 다른 안: `go.yaml.in/yaml`. 어떤 YAML도 읽지만 주석과 키 순서를 보존해 다시 쓰려면 노드 API로 같은 일을 해야 하고, 형식 하나를 위해 의존성이 는다(`AGENTS.md` "Add a dependency only when the standard library cannot reasonably do the job").
20. **[권고안으로 확정] manifest 항목은 placeholder 표기마다 하나이고 이름으로 식별한다.** 한 묶음이 `.yml`과 `.sh`에 걸치면 `ext.db.main.password`와 `EXT_DB_MAIN_PASSWORD` 두 항목이 같은 `store`를 가리키고, 각 항목은 그 표기가 쓰인 위치만 갖는다. 소스에서 본 placeholder를 그대로 찾을 수 있다. 제거한 파일의 항목은 설정 표기 이름, `action: file-removed`, `line` 없는 위치다. `category`는 항목의 분류 그대로다(`storage-credential`, `ssh-credential`, `partner-session`, `other-secret`. 설계 예시의 `ssh-key-file`은 코드에 없는 분류라 쓰지 않는다). 항목은 이름순, 위치는 파일과 줄 순이다. 이미 있는 이름에는 위치를 더하고(같은 파일과 줄은 한 번) `category`, `action`, `store`는 새 값으로 바꾼다. 줄 번호는 적용한 뒤의 줄이다. 고객정보는 넣지 않는다.
21. **[권고안으로 확정] 적용 기록은 테이블 셋이다.** `apply_run`(프로젝트, 스캔, 요청자, 상태, 계획 지문, 조건 점검 결과, 복구 불가 파일 목록, 건수, 실패 사유, 확인 스캔), `apply_item`(위치 하나의 결과: 적용, 건너뜀과 사유, 실패와 사유, 적용한 뒤의 줄, 이름, 저장 경로와 버전, 코드 수정 필요), `apply_file`(파일 하나의 쓰기 전후 해시와 임시 파일 이름. manifest도 한 줄이다). 묶음에는 `applied_at`, `store_path`를 더한다. 값은 어디에도 없다.
22. **[권고안으로 확정] 한 프로젝트에서 스캔과 적용은 겹치지 않고, 적용이 걸려 있는 동안 판정을 바꿀 수 없다.** 점검 중, 대기 중, 실행 중인 적용이 있으면 스캔 요청, 판정, 묶음 옮기기는 거부된다(`db.ErrApplyActive`, 화면은 409와 안내). 적용 요청은 화면이 보여 준 계획의 지문(`plan_digest`: 스캔 ID, 묶음 ID, 판정, 이름, 구성원 ID의 SHA-256)을 함께 보내고, 점검 뒤에 판정이 바뀌어 지문이 다르면 거부된다. 사람이 본 것과 다른 것이 적용되지 않는다.
23. **[권고안으로 확정] (바꿈) 중간에 죽어도 값이 사라지지 않고, 다음 점검이나 적용이 기록을 맞춘다.** 규칙은 Global Constraints의 R1~R9다. 요지: 저장이 확인된 값만 소스에서 지운다. 파일을 바꾸기 직전에 "이 파일을 이 해시로, 이 임시 파일을 거쳐 바꾼다"를 postgres에 적고, 바꾼 뒤 "바꿨다"를 적는다. 모든 점검과 적용은 시작할 때 그 프로젝트의 "바꾼다"로만 남은 기록(실패했거나 버려진 실행의 것 포함)을 디스크와 맞춘다: 파일의 해시가 "바꾼 뒤" 해시면 적용된 것으로, 아니면 실패로 닫고 남은 임시 파일을 지운다. 이미 저장한 값은 저장된 바이트의 지문이 같아 다시 쓰지 않는다. 그 프로젝트의 어느 실행이든 스스로 바꾼 파일(지금 해시가 기록의 "바꾼 뒤" 해시)은 "커밋되지 않은 변경"으로 세지 않는다.
24. **[권고안으로 확정] 적용한 외부화 묶음의 판정과 이름은 고정된다.** 이름이 바뀌면 소스의 placeholder, manifest, 저장 경로가 어긋난다. `Decide`는 `applied_at`이 있는 외부화 묶음의 변경을 `triage.ErrNotAllowed`로 거부하고, `MoveFinding`은 그런 묶음의 마지막 구성원을 옮기지 않는다(묶음이 지워지면 이름이 풀려 다른 값이 같은 경로를 쓴다). 설계의 "판정은 적용 전까지 바꿀 수 있다"의 뒷면이다.
25. **[권고안으로 확정] 적용이 파일을 하나라도 바꿨으면 worker가 같은 트랜잭션에서 확인 스캔을 요청한다.** 그 트랜잭션은 실행을 먼저 닫고 스캔을 넣는다(걸린 적용이 있으면 스캔 삽입이 거부되기 때문이다). 스캔에는 `apply_id`가 남는다. 확인 스캔 뒤에는 적용한 묶음에 마지막 스캔의 구성원이 없어 판정 목록에서 사라지므로, 판정 화면에 "적용됨" 탭을 더해 `applied_at`이 있는 묶음을 이름, 분류, 저장 경로, 적용한 위치, 코드 수정 필요와 함께 보인다. 계획 6의 리포트는 `apply_item`을 읽는다. 확인 스캔이 적용한 묶음의 값을 다시 찾으면 그 묶음은 판정 목록에도 "적용됨 · 다시 발견"으로 나오고 다음 적용의 대상이 된다.
26. **[권고안으로 확정] (바꿈) 오탐으로 판정한 값의 임시 원본은 적용 작업이 지우고, 다음 스캔도 지운다.** 계획 4의 결정 14와 설계("오탐으로 판정되면 지운다")대로, 적용 작업은 끝날 때 그 프로젝트에서 같은 지문의 모든 묶음이 오탐인 값의 `pending/` 원본을 지운다(실패는 로그에만 남긴다). 스캔 실행기도 그런 값을 보관하지 않고(`has_original = false`), 지금 있는 "이번 스캔에 없는 지문 지우기"가 남은 것을 지운다. 적용한 값은 소스에서 사라졌으므로 확인 스캔의 같은 정리로 지워진다. 오탐을 다른 판정으로 바꾸면 다음 스캔이 다시 보관한다(원본 보기의 "다시 스캔하면 보관됩니다" 안내 그대로). worker가 둘 이상일 때의 경합(`docs/next-steps.md`)은 그대로 남는다. 적용도 worker 하나를 전제로 한다.
27. **[권고안으로 확정] (바꿈) OpenBao 정책은 worker에 `secret/data/projects/*`의 `read`를 더하고, web 정책은 그대로 둔다.** worker는 이미 `create`, `update`가 있고, 저장된 바이트로 확인하려면 읽어야 한다. worker는 소스에서 그 값을 이미 읽는다. web의 `projects/*` 읽기는 계획 3부터 정책에 있고(결정 기록 0017) 설계 6절의 표("worker 쓰기, web 읽기")와 같으므로 빼지 않는다. 다만 이 계획에서 web에는 그 경로를 읽는 코드가 없고, 화면은 저장 경로만 보인다. self-init은 한 번만 실행되므로 `config.hcl`을 고친 뒤에는 `openbao-data`, `openbao-secrets` 볼륨을 지우고 다시 띄워야 한다. **이 계획부터 그 볼륨에는 추적되지 않는 파일에서 빼낸 값의 유일한 사본이 있을 수 있다.** `docker compose down -v`는 한 번도 적용하지 않은 환경에서만 안전하다고 `docs/local-run.md`에 경고하고, "볼륨을 지우지 않고 정책을 바꾸는 방법"을 `docs/next-steps.md`에 남긴다.
28. **[권고안으로 확정] 화면은 시안을 새로 만들지 않고 확인받은 토큰과 구성 요소로 만든다.** `docs/design/README.md`의 색, 글꼴, 간격과 `internal/web/assets/app.css`의 `card`, `facts`, `table`, `badge`, `notice`, `skips`, `btn`을 쓰고 frontend-design 스킬로 구현한다. 적용의 상태 색은 스캔의 것(`queued`, `running`, `succeeded`, `failed`)을 그대로 쓴다. 역할은 `user`, `admin` 모두 적용할 수 있다(설계 7절).
29. **[권고안으로 확정] 도구는 커밋하지 않고, 저장소를 바꾸는 git 명령을 실행하지 않는다.** 인덱스도 쓰지 않는다(`--no-optional-locks`). 되돌리기는 개발자가 `git checkout`으로 한다.
30. **[권고안으로 확정] worker의 uid를 compose에서 정할 수 있게 하고 `restart: unless-stopped`를 둔다.** Linux 호스트에서는 uid 65532가 개발자의 파일을 쓸 수 없고 worker가 쓴 파일의 소유자도 그 uid가 되므로, `SE_UID`, `SE_GID`(기본 65532)로 worker의 사용자를 정하고 `make-secrets.sh`가 worker의 secret-id 소유자를 그 값으로 맞춘다. 적용 중에 worker가 죽으면 임대가 끝난 뒤 다시 뜬 worker가 이어 간다.
31. **[권고안으로 확정] `docs/next-steps.md`의 항목은 아래 표대로 한다.**

## Global Constraints

- `AGENTS.md`의 모든 규칙을 따른다. 작업 하나를 끝낼 때마다 `make check`가 통과해야 한다. 코드, 주석, 커밋 메시지는 영문, `CHANGELOG.md`와 `docs/` 아래는 한글로 쓴다.
- 설계의 실패 조건이다. 각 줄 끝의 테스트가 그 조건을 붙잡는다.
  - 원본 값이 postgres, valkey, 로그, 리포트, PDF, manifest 중 어디에든 평문으로 남는다. (`TestApply_NoValueOutsideVault`, `TestEncode_HoldsNoValue`, Task 15의 12번)
  - 사람의 판정 없이 소스가 바뀐다. (`TestPlan_OnlyDecidedBundles`, `TestApply_UndecidedBytesUntouched`, `TestConfirmApply_PlanChanged`, `TestApply_ConsentCoversShownFilesOnly`)
  - 소스에서 값이 지워졌는데 OpenBao에는 저장되지 않아 값이 사라진다. (`TestApply_StoreFailureLeavesSource`, `TestApply_VerifyMismatchLeavesSource`, `TestApply_KeyFileNotStoredKeepsFile`, `TestApply_CrashAfterStore`)
  - 고객정보의 사본이 도구 안에 새로 만들어진다. (`TestApply_CustomerDataNotStored`, `TestPlan_KeyFileWithCustomerData`)
  - 커밋되지 않은 변경이 있는 작업본을 도구가 덮어쓴다. (`TestCheck_DirtyTree`, `TestApply_DirtyTreeRefused`, `TestInspect_Dirty`, `TestInspect_HiddenChanges`, `TestApply_ChangedFileSkipped`)
- 실행 규칙 R1~R9.
  - **R1 (맞추기)** 모든 `apply-check`와 `apply` 작업은 계획을 세우기 전에, 그 프로젝트의 `apply_file` 가운데 `written`이 false인 줄(어느 실행의 것이든)을 디스크와 맞춘다. 지금 해시가 `after_hash`면(제거 기록은 파일이 없으면) `written`으로 하고 그 파일의 `writing` 항목을 `applied`로, 묶음의 `applied_at`, `store_path`를 채운다. 아니면 `writing` 항목을 `failed`와 `interrupted`로 닫는다. 어느 쪽이든 기록된 임시 파일이 남아 있으면 지우고 그 줄을 닫는다.
  - **R2 (조건)** `apply` 작업은 조건 여섯 가지를 처음부터 다시 점검한다. 어긋나면 파일도 OpenBao도 건드리지 않고 정해진 사유로 실패로 닫는다. 그 프로젝트의 `apply_file`(어느 실행이든, manifest 포함)에 있고 지금 해시가 그 줄의 `after_hash`인 파일, 제거 기록이 있고 지금 없는 파일은 "커밋되지 않은 변경"으로 세지 않는다.
  - **R3 (저장 확인)** 외부화 위치는, 이번 시도에서 그 묶음의 저장 경로를 다시 읽고 **저장된 바이트의 HMAC을 다시 계산해** 묶음의 지문과 같음을 확인한 뒤에만 치환 목록에 들어간다. 저장된 `fingerprint` 필드는 확인에 쓰지 않는다.
  - **R4 (값 다시 읽기)** 값은 소스의 저장된 위치에서 다시 읽고, 다시 계산한 지문이 묶음의 지문과 같아야 한다. 다르면 `value-mismatch`로 건너뛴다.
  - **R5 (파일 제거)** 파일은 그 파일 전체 값이 R3을 통과했을 때만 제거한다. 통과하지 못하면 그 파일의 모든 대상을 같은 사유로 건너뛴다.
  - **R6 (먼저 적기)** 파일 하나의 변경은 한 번의 `rename`(또는 제거)이다. 그 전에 `apply_file`(`before_hash`, `after_hash`, 임시 파일 이름, `written` false)과 그 파일의 `apply_item`(`writing`, 적용 뒤의 줄)을 한 트랜잭션으로 적고, 뒤에 `written`, `applied`, 묶음의 `applied_at`, `store_path`를 한 트랜잭션으로 적는다. manifest를 쓰는 일도 같은 두 기록을 거친다.
  - **R7 (다시 실행)** 파일의 지금 해시가 스캔 때 해시면 바꾼다. 아니면 `file-changed`로 건너뛴다(이 프로젝트가 이미 바꾼 파일은 R1이 적용된 것으로 맞춰 두었으므로 그 대상은 이미 `applied`다).
  - **R8 (manifest)** manifest는 치환 단계 뒤에, 그 프로젝트의 `apply_item` 가운데 적용되었고 아직 manifest에 넣지 않은 것(이전 실행의 것, R1이 맞춘 것 포함) 전부로 한 번 쓴다. 쓴 뒤 `in_manifest`를 표시한다. 표시 전에 죽으면 다음 적용이 같은 항목을 다시 합치고, 합치기는 여러 번 해도 결과가 같다.
  - **R9 (멈추기)** 작업의 context가 끝나면 파일 사이에서만 멈춘다. `rename`을 한 파일의 뒤 기록은 취소된 context에서 떼어 낸 context(제한 5초)로 쓴다. 그 기록마저 실패하면 R1이 다음에 맞춘다.
- 값은 worker의 메모리에만 있다. 값을 담는 타입은 `String`, `Format`, `LogValue`, `MarshalJSON`이 가린 형태를 돌려주고, 저장 단계와 파일 하나의 치환이 끝나면 0으로 지운다. 텍스트 값은 파일 내용 버퍼의 일부를 가리키지 않고 복사본을 쓴다. 0으로 지우는 버퍼를 아직 쓸 다른 값이 가리키면 안 된다(파일 전체 값이 그 파일 내용 버퍼 자체일 때 포함). 오류, 실패 사유, 건너뛴 사유는 정해진 문구와 코드만 쓰고 오류의 글을 넣지 않는다.

- 커밋, 인덱스 변경, 되돌리기. 개발자가 `git diff`로 확인하고 git으로 한다.
- git 히스토리에 남은 값의 제거, 원격 저장소, AWS Secrets Manager로 옮기기, 키 폐기와 재발급 (설계의 비목표)

- 저장한 값의 이스케이프 풀기. 값은 소스에 적힌 글자 그대로 저장된다
- JSP, JS, HTML의 자동 치환 (설계의 비목표. 그런 구성원이 있는 묶음은 통째로 건너뛴다)
- 고객정보가 있을 수 있는 파일, 목록에 없고 PEM뿐이 아닌 파일을 키 파일로 통째로 옮기는 일
- 외부화한 값을 도구의 화면에서 다시 보기. 화면은 저장 경로만 보인다
- 볼륨을 지우지 않고 OpenBao 정책을 바꾸는 방법 (`docs/next-steps.md`)
- 리포트와 PDF (계획 6). 자료는 `apply_run`, `apply_item`, `audit_event`에 쌓인다
- 대시보드의 추이 (계획 7). 확인 스캔이 그 한 점이 된다
- 한 파일 안의 같은 값에 다른 이름 주기, 호스트·포트·계정의 자동 묶기, 스캔 쪽 파일 열기 통합, worker를 둘 이상 두는 구성, 네트워크 나누기 (`docs/next-steps.md`)
- 주석이나 손으로 고친 내용이 든 manifest의 보존. 읽을 수 없으면 적용을 시작하지 않는다
