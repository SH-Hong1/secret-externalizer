# 대시보드 Implementation Plan (계획 7/7)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 로그인한 사용자가 `/dashboard`에서 남은 항목(지난 스캔 대비 증감), 외부화 완료, 삭제·마스킹 완료, 오탐, 보류 건수와, 스캔별·분류별로 쌓은 남은 항목 추이, 분류별 남은 항목, 오탐이 많은 규칙, 프로젝트별 표(마지막 스캔, 남은 항목, 완료율, 보류)를 보고, 프로젝트와 기간으로 거른다. 대시보드에는 값도, 미리보기도, 지문도 없다.

**Architecture:** 대시보드는 저장하지 않고 열 때마다 postgres에서 읽는다. `db.Store.Dashboard`가 한 스냅숏 트랜잭션에서 프로젝트마다의 요약(`readTotals`를 그대로 쓴다), 성공한 스캔마다의 분류별 남은 묶음 수, 규칙별 오탐 수를 읽고, 순수 함수 `dashboard.Build`가 합치고 추이의 단계를 만든다. 추이 차트는 라이브러리 없이 서버가 그린 인라인 SVG다(`internal/web/chart.go`가 좌표를 계산하고 템플릿이 그린다). 스크립트를 더하지 않고 CSP를 바꾸지 않는다.

**Tech Stack:** Go 1.27, postgres 18, `html/template`, tailwindcss 4. 새 의존성도 새 정적 파일도 없다.

**Spec:** `docs/superpowers/specs/2026-11-18-secret-externalizer-design.md` (2절 실패 조건, 5절 "스택 세부", 7절, 8절 "대시보드", 10절 8단계, 11절). 결정 기록 0027, 0036, 0042, 0044.

## 검토 때 정해 주실 것

설계 문서가 정하지 않은 내용이다. 각 항목의 첫 문장이 이 계획이 따르는 안이다. **[권고안으로 확정]** 은 2026-11-20의 지시("묻지 말고 권고안으로 정하고 문서로 남긴다")에 따라 작성자가 정한 항목이다. 구현하면서 바꾼 것은 결정 기록 0047에 모은다.

1. **[권고안으로 확정] 계획도 PR도 하나다.** Task 다섯 개이고 화면 하나다.
2. **[권고안으로 확정] 차트 라이브러리를 넣지 않고 서버가 SVG로 그린다.** 설계 5절의 [제안]은 "차트용 라이브러리 하나를 정적 파일로 포함"이고 11절은 선택을 만드는 사람에게 맡긴다. 그릴 것은 막대를 쌓은 차트 하나(막대 30개 이하, 분류 5개)다. Go가 좌표를 계산해 `<rect>`를 내면 스크립트가 필요 없고, CSP(`default-src 'self'`)가 그대로이며, 숫자와 그림이 같은지를 Go 테스트로 붙잡을 수 있고, 고정할 버전과 체크섬이 늘지 않는다(`AGENTS.md`: 표준 라이브러리로 할 수 있으면 의존성을 더하지 않는다). 막대 위에 마우스를 올리면 SVG `<title>`이 수를 보이고, 차트 아래 "표로 보기"에 같은 숫자의 표가 있다. 다른 안: Chart.js나 uPlot을 정적 파일로 넣는다. 확대, 범례 끄기 같은 상호작용을 얻지만 자료를 스크립트에 넘길 길(JSON 주소나 `data-` 속성)과 스크립트 파일 하나가 늘고, 그림을 테스트할 수 없다. 결정 기록 0046.
3. **[권고안으로 확정] 건수의 단위는 묶음이고, 숫자는 프로젝트의 마지막 성공한 스캔의 리포트 요약과 같다.** 프로젝트마다 `readTotals`(리포트가 쓰는 그 함수)를 마지막 성공한 스캔과 그 앞의 성공한 스캔에 한 번씩 부른다. **남은 항목 = 미판정 + 보류 + 적용 대기**(= 찾은 항목 − 오탐)이고, 타일 아래에 그 셋을 나눠 적는다. 보류 타일은 남은 항목의 일부다. 외부화 완료와 삭제·마스킹 완료는 묶음 수와 위치 수를 함께 보인다. 여러 프로젝트를 볼 때는 프로젝트마다의 수를 더한다.
4. **[권고안으로 확정] 증감은 "지난 스캔 대비"다.** 프로젝트마다 (마지막 성공한 스캔의 남은 항목 − 그 앞 성공한 스캔의 남은 항목)이고, 여러 프로젝트면 앞 스캔이 있는 프로젝트의 차이를 더한다. 앞 스캔이 있는 프로젝트가 하나도 없으면 "이전 스캔 없음"이다. 기간 필터와 무관하다.
5. **[권고안으로 확정] 추이를 위한 스냅숏 테이블을 만들지 않는다. 추이의 한 점은 "그 스캔이 찾은 묶음 가운데 지금 오탐이 아닌 것"의 수다.** 판정은 지금의 것이다(리포트와 같다, 결정 기록 0042). 그래서 추이가 내려가는 것은 적용으로 값이 소스에서 사라졌을 때이고, 오탐으로 판정하면 그 묶음은 지난 점에서도 빠진다(오탐은 처음부터 남은 항목이 아니었다). 다른 안: 스캔이 끝날 때 건수를 저장한다. 판정은 스캔이 끝난 뒤에 하므로 스캔 종료 시점의 수는 전부 "미판정"이고, 지금 있는 스캔에는 저장된 수가 없어 같은 계산으로 채워야 한다. 다른 안: `audit_event`를 되감아 그때의 판정을 만든다. 묶음 옮기기 때문에 정확히 되돌릴 수 없다(0042). `docs/next-steps.md`의 "스냅숏이 필요한지 정한다"는 이것으로 닫는다. 결정 기록 0045.
6. **[권고안으로 확정] 추이의 막대 하나는 성공한 스캔 하나이고, 여러 프로젝트를 볼 때는 그 스캔이 끝난 시각의 "프로젝트마다 마지막 성공한 스캔의 수를 더한 값"이다.** 스캔이 끝난 시각 순으로 늘어놓고, 스캔이 끝날 때마다 그 프로젝트의 수를 바꿔 넣은 합을 그린다. 프로젝트 하나만 보면 스캔마다의 수 그대로다. 새 프로젝트가 처음 스캔되면 합이 오른다(알게 된 남은 항목이 는 것이다). 막대는 새것부터 30개(`dashboard.MaxPoints`)까지이고 넘으면 "이전 스캔 N개는 싣지 않았습니다"를 적는다.
7. **[권고안으로 확정] 기간 필터는 추이에만 적용한다: 전체(기본), 최근 7일, 30일, 90일.** 그 기간에 끝난 성공한 스캔만 막대가 된다. 기간 전에 끝난 스캔은 막대가 되지 않지만, 그 프로젝트의 수는 합에 들어 있다(기간 시작 때의 상태). 타일, 분류별, 규칙, 프로젝트 표는 언제나 지금 상태이고 화면에 "기간은 추이에만 적용됩니다"를 적는다. 다른 안: 기간이 규칙 통계(그 기간에 내린 오탐 판정)와 증감(기간 시작 대비)에도 걸린다. 한 화면에 "지금"과 "그 기간"의 숫자가 섞여 읽기 어렵다.
8. **[권고안으로 확정] 프로젝트 필터는 타일, 추이, 분류별, 규칙에 적용하고, 프로젝트 표는 언제나 모든 프로젝트를 보인다.** 표의 프로젝트 이름은 그 프로젝트로 거른 대시보드로, "프로젝트 열기"는 프로젝트 화면으로 간다. 고른 프로젝트의 줄은 표시한다.
9. **[권고안으로 확정] "오탐이 많은 규칙"은 마지막 성공한 스캔이 찾은 묶음을 규칙(도구와 규칙 이름)마다 세어, 오탐으로 판정된 묶음이 많은 순으로 10개(`dashboard.MaxRules`)다.** 줄마다 오탐 묶음 수, 그 규칙이 찾은 묶음 수, 비율을 보인다. 한 묶음을 두 규칙이 찾았으면 둘 다에 센다. 오탐이 0인 규칙은 싣지 않는다.
10. **[권고안으로 확정] 완료율 = 완료 ÷ (완료 + 남은 항목), 완료 = 외부화 완료 묶음 + 삭제·마스킹 완료 묶음.** 내림한 백분율이다. 분모가 0이면 "—"다. 적용한 뒤 다시 발견된 묶음은 완료와 남은 항목에 모두 세어진다(리포트의 셈과 같다).
11. **[권고안으로 확정] 주소는 `GET /dashboard?project=<ID>&period=<all|7d|30d|90d>`이고 `user`와 `admin` 모두 본다.** 머리 띠 메뉴의 첫 자리에 "대시보드"를 둔다. 홈(`/`)과 로고의 링크는 그대로다. `project`나 `period`가 없거나 빈 값이면 주지 않은 것이다(양식의 "전체"가 빈 값을 보낸다). `project`가 비어 있지 않은데 양의 정수가 아니거나 `period`가 모르는 값이면 400, 없는 프로젝트면 404다. 필터는 스크립트 없는 `GET` 양식이다.
12. **[권고안으로 확정] 분류의 색 다섯 개를 새로 정해 `docs/design/README.md`에 적는다.** 시안에는 판정의 색만 있고 분류의 색이 없다. Task 4에서 dataviz 스킬의 방법(검증 스크립트 포함)으로 흰 면 위에서 구분되는 다섯 색을 고르고, 색만으로 구분하지 않게 범례의 글자, 막대 조각 사이의 1px 틈, `<title>`, 표를 함께 둔다. 대시보드 시안은 새로 만들지 않고(계획 5, 6과 같다) 확인받은 토큰과 구성 요소(`tiles`, `bars`, `table`, `card`)로 만든다. 실제 확인(Task 5)에서 화면 그림을 남긴다.

## Global Constraints

- `AGENTS.md`의 모든 규칙을 따른다. Task 하나를 끝낼 때마다 `make check`가 통과해야 한다. 코드, 주석, 커밋 메시지는 영문, `CHANGELOG.md`와 `docs/` 아래는 한글로 쓴다. 화면의 문구는 한글이다.
- 설계의 실패 조건: **원본 값이 어디에든 평문으로 남는다.** 대시보드의 자료는 postgres에서만 오고, 미리보기·지문·주변 줄을 고르는 쿼리가 없다. `dashboard` 패키지의 타입에는 그것을 담을 필드가 없다(`TestTypes_HoldNoValueField`).
- 화면에 실리는 글자는 모두 `html/template`이 이스케이프한다. `template.HTML`·`template.CSS`·`template.JS`·`template.URL`로 바꾸지 않는다. CSP를 넓히지 않고 인라인 스크립트와 `style` 속성을 쓰지 않는다. SVG의 색은 `app.css`의 클래스로 준다.
- DB를 읽는 요청은 지금의 제한(5초, `usesStore`) 안에 있다. `db.Store.Dashboard`는 `readOnly` 트랜잭션 하나로 읽는다. SQL은 `internal/db`에만 있다.
- 마이그레이션은 더하지 않는다(새 테이블도 인덱스도 없다). Task 2의 확인에서 인덱스가 필요하면 `0009`를 더하고 계획을 고친다.
- 건수는 묶음 수다. "찾은 묶음"의 뜻은 `db/report.go`의 `reportFound`와 같다(그 스캔의 `location`이 있는 `finding`의 묶음, 분류는 ID가 가장 작은 구성원의 것).
- 테스트 예제 값은 가짜임이 분명해야 한다.
- 결정 기록은 0045(대시보드가 세는 것과 추이), 0046(차트를 서버가 SVG로 그린다), 0047(계획 7을 구현하면서 대신 정한 것)이다.

## Review Focus

1. 빈 상태: 프로젝트가 없거나, 스캔이 없거나, 실패한 스캔만 있거나, 기간에 끝난 스캔이 없어도 0으로 나누지 않고 각 절이 "없습니다"를 말한다. (Task 1 `TestBuild_Empty`, Task 4 `TestNewBarChart_Empty`, `TestHandleDashboard_Empty`, `TestHandleDashboard_NoScans`)
2. 숫자의 일치: 타일의 수가 마지막 성공한 스캔의 리포트 요약과 같고, 추이의 마지막 막대의 합이 남은 항목 타일과 같으며, 막대 조각의 높이 합이 막대의 높이다. (Task 1 `TestBuild_LastStepIsRemaining`, Task 2 `TestDashboard_TotalsMatchReport`, `TestDashboard_PointsMatchTotals`, Task 4 `TestNewBarChart_Stacks`)
3. 기간 밖의 프로젝트: 마지막 스캔이 기간 전에 끝난 프로젝트의 수도 추이의 합에 들고, 막대는 되지 않는다. (Task 1 `TestBuild_Baseline`, Task 2 `TestDashboard_Period`)
4. 많은 스캔과 큰 수: 스캔이 30개를 넘으면 새것 30개만 그리고 싣지 않은 수를 적는다. 수가 수만이어도 눈금과 막대가 그림 안에 있다. (Task 2 `TestDashboard_Cap`, Task 4 `TestNewBarChart_Large`)
5. 이름에 든 글자: 프로젝트 이름과 규칙 이름에 HTML이 있어도 표, 선택 상자, SVG `<title>`에서 이스케이프된다. (Task 4 `TestHandleDashboard_Escapes`)
6. 잘못된 주소: `project=abc`, `project=0`, `period=1y`, 없는 프로젝트. (Task 4 `TestHandleDashboard_BadQuery`, Task 2 `TestDashboard_UnknownProject`)
7. 다른 프로젝트: 프로젝트로 거르면 다른 프로젝트의 스캔, 묶음, 규칙이 섞이지 않는다. (Task 2 `TestDashboard_ProjectFilter`)

  ```go
  // Package dashboard shapes the numbers of the dashboard: what the newest
  // succeeded scan of each project leaves to do, and how that changed from
  // scan to scan. Nothing here holds a value, a fingerprint, a preview or a
  // line of source.
  package dashboard

  const (
  	MaxPoints = 30 // the most scans the trend shows
  	MaxRules  = 10 // the most rules the false-positive list shows
  )

  // ErrUnknownPeriod means a period name is not one of the Period constants.
  var ErrUnknownPeriod = errors.New("unknown period")

  // Period is the span of time the trend covers.
  type Period string

  const (
  	PeriodAll     Period = "all"
  	PeriodWeek    Period = "7d"
  	PeriodMonth   Period = "30d"
  	PeriodQuarter Period = "90d"
  )

  // ParsePeriod returns the period named s. The empty string is PeriodAll.
  func ParsePeriod(s string) (Period, error)

  // Since returns the start of the period that ends at now, or the zero
  // time for PeriodAll.
  func (p Period) Since(now time.Time) time.Time

  // Filter selects what the dashboard shows: one project, or every project
  // when Project is zero, and the trend of the scans that finished at or
  // after Since, or of every scan when Since is zero.
  type Filter struct {
  	Project project.ID
  	Since   time.Time
  }

  // Split is a number of bundles that are left, by the verdict they have
  // now: none, hold, or externalize or redact.
  type Split struct{ Undecided, Hold, Pending int }

  // Total returns the bundles of s.
  func (s Split) Total() int

  // Point is what one succeeded scan found and is not a false positive,
  // by category. Baseline marks a scan that finished before the trend
  // starts: it is not shown, but its project counts from the start.
  type Point struct {
  	Project   project.ID
  	Scan      scan.ID
  	At        time.Time
  	Baseline  bool
  	Remaining map[finding.Category]Split
  }

  // ProjectState is a project with its newest scan in any state (a zero ID
  // when it was never scanned) and the numbers of its newest succeeded scan
  // (Basis) and of the succeeded scan before that (Previous); each is zero
  // when there is no such scan.
  type ProjectState struct {
  	Project        project.Project
  	Last           scan.Scan
  	Basis          scan.ID
  	Previous       scan.ID
  	Totals         report.Totals
  	PreviousTotals report.Totals
  }

  // Rule counts the bundles a rule of a scanner found in the newest
  // succeeded scans, and those of them that are false positives.
  type Rule struct {
  	Tool, Rule             string
  	Bundles, FalsePositive int
  }

  // Data is what the database tells for a dashboard. Projects holds every
  // project by name, whatever the filter. Points holds, for the projects of
  // the filter, the newest MaxPoints succeeded scans of the period in the
  // order they finished and, as baselines, the newest succeeded scan of
  // each project that finished before the first of them. PointTotal counts
  // the succeeded scans of the period. Rules is ordered by FalsePositive,
  // largest first.
  type Data struct {
  	Projects   []ProjectState
  	Points     []Point
  	PointTotal int
  	Rules      []Rule
  }

  // Step is one bar of the trend: the scan that finished, and what was left
  // in the projects of the filter once it had.
  type Step struct {
  	Project   project.ID
  	Name      string // the project's name
  	Scan      scan.ID
  	At        time.Time
  	Remaining map[finding.Category]int
  	Total     int
  }

  // Row is one line of the project table. Rate is the share of done
  // bundles in percent, or -1 when the project has nothing done and
  // nothing left. Scanned is false when no scan of the project succeeded.
  type Row struct {
  	Project   project.Project
  	Last      scan.Scan
  	Scanned   bool
  	Remaining int
  	Hold      int
  	Rate      int
  }

  // Dashboard is the dashboard for one filter, ready to be shown.
  type Dashboard struct {
  	Project       project.ID // the filter's project, zero for all
  	Scanned       int        // projects of the filter with a succeeded scan
  	Remaining     Split
  	Delta         int  // Remaining.Total() minus that of the scans before
  	HasDelta      bool // false when no project of the filter has a scan before
  	Externalized  report.Count
  	Redacted      report.Count
  	FalsePositive report.Count
  	Trend         []Step
  	TrendMore     int // scans of the period the trend leaves out
  	Categories    map[finding.Category]Split
  	Rules         []Rule
  	Rows          []Row
  }

  // Build shapes d for the filter f. It keeps no slice or map of d.
  func Build(d Data, f Filter) Dashboard
  ```

- `Build`의 규칙:
  - "필터의 프로젝트"는 `f.Project`가 0이면 `d.Projects` 전부, 아니면 그 하나다. `Remaining`, `Externalized`, `Redacted`, `FalsePositive`는 `Basis`가 0이 아닌 필터의 프로젝트의 `Totals`를 더한 것이다(`Remaining`의 `Undecided`, `Hold`, `Pending`은 `Totals`의 같은 이름의 `Bundles`).
  - `Delta`는 `Previous`가 0이 아닌 필터의 프로젝트마다 (`Totals`의 남은 묶음 − `PreviousTotals`의 남은 묶음)을 더한 것이고, 그런 프로젝트가 있으면 `HasDelta`다.

  ```go
  }
  ```

- 차트의 규칙: viewBox는 960×300이고 왼쪽 48, 아래 28, 위 12, 오른쪽 8을 여백으로 둔다. 세로 눈금의 최댓값은 가장 큰 `Total` 이상의 가장 작은 "1, 2, 5 × 10ⁿ"이고(모두 0이면 1), 눈금은 0부터 최댓값까지 정수 간격("1, 2, 5 × 10ⁿ" 가운데 눈금이 여섯 개 이하가 되는 가장 작은 것)으로 놓는다(최댓값 1은 0, 1. 5는 0~5. 10은 0, 2, …, 10. 20은 0, 5, …, 20). `chartTick.Label`은 자릿수 구분 없는 십진 정수다. 막대는 고르게 놓고 폭은 40을 넘지 않는다. 조각의 위치는 쌓인 합을 반올림해 정하므로(조각마다 따로 반올림하지 않는다) 조각의 높이 합이 막대의 높이다. 수가 0인 조각은 내지 않는다. 막대 이름은 `#<스캔 번호>`이고, 막대가 15개를 넘으면 마지막 막대부터 하나 걸러 하나만 적는다. `newBarChart`는 프로젝트 하나를 골랐는지를 둘째 인자 `all bool`로 받는다(`newBarChart(steps []dashboard.Step, all bool) barChart`). `Title`은 `<프로젝트 이름> · 스캔 #N · <끝난 시각> · 남은 항목 T개`(전체 보기에서는 `전체 남은 항목 T개`)와 수가 0이 아닌 분류마다 `<분류> n개`다.
