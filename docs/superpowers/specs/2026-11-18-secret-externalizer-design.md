# 민감 정보 외부화 도구 설계 (1차)

- 작성일: 2026-11-18
- 프로젝트 이름: `secret-externalizer`
- 상태: 승인됨 (2026-11-18)

표기: **[확정]** 은 대화에서 사용자가 정한 내용, **[제안]** 은 작성자가 채운 내용이며 바꿀 수 있다.

## 1. 의도

레거시 소스에 박혀 있는 민감 정보를 소스 밖으로 빼내는 프로젝트가 진행 중이다. 이 도구는 그 프로젝트를 수행하는 개발자가 쓰는 작업 도구다. 개발자는 로컬에 있는 소스를 스캔하고, 탐지된 항목을 하나씩 판정하고, 판정된 항목을 placeholder로 바꾸고, 무엇을 어디서 뺐는지 기록으로 남긴다. 진행 상황은 리포트와 대시보드로 확인한다.

도구가 책임지는 범위는 "찾고, 사람이 판정하게 하고, 소스에서 빼내고, 기록하는 것"까지다. 빼낸 값을 AWS에 넣는 일, 앱이 다시 기동되게 만드는 일, 키를 폐기하고 바꾸는 일은 개발자와 devops 담당자의 몫이다.

## 2. 목표, 비목표, 실패 조건

### 목표 [확정]

1. 로컬 소스에서 민감 정보를 탐지한다.
2. 탐지 항목마다 사람이 판정한다. 판정되지 않은 항목은 소스에 반영되지 않는다.
3. 판정된 항목을 소스에서 제거하고 `${이름}` placeholder로 바꾼다.
4. 프로젝트 루트의 manifest 파일에 위치와 placeholder를 기록한다. 사람이 읽고 다음 작업에 참고하는 용도다.
5. 제거한 실제 값은 OpenBao KV에 보관한다.
6. 스캔별 리포트를 화면으로 제공하고 PDF로 내보낸다.
7. 대시보드에서 통계와 추이를 보여준다.
8. 로그인을 요구하고, 원본 값 보기는 `admin` 역할만 할 수 있다.
9. 코드와 구조가 Go 모범사례의 본보기가 될 수준이다.

### 비목표 (1차에서 하지 않음) [확정]

- 원격 저장소(GitHub 등) 대상 스캔과 인증 토큰 관리
- git 히스토리에 남은 값의 탐지와 제거
- AWS KMS, Secrets Manager 연동
- 치환 후 앱이 기동되는지 보장하는 일
- 키 폐기와 재발급
- AI를 이용한 전수 검사와 판정 보조 (2차 후보. 주소 탐지 보완이 가장 유력한 용도)
- trivy 연동
- 프론트에 하드코딩된 토큰의 자동 치환 (탐지와 리포트만 한다)
- 도구가 대신 커밋하는 일

### 실패 조건 (동작하더라도 실패로 보는 경우)

- 원본 값이 postgres, valkey, 로그, 리포트, PDF, manifest 중 어디에든 평문으로 남는다.
- 사람의 판정 없이 소스가 바뀐다.
- 소스에서 값이 지워졌는데 OpenBao에는 저장되지 않아 값이 사라진다.
- 고객정보의 사본이 도구 안에 새로 만들어진다.
- 커밋되지 않은 변경이 있는 작업본을 도구가 덮어쓴다.

## 3. 대상

### 사용자와 실행 환경 [확정]

- 사용자는 외부화 프로젝트를 수행하는 개발자다.
- 주로 개발자 PC에서 docker compose로 띄워 쓴다. 그래도 인증은 둔다. 마스킹되어 있어도 민감 정보를 다루는 도구이기 때문이다.
- 프로젝트 하나는 한 사람(주로 AA)이 맡아 진행한다. 여러 사람이 같은 프로젝트를 각자의 인스턴스로 나눠 작업하는 경우는 다루지 않는다.

### 대상 소스 [확정]

- Java, Spring Framework 구버전(3 계열)
- 빌드: Maven, Ant
- 배포: ssh로 접속해 실행하던 shell script
- 버전 관리: git
- 인코딩과 줄바꿈: EUC-KR(MS949)과 UTF-8, CRLF와 LF가 섞여 있다고 가정한다. 도구는 파일별로 인코딩을 판별해 탐지하고, 치환할 때 원래 인코딩과 줄바꿈을 그대로 보존한다.

### 민감 정보의 범위 [확정]

| 분류 | 예 |
|---|---|
| 제휴사 로그인 세션 | 세션 토큰, 쿠키, 제휴사 계정 |
| 스토리지 접속 정보 | DB 호스트, 포트, 계정, 비밀번호, JDBC URL |
| ssh 접속 정보 | 호스트, 계정, 비밀번호, 개인키 파일 |
| 고객정보 | 로그와 샘플 데이터 안의 전화번호, 주소 등 고객을 특정할 수 있는 정보 |

| 파일 | 내용 | 처리 |
|---|---|---|
| `.java` | 문자열 리터럴 | 탐지, 치환 |
| Spring XML 컨텍스트, `.properties` | dataSource 등 bean 설정 | 탐지, 치환 |
| `application.yml`, `application-*.yml` [확정] | 설정 값 | 탐지, 치환 |

| 개인키, 인증서 파일 | 파일 전체 | 탐지, 파일 제거 |
| JSP, JS, HTML | 하드코딩된 인증 토큰 | 탐지만 [확정] |

## 4. 검토한 구성 방식

### A. 단일 프로세스

웹 서버와 스캔 실행을 하나의 Go 바이너리에 둔다. 구성이 가장 단순하다. 로그인 화면을 받는 프로세스가 소스 쓰기, 스캐너 실행, OpenBao 쓰기 권한을 모두 가지므로 웹 쪽 취약점 하나로 전부 노출된다.

### B. web과 worker 분리 (선택) [확정]

하나의 Go 모듈에서 두 바이너리를 만들어 컨테이너를 나누고, postgres의 작업 큐로만 연결한다. web은 소스와 스캐너에 접근할 수 없고 worker는 포트를 열지 않는다. OpenBao 권한도 둘로 나뉜다. 컨테이너가 하나 늘고 작업 큐를 구현해야 한다.

### C. docker client로 스캐너 컨테이너를 매번 실행

처음 구상한 방식이다. 앱 컨테이너에 docker.sock을 넘겨야 하고 이는 호스트 root 권한과 같다. socket proxy로 범위를 좁혀도 컨테이너 생성 권한이 있으면 호스트 장악이 가능하다. 스캐너 컨테이너에 소스를 넘기려면 컨테이너 안 경로가 아닌 호스트 경로가 필요해 로컬 소스 대상에서는 구성도 까다롭다. 제외했다.

### 선택 이유

민감 정보를 다루는 도구이므로 권한 분리의 이점이 컨테이너 하나의 비용보다 크다. `cmd/` 아래 두 바이너리가 `internal/` 패키지를 공유하는 구조는 "Organizing a Go module"의 서버 프로젝트 배치와 같다.

## 5. 구성

```
브라우저 ─ web ──┬─ postgres (탐지 항목, 판정, 작업 큐, 통계, 감사 로그)
                 ├─ valkey (세션)
                 ├─ keycloak (로그인)
                 ├─ openbao (admin의 원본 보기, 읽기 전용)
                 └─ pdf (리포트 HTML을 PDF로 변환)

          worker ─┬─ postgres (작업 수신, 결과 기록)
                  ├─ openbao (원본 저장과 삭제, 지문 계산)
                  ├─ 작업 루트 디렉터리 마운트
                  └─ betterleaks, opengrep (os/exec)
```

### 컨테이너 [확정: 구성 요소, 제안: 세부]

| 컨테이너 | 역할 | 비고 |
|---|---|---|
| web | HTTP 서버, 화면, 판정 기록, 작업 요청 | 소스 마운트 없음, 스캐너 없음 |
| worker | 스캔, 적용, 재스캔 | 포트 없음. 스캐너 바이너리를 버전 고정으로 이미지에 포함 |
| postgres | 업무 데이터와 작업 큐 | Keycloak용 데이터베이스를 같은 인스턴스에 별도로 둔다 [제안] |
| valkey | 서버 측 세션 저장 | 쿠키에는 세션 ID만 담는다 |
| keycloak | OIDC 로그인, 역할 관리 | realm, client, 초기 사용자를 기동 시 import 파일로 구성 [제안] |
| openbao | 원본 값 보관, 지문 계산 | 재시작해도 데이터가 유지되어야 한다 |
| pdf | 리포트 HTML을 PDF로 변환 | 헤드리스 브라우저 기반. web만 접근하고 외부로 나가는 통신은 막는다 |

### 스택 [확정]

- 백엔드: Go
- 화면: Go `html/template` + htmx + tailwindcss
- 저장소: postgres, valkey, OpenBao
- 인증: Keycloak OIDC
- 탐지 도구: betterleaks, opengrep

### 스택 세부 [제안]

- tailwindcss는 Node 없이 standalone CLI로 빌드한다.
- 대시보드 차트용 라이브러리 하나를 정적 파일로 포함한다. CDN은 쓰지 않는다.
- HTTP 라우팅은 표준 라이브러리 `net/http`의 `ServeMux`, 로그는 `log/slog`를 쓴다.
- OIDC는 Authorization Code + PKCE 흐름으로 구현한다.
- web과 worker는 각각 AppRole로 OpenBao에 인증하고, 정책을 따로 둔다.

### 스캐너 호출 [확정: os/exec 방식]

- worker 이미지에 betterleaks와 opengrep 바이너리를 버전과 체크섬을 고정해 넣는다.
- worker가 `os/exec`로 실행하고 JSON 출력을 읽는다.
- 스캐너는 공통 인터페이스 뒤에 둔다. 도구를 추가할 때 인터페이스 구현 하나를 더하면 된다.
- [제안] 스캐너 출력에는 평문 값이 들어 있으므로 메모리나 tmpfs에서만 다루고, 처리 후 지운다. 로그에 남기지 않는다.

### 도구별 역할

| 도구 | 역할 |
|---|---|
| betterleaks | 키, 토큰, 비밀번호 등 알려진 형식의 값. 전화번호, 주민등록번호, 이메일, 카드번호 등 형식이 있는 고객정보 규칙 추가 |
| opengrep | 문맥으로 잡아야 하는 항목. Spring dataSource 설정, `ssh`/`scp`/`sshpass` 인자, 설정 키 이름 기반의 호스트와 계정, Java 리터럴 대입 패턴 |

주소는 "시/구/동/로" 같은 키워드에 의존하는 규칙으로 가능한 범위만 탐지한다. 오탐과 누락이 모두 많을 것으로 예상하며, 사람이 선별한다. [확정]

## 6. 동작

### 전체 흐름

```
프로젝트 등록 → 스캔 → 탐지 목록 → 판정 → 적용 → 확인 재스캔 → 리포트
```

### 프로젝트 등록 [제안]

- compose에서 작업 루트 디렉터리 하나를 worker에 마운트한다.
- 사용자는 그 아래의 경로를 프로젝트로 등록한다. 작업 루트 밖을 가리키는 경로는 거부한다.

### 스캔

- 화면에서 수동으로 시작한다. [제안]
- 현재 작업본의 파일만 대상으로 한다. git이 추적하지 않는 파일과 `.gitignore` 대상 파일도 포함한다. 로그, 샘플 데이터, 개인키가 주로 여기에 있기 때문이다. [확정]
- 두 도구의 결과를 합친다. "파일, 위치, 값의 지문"이 같으면 하나의 탐지 항목으로 묶고, 어느 도구의 어느 규칙이 잡았는지를 항목에 기록한다.
- 스캔 시점의 커밋 해시, 도구 버전, 규칙 버전을 스캔 기록에 남긴다.

### 탐지 항목이 갖는 정보

| 정보 | 저장 위치 |
|---|---|
| 분류, 파일, 줄과 열 범위, 탐지 규칙 | postgres |
| 값의 지문 | postgres |
| 마스킹된 미리보기 | postgres |
| 주변 코드 몇 줄 (해당 값은 마스킹) | postgres |
| 파일 내용의 해시 (스캔 시점) | postgres |
| 원본 값 (비밀 값 분류만) | OpenBao |

- [제안] 지문은 단순 해시가 아니라 OpenBao가 보관하는 키로 계산한 HMAC이다. 짧은 비밀번호는 단순 해시로는 역산이 쉽기 때문이다. OpenBao의 transit 기능을 쓴다.
- [제안] 비밀 값의 마스킹 미리보기는 앞 4자와 `****`다. 8자 미만인 값은 전부 가린다.
- [제안] 비밀 값 분류의 원본은 스캔 시점에 OpenBao의 임시 경로에 저장한다. 정탐 여부를 판단하려면 admin이 원본을 봐야 하는 경우가 있고, web은 소스를 읽을 수 없기 때문이다. 오탐으로 판정되면 지운다.
- 고객정보의 원본은 어디에도 저장하지 않는다. admin도 도구에서 볼 수 없다. [확정]
- [확정] 고객정보 분류는 주변 줄을 저장하지 않는다. 로그와 샘플 데이터의 주변 줄에는 탐지되지 않은 다른 고객정보가 섞여 있을 수 있기 때문이다. 미리보기도 숫자를 노출하지 않고 종류와 형식만 남긴다(예: `전화번호 010-****-****`). 판정 화면에서는 종류, 파일, 줄 번호, 같은 파일 안의 건수를 보여주고, 내용 확인은 개발자가 자신의 편집기에서 한다.

### 스캔 간 항목 식별 [제안]

"프로젝트, 지문, 파일 경로"가 같으면 같은 항목으로 본다. 줄 번호가 밀려도 이전 판정이 유지되고, 오탐으로 판정한 항목이 다음 스캔에서 다시 미판정으로 올라오지 않는다.

### 판정 [확정]

항목마다 다음 중 하나를 고른다.

| 판정 | 의미 | 적용 시 동작 |
|---|---|---|
| 외부화 | 정탐. 소스에서 빼낸다 | 치환 또는 파일 제거, OpenBao 보관, manifest 기록 |
| 삭제·마스킹 | 고객정보 | 소스에서 가린다. 보관하지 않는다 |
| 오탐 | 민감 정보가 아니다 | 없음. 사유를 남길 수 있다 |
| 보류 | 지금 처리하지 않는다 | 없음. 사유를 고른다 (예: 구조 변경 필요) |

- AI 판정은 없다. 사람이 판정한 항목만 적용으로 넘어간다. [확정]
- 규칙 기반 제안은 한다. [확정]
  - 탐지 규칙과 변수명, 설정 키로 placeholder 이름을 만들어 미리 채운다.
  - 같은 지문에 과거 판정이 있으면 그 판정을 미리 채운다.
- 판정 단계는 "제안자"를 끼울 수 있는 구조로 만든다. 2차에서 AI 제안을 붙일 자리다. [확정]
- JSP, JS, HTML의 항목은 "외부화"를 고를 수 없다. "보류: 구조 변경 필요"가 기본값이다. [확정]

### placeholder [확정]

- 문법은 `${이름}`이다. Spring의 property placeholder와 shell 환경 변수로 그대로 동작한다.
- 기존 `${...}`와 구분하기 위해 접두어를 붙인다. 설정 파일은 `ext.`, shell은 `EXT_`다.
- 같은 값(같은 지문)은 같은 이름을 쓰는 것이 기본이다. [확정]
- [확정] 묶음은 나눌 수 있다. 포트 `3306`이나 계정 `root`처럼 값은 같아도 가리키는 대상이 다른 경우가 있기 때문이다. 판정 화면에서 묶음의 일부 위치를 떼어 다른 이름을 줄 수 있고, 판정과 이름의 단위는 "지문 + 묶음"이다. 호스트, 포트, 계정명처럼 값이 흔한 구성 요소는 설정 키나 문맥이 같을 때만 자동으로 묶는다.
- [제안] 이름 형태는 `ext.<분류>.<대상>.<항목>`이다(예: `ext.db.main.password`). 프로젝트 안에서 유일해야 하고, 판정 화면에서 고칠 수 있다.
- 접속 정보 묶음(JDBC URL, `user@host:port`)은 구성 요소별로 나눠 치환한다. [확정]
- Java 문자열 리터럴 안의 값은 리터럴 안에서 `${이름}`으로 바뀐다. 이 상태로는 동작하지 않으므로 리포트에 "코드 수정 필요"로 표시한다. [확정: 동작 보장은 범위 밖]

### 적용

- 조건: 대상이 git 저장소이고, 추적되는 파일에 커밋되지 않은 변경이 없어야 한다. [확정]
- 추적되지 않는 파일의 비밀 값은 그대로 적용한다. 원본이 OpenBao에 남는다. [확정]
- 추적되지 않는 파일의 고객정보 마스킹은 되돌릴 수 없다. 적용 확인 화면에서 "복구 불가"로 따로 표시하고 별도 확인을 받는다. [확정]
- 스캔 이후 파일 내용이 바뀐 항목은 적용하지 않고 "재스캔 필요"로 표시한다. [제안]
- 순서: OpenBao 저장, 소스 치환, manifest 기록. OpenBao 저장에 실패하면 소스를 건드리지 않는다. [제안]
- 도구는 파일만 고친다. 커밋하지 않는다. 개발자가 `git diff`로 확인하고 커밋하며, 되돌릴 때도 git을 쓴다. [제안]
- 개인키와 인증서 파일은 내용을 OpenBao에 저장한 뒤 파일을 제거한다. [확정]
- 고객정보는 종류를 알 수 있는 고정 표식으로 바꾼다(예: `[REDACTED:phone]`). 줄을 지우지 않는다. [제안]
- 적용이 끝나면 자동으로 재스캔해 실제로 사라졌는지 확인한다. 이 결과가 추이 통계의 한 점이 된다. [제안]

### manifest [확정: 용도와 내용, 제안: 형식]

프로젝트 루트의 `secrets-manifest.yml`. 사람이 읽고 Secrets Manager 이전 등 다음 작업에 참고한다. 값은 들어가지 않는다.

```yaml
version: 1
entries:
  - name: ext.db.main.password
    category: storage-credential
    action: externalized
    store: openbao:secret/data/projects/shop/ext.db.main.password
    locations:
      - file: src/main/resources/application-prod.yml
        line: 14
      - file: src/main/webapp/WEB-INF/spring/root-context.xml
        line: 31
  - name: EXT_DEPLOY_SSH_KEY
    category: ssh-key-file
    action: file-removed
    store: openbao:secret/data/projects/shop/EXT_DEPLOY_SSH_KEY
    locations:
      - file: deploy/id_rsa
```

고객정보 마스킹 건은 manifest에 넣지 않고 리포트에만 남긴다.

저장소에 이미 `secrets-manifest.yml`이 있으면 덮어쓰지 않고 읽어서 이어 쓴다. [확정]

### OpenBao 사용 범위

| 용도 | 접근 |
|---|---|
| 외부화한 값의 보관 (KV v2, 프로젝트별 경로) [확정] | worker 쓰기, web 읽기 |
| 판정 전 원본의 임시 보관 [제안] | worker 쓰기와 삭제, web 읽기 |
| 지문 계산용 HMAC (transit) [제안] | worker만 |
| 감사 기록 (audit device) [제안] | OpenBao 자체 기능 |

원격 저장소 인증 토큰 보관은 2차에서 원격 대상을 다룰 때 추가한다.

## 7. 인증과 권한 [확정]

- Keycloak OIDC로 로그인한다. 세션은 valkey에 둔다.
- 역할은 두 가지다.

| 역할 | 할 수 있는 일 |
|---|---|
| `user` | 프로젝트 등록, 스캔, 판정, 적용, 리포트, 대시보드. 값은 마스킹된 상태로만 본다 |
| `admin` | 위 전부와 원본 값 보기 |

- 원본 보기는 별도 동작이다. 볼 때마다 OpenBao에서 읽고 앱에 캐시하지 않는다. 누가 언제 어떤 항목을 봤는지 감사 로그에 남긴다.
- [제안] 판정, 적용, 원본 보기는 모두 postgres 감사 로그에 사용자와 시각을 남긴다. 감사 로그에도 값은 넣지 않는다.
- [제안] 상태를 바꾸는 요청에는 CSRF 방어를 적용한다.

## 8. 화면

배치는 시안으로 확인했다. 시각 디자인은 구현 전에 Claude design으로 시안을 만들어 다시 확인받는다.

### 판정 화면: 목록 + 상세 [확정]

```
┌ 필터: 분류 / 상태 ────────────────────────────────────────────┐
├─────────────────────┬─────────────────────────────────────────┤
│ DB 접속 · 2곳       │ application-prod.yml:14                 │
│  ext.db.main.pass.. │ betterleaks generic-password,           │
│ ssh · 1곳           │ opengrep spring-datasource              │
│ 고객정보 · 37곳     │ 13    username: shop_app                │
│ 제휴사 토큰 · 1곳   │ 14    password: Sh0p****                │
│ …                   │ 같은 값: root-context.xml:31            │
│                     │ placeholder [ext.db.main.password]      │
│                     │ [외부화] [삭제·마스킹] [오탐] [보류]    │
│                     │ 사유(선택) [                    ]       │
└─────────────────────┴─────────────────────────────────────────┘
```

- 같은 값은 한 묶음으로 보여주고 한 번에 판정한다.
- 주변 코드와 탐지 규칙이 항상 옆에 보인다. 고객정보 분류는 예외로, 종류, 파일, 줄 번호, 같은 파일 안의 건수만 보인다.
- 묶음의 일부 위치를 떼어 다른 placeholder 이름을 줄 수 있다.
- 목록의 항목을 마우스로 눌러 선택하고, 판정도 버튼을 눌러서 한다. 키보드 단축키는 두지 않는다. [확정]
- 고객정보처럼 건수가 많은 분류는 묶음 단위로 일괄 판정할 수 있다.

### 대시보드 [확정: 시안 그대로]

- 맨 위: 남은 항목(지난 스캔 대비 증감), 외부화 완료, 삭제·마스킹, 오탐, 보류 건수
- 남은 항목 추이: 스캔별, 분류별 누적
- 분류별 남은 항목
- 오탐이 많은 규칙
- 프로젝트별 표: 마지막 스캔, 남은 항목, 완료율, 보류
- 필터: 프로젝트, 기간

### 리포트 [확정]

스캔 한 건 기준이다. 주 독자는 개발자이고, 공유를 위해 PDF로 내보낸다. 값은 들어가지 않는다.

1. 요약: 탐지, 외부화, 삭제, 오탐, 보류 건수와 이전 스캔 대비 증감
2. 외부화한 항목: placeholder 이름, 분류, 파일과 줄, 저장 위치, 코드 수정 필요 여부
3. 삭제·마스킹한 고객정보: 종류별 건수와 파일
4. 구조 변경이 필요한 항목
5. 남은 미판정 항목
6. 오탐으로 판정한 항목과 사유
7. 판정 이력

PDF는 별도 컨테이너에서 만든다. [확정]

- [제안] 헤드리스 브라우저 기반 변환 서비스(Gotenberg)를 쓴다. 화면과 같은 템플릿에 인쇄용 스타일을 더해 쓰므로 화면과 PDF의 모양이 같다.
- [제안] web이 리포트 HTML을 완성해 pdf 컨테이너로 보내고 PDF를 돌려받는다. pdf 컨테이너가 web에 접속해 페이지를 가져오는 방식은 쓰지 않는다. 변환기에 세션이나 접근 권한을 줄 필요가 없어진다.
- [제안] 리포트 HTML은 글꼴, 스타일, 차트를 모두 포함한 상태로 보낸다. pdf 컨테이너는 외부 자원을 받아오지 않는다. 한글 글꼴은 pdf 이미지에 넣는다.

### 그 밖의 화면 [제안]

로그인, 프로젝트 목록과 등록, 스캔 목록과 진행 상태, 적용 확인(적용할 항목 요약과 조건 점검 결과), 감사 로그(admin).
